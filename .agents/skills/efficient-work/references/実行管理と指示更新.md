# 実行管理と指示更新

委任・分担復旧・指示更新・統合時の該当節だけを読む。本書と品質・レビュー・引継ぎの「管理役」は、不在時には主担当が担う。モデル別の詳細は[モデル選択と再利用](モデル選択と再利用.md)、レビュー・品質・保存する再開情報は[品質・レビュー・引継ぎ](品質・レビュー・引継ぎ.md)の必要節だけ読む。

## 直接処理と管理役

密接な設計判断、同じ共有状態の頻繁な編集、必要な背景を小さく正確に渡せない作業は主担当に残す。独立して受入条件を閉じられるまとまった調査・実装には委任を検討する。単純作業に管理層を足さず、管理役の入力・出力・履歴・待ち・再試行も総負担に含める。

### 実作業を中心にした構成

主担当は要求・範囲・費用・品質・mergeと最終受入を判断し、実行側は調査・実装・検証を完了単位として閉じる。構成は実際に進められる仕事から決め、管理専任者の起動は継続調整で減らせる主担当の負担と追加費用を比べて選ぶ。下表の人数は主担当を除く。独立レビューも具体的な成果と受入条件を持つ実作業として扱う。

| 実作業と利用可能枠 | 望ましい構成・分担 |
|---|---|
| 小さな一仕事 | 主担当が直接完了する |
| 作業者一人で閉じる仕事 | 主担当→作業者一人。作業者が調査・実装・検証を一貫して行い、主担当は必要な判断と受入を行う |
| 少数の独立作業、短い調整 | 主担当→作業者A・作業者B。各担当が異なる完了単位を持ち、主担当は境界と受入を管理する |
| 複数の実作業担当に継続的な調整が必要で、その枠もある | 主担当→管理役一人→複数の作業者/レビュー役。管理役が通常調整を閉じ、主担当へ判断だけを返す |
| 複数の管理役が有効な規模 | 各系統も上の管理役設置条件を満たし、管理役ごとに独立した作業系統・成果・担当・worktreeを持つ。各系統で実作業が進み、主担当が系統間の依存とmergeを判断する |
| 枠不足や残件減少で実作業者が一人になった | 主担当→作業者一人へ簡素化する。管理役が実作業を引き受ける場合は作業者を兼ねる契約に変え、変更する所有と連絡先を揃える |

「管理役二人→共通の作業者一人」は、管理の重複と実行の直列化を生む構成として、主担当が速やかに上表へ組み替える。依頼窓口の一本化だけで完了とせず、余剰の管理専任契約を閉じ、独立した実作業があれば所有を分けて割り当てる。役割の引渡しは[担当契約と連絡](#担当契約と連絡)、枠の復旧は[分担の復旧と定期見直し](#分担の復旧と定期見直し)を適用する。

| 運用中に見つける状態 | 望ましい立て直し |
|---|---|
| 管理役が伝言・全文再読・同じ結果の集約だけを重ねている | 契約と判断パケットを一か所に集約し、実益のある管理役一人か主担当からの直接委任へ揃える |
| 管理役の調査中に作業者が待つ、または一人の依頼待ちが伸びる | 最小契約が揃う独立作業から開始し、狭い参照と差分で管理する。独立残件は別担当へ分け、順序が必要な仕事は一人が一貫して閉じる |
| 主担当と担当が同じ調査・編集・検証を重ねる | 実行を所有者へ任せ、主担当は判断に必要な差分・証跡を確認する。独立レビューは目的と観点を明示して割り当てる |
| 小さすぎる依頼や無関係な仕事が一人の履歴に積まれる | 同じ背景の仕事を受入条件までまとめ、異なる背景の仕事は直接処理か新規担当へ分ける |
| 管理役が枠を使い切り、実作業を増やせない | 実作業の枠を先に確保できる構成へ縮め、管理役の実務兼任・直接委任を選ぶ |

各担当の役割名に加えて「今進める実作業/必要な調整・成果・待ち先」を短い担当メモで把握する。着手時と[定期見直し](#分担の復旧と定期見直し)で、コアの進展、管理と待ちの負担、品質・回帰保護を照合して構成を更新する。agent数や稼働率を上げるための仕事追加ではなく、必要な残件を閉じる構成を選ぶ。

| 担当 | 仕事 | 境界 |
|---|---|---|
| 主担当 | 要求・全体設計、範囲と費用、未解決対立、最終受入を判断 | 管理役へ目的・不変条件・受入条件・利用可能枠・再委任範囲・コミット実行者を渡す。最終責任を保持 |
| 実行管理役 | 広い範囲の依存、順序、担当契約、検証対象、通常質問、証跡集約、指示更新、回収を管理 | 利用可能モデルのうち、必要な文脈・調整能力を満たす低コスト担当を優先候補とする。要求の意味・品質閾値・承認範囲の変更は主担当の判断を受けて反映する |
| 作業者 | 指定された完了単位を実行 | 指定範囲で調査・修正・検証。通常の質問と結果は管理役へ返す。追加分担の判断・担当起動は管理役が行い、作業者は必要性と依頼内容を管理役へ返す |
| レビュー役 | 変更リスク・レビュー観点に必要な能力と独立性で選ぶ | 指定ソースを独立に調べ、管理役と作業者へ根拠を返す。受入は主担当が判断し、編集は所有する作業者が行う |

### 再委任と総枠

再委任は主担当が明示許可した実行管理役だけが、対象・最大深さ・総同時枠の範囲で行う。最大深さの初期値は主担当→管理役→作業者またはレビュー役まで。配下全体の同時上限は指定がなければ二人とし、主担当は上の構成表と実環境の上限に照らして必要人数を明示する。管理役一人＋実作業者二人には配下三枠が必要なため、その構成には主担当の三枠以上の明示配分と実際の空きを揃える。人数を増やす利益がなければ直接委任を選ぶ。主担当と管理役は一つの担当メモで総数を数え、待機中の枠もツール仕様に従って扱う。

委任に実益がある場合は、利用可能なら担当モデル・設定・役割を明示する。実行環境ごとに異なる起動・継続・連絡機能は、その環境で確認できる仕様に従い、存在しない機能や設定を前提にしない。必要な背景だけを渡し、担当が利用できるツールと権限を確認して依頼する。関連する検索・調査は一つの依頼にまとめる。

## 分担の復旧と定期見直し

起動失敗時は、管理役（不在時は主担当）がツール結果から同時枠・一時障害・モデルの利用可否・権限/指示の制約を切り分け、失敗理由・暫定担当・残る委任候補・次回確認時点を担当メモへ残す。一時障害や枠不足では次の小さな実行単位まで暫定対応し、主担当による代行はその区切りで分担を再判定する。利用者の直接処理指定や権限上の制約は、その条件が変わった時に見直す。

復旧を待つ間も独立した許可済み作業を進める。担当の完了・枠解放・障害復旧の通知があれば、その時点で再確認する。通知がなくても継続作業中は原則5〜10分ごと、または次の調査・編集・テスト単位の着手前の早い方で確認する。長いテスト待ちは取得可能な状況通知・待機の区切りに確認を組み込み、再試行だけのために主担当を待機させる費用も含めて間隔を調整する。

再試行は委任の利益と実際の空き枠・モデルの利用可否を確認して行う。同じ一時障害が続く場合はサービス指定の待ち時間を優先し、指定がなければ5分→10分→20分を目安に間隔を広げ、次回時点を更新する。作業単位ごとの分担確認は続け、条件が変わったら前倒しする。残件が小さく直接完了する方が有利ならその根拠を残して閉じる。再試行も元の権限・総同時枠・モデルと思考の選択条件を適用する。

起動成功後は現在のソース・成果・残件から必要な契約だけを渡し、[所有移管](#担当契約と連絡)を完了する。定期確認は既存の担当メモと状態変化を使い、長い再調査・全文再読・モデル比較を繰り返す代わりに、残件・待ち先・利用可能枠の差分を確認する。一人への集中や管理待ちは[構成表](#実作業を中心にした構成)で立て直し、効果は[完了単位の振り返り](品質・レビュー・引継ぎ.md#完了単位で運用を改善する)で確認する。

## 担当契約と連絡

各担当の指示・優先順位・終了を管理する管理役は同時に一人とし、管理役不在時は主担当を所有者とする。別の管理役は、その所有者へ依頼・根拠・必要時期を送り、所有者が現行契約への影響と順序を決めて担当へ渡す。当事者間の直接連絡は根拠共有と調整に使い、作業契約の追加・変更は所有者へ集約する。

管理役を移す場合は、旧管理役が旧契約の完了または安全な停止、未完了作業・生存process・編集所有・成果を引き渡し、新管理役と担当が現行契約を受領してから再開する。移管は上記の所有変更であり、[コンテキスト再利用の継続条件](モデル選択と再利用.md#渡したコンテキストと再利用性で分担を決める)も満たす場合に行う。

独立作業は編集範囲・実行資源を分け、最低限の契約が揃ったものから開始する。同じ担当への複数依頼は順次処理として扱う。枠・依存・共有資源で順次実行を選ぶ理由を短く残し、待ちや管理負担が増えたら[構成表](#実作業を中心にした構成)と[復旧手順](#分担の復旧と定期見直し)を使う。

| 契約へ渡す内容 | 具体化すること |
|---|---|
| 目的と正本 | 目的、対象ソースの基準commitまたは差分、必要な原文・規約・決定、受入条件。[モデルに適した入力](モデル選択と再利用.md#得意な工程に合わせて渡す)を揃え、適用境界・数値・単位・例外・品質閾値は正確に保持する |
| 所有と権限 | 対象ファイルと編集可否、App/packageの工程、共有Simulator/build/processの所有者、委任・外部操作の許容範囲 |
| 実行と終了 | 検証方法、終了条件、返す証跡、連絡先の管理役ID、担当間の直接連絡先、適用する指示記録の位置と更新日時 |

管理役は一つの短い担当メモに、自分と各担当の識別子・利用モデル/設定（確認可能な場合）・管理所有・対象worktree/branch・編集範囲・要求/更新と参照先・既読資料/確認ソース・成果/未解決・実行handle・稼働/待機と待ち先を保持する。既存記録を参照し、同じ情報の転記は参照へ揃える。[再利用表](モデル選択と再利用.md#渡したコンテキストと再利用性で分担を決める)の継続条件と所有を確認してから差分を渡し、担当変更・履歴肥大化も同表で判断する。

作業者とレビュー役は、実行環境で利用できる連絡手段を通じて管理役へ連絡し、同じ論点の当事者間でも必要な根拠を共有する。作業者は待ち・修正・再検証を管理役へ返し、管理役は通常質問に既存決定の範囲内で答える。自動テストの実行・解析・許可範囲内の修正は[品質・レビュー・引継ぎ](品質・レビュー・引継ぎ.md)の該当節で担当側に閉じ、難しい原因調査も必要な推論能力とツールを持つ担当へ渡す。主担当へは判断が必要な論点を根拠付きで渡す。変更指示は管理役が正本へ反映・差分配信し、要求変更は正本と関係担当へ反映する。

返却は結論、根拠のパス・行・URL、変更箇所、検証結果とログ保存先、未解決に絞る。長い探索記録は参照へ退避する。管理役も主担当も採用時は、判断に必要な原文・差分・証跡を確認する。

| 主担当へ戻す判断パッケージ | 含める内容 |
|---|---|
| 要求の曖昧さ・正本との矛盾 | 該当原文と参照、解釈候補、影響、管理役の推奨、必要な回答 |
| 範囲・費用・権限・品質の変更 | 現在の許可と提案差分、理由、選択肢と負担・品質への影響。未承認部分を止め、独立作業は続ける |
| 未解決対立・進展なし・外部制約 | 相反する証拠、試行と結果、不足情報、止めた対象、再開条件。次の試行は仮説や観測が変わるものを選ぶ |
| 最終受入 | 要求充足、最終対象差分、検証ソース・設定・環境と結果、残る制限と未確認、レビューの処理状況、受入の推奨 |

ツールが子の完了を親へ自動通知することや、孫が親以外へ起動できないことがある。通信・既存担当の再利用がツリー制約でできなければその制約を明記し、主担当が必要な起動・中継だけを行う。管理役への直通が失敗した場合も、配送不能の範囲をツール結果で示し、確認できたツール結果・宛先・未配送内容を添えた最小パケットだけを主担当が管理役へ中継する。必須報告の隠蔽と承認回避は禁止する。主担当が利用者への報告・承認を担当する。利用者への質問と重大な判断は主担当が担う。

## 指示の正本と更新

作業開始時に管理役は指示の正本を一つ示す。短い作業なら担当メモ、長い作業なら既存引継ぎ文書を使い、恒久要求・仕様・検証記録はリポジトリの分類へ置く。製品要求を満たす進め方をスキルで定める。ゴール遂行中のスキルの扱いは[作業中の改善記録と後続のスキル改訂](#作業中の改善記録と後続のスキル改訂)に従う。

| 更新記録 | 残す内容 |
|---|---|
| 出典と担当 | 利用者の訂正または決定の参照、正本パスと更新日時、起案者・更新担当・判断した主担当。指示の識別には見出し・出典・更新日時を使う |
| 変更理由と範囲 | なぜ変えるか、変更前の前提と置換する文言、維持する条件、適用対象と対象外、発効条件 |
| 対象と検証 | 対象commitまたは差分・ファイル・設定・環境、影響する検証、再検証の要否と根拠、未解決 |
| 実行中への影響 | 該当担当・process・成果の有効/無効、停止・継続・やり直しの範囲、次の完了条件 |
| 配信と受領 | 配信先、受領確認と理解した適用範囲。未確認の担当と次の取得方法 |

既存担当へは差分と置換対象を送り、担当が受領した指示の位置・更新日時、変更後の範囲と検証を言い返して一致を確かめる。新規担当には現行契約と必要原文を渡す。担当の受領と理解の一致を確認して適用済みとする。返信待ちは影響する次の編集・検証・受入を止め、無関係な作業を進める。送信が処理中のツールを止めない場合、その結果は旧条件の証跡と明記し、再利用は新条件への影響を確認してから判断する。旧条件の実行が新条件や共有状態を壊す、または不要な費用を生む場合は、当該作業が所有し安全に止められるprocessだけを停止する。参照のみのテストなど新条件へ影響しない実行は継続して旧条件の証跡として保持できる。他作業・所有不明のprocessやSimulatorを止めず、判断が必要なら対象と影響を主担当へ返す。

利用者の明確な訂正・変更指示は既に与えられた承認として、管理役が既存の権限と範囲内で正本へ差分適用・配信する。要求の解釈が曖昧、正本との矛盾、範囲・品質・費用のトレードオフ、外部操作・承認範囲または所有の衝突が未解決な場合だけ、その論点を主担当の判断へ戻す。既存許可内の誤記修正や確定済み決定の伝達も管理役で閉じ、明確な訂正は既存承認の範囲で適用する。実行権限は元の承認範囲を維持する。

秘密・音声内容の記録への複製は禁止する。全文ログ・探索履歴は適切な保存先を参照する。原文の参照と判断に必要な抜粋だけを保ち、重要な数値・例外・禁止は正確に保持する。古い記録は現行指示と区別して置換先を示し、過去の成功は元条件で保持し、新条件は対応する結果を記録する。圧縮前は正本と受領状態を含む再開情報を保存し、復元後はその位置と実ソースの一致を確認して必要な担当へ差分を再通知する。

## 作業中の改善記録と後続のスキル改訂

ゴールを遂行する主担当・管理役・作業者は、スキル本文を参照専用として扱う。作業中は現行ルール内で入力・モデル/思考・分担・待ち方を調整し、改善を続ける。恒久的なスキル改訂は、別途明示されたスキル保守の依頼で行う。今回のようなスキル改訂の依頼はその保守工程として扱い、製品実装の権限と分ける。

運用上の遅延・費用増・手戻り・指示不足を見つけた担当は、管理役へ根拠を返す。管理役は[改善候補の開発運用欄](../../../../docs/backlog/改善候補.md#開発運用とスキルの改善候補)の同じ論点を一件にまとめて更新する。観測事実と利用者報告/仮説を分け、次を短く残す。

| 残す情報 | 内容 |
|---|---|
| 条件と問題 | 日時、対象作業/ソース、モデル/思考と構成、渡した指示の不足、待ち・再読・再試行等の事実。利用可能なメッセージ・差分・証跡の参照を使う |
| 影響と暫定対応 | コアの進展・時間/利用量・品質/回帰への影響と未計測、現行権限内で変えた分担/入力、結果と残件 |
| 改訂候補と再確認 | 関連するスキルの節、判断を変えたい点、同じ問題を見分ける条件、次回の確認方法、記録済み/見直し待ち/指示反映済み/効果確認済みの状態 |

記録は節目に集約し、コアの阻害や重大な品質問題はその時点で主担当へ返す。参照先が読めない・記録先が書けない場合は既存の引継ぎ情報へ残して未反映と明記する。後のスキル保守担当は該当課題と現行本文を照合し、再現条件に合う変更だけを正本へ集約して検証・commitし、課題へ反映先を記す。指示の反映と実運用の効果確認を分け、次の通常作業で結果を追記する。スキル変更のためだけに元のゴールを広げる代わりに、この記録と次の保守工程で改善を蓄積する。

## 統合とコミットの単一実行者

主担当は統合とコミットの可否・対象・実行者を判断する。管理役を置く構成では、開始時に管理役または一人の作業者を単一実行者として指定し、[完了単位](品質・レビュー・引継ぎ.md#動作を保つ小さな完了単位)の検証と局所commitの許可条件を満たした時点で実行し、mainへの統合は主担当が対象を受け入れてmergeを明示許可してから行う。管理役が必要ない短い作業は主担当が直接終える。ツール・権限上どうしても主担当の操作が必要なら、その部分だけを主担当が実行する。実行委任は判断責任の移転ではない。実行者は同時に一人とし、交代時は停止と所有移管を確認する。メッセージ作成は既存担当または主担当が直接行う。

実行者は検証対象と最終差分・既存indexを確認し、自分の差分だけを含むパス限定の方法を使う。他作業のindexを保護し、同じファイルに他作業が混在し安全に分離できなければそのコミットを止めて主担当へ戻す。他担当が書込中なら待ち、commit後に対象ファイルと内容が決定・検証と一致する証跡を返す。統合は主担当が受け入れた変更を対象にする。


## 管理役単位のworktreeとmainへの段階的merge

利用者の「実行制御役」は本スキルの実行管理役として扱う。並行作業を隔離するため、実行管理役単位でmain由来の短期branchとworktreeを使うことを許可する。worktreeは管理役単位で共有し、同じ管理役の配下は編集所有を分けてその作業領域を使う。小作業や編集が競合しない作業は既存の作業領域を使う。別管理役と分かれたworktreeでもApp/package工程・共有Simulator/build/processの所有と総同時枠は共通して守る。

[開発方針の完了単位](../../../../docs/policies/開発方針.md#小さく動く単位で検証・コミットする)で検証・commitを閉じ、mainへ段階的にmergeする。worktree内の局所commitだけで滞留の確認を終えず、検証済み・merge許可待ち・統合済みを担当メモで区別し、小さな単位の統合判断を親へ順次返す。管理役は実務と記録更新を行えるが、各単位のmerge許可・保留の決定と管理責任は親/主担当が必ず持つ。worktree使用・局所commit・mergeの許可はそれぞれ対象を明確にして管理する。

| 親/主担当が必ず管理する項目 | 記録と判断 |
|---|---|
| 領域と所有 | worktreeの絶対パスとbranch、管理役と編集所有、基準mainのcommit、対象commit/差分と予定する小さな完了単位 |
| 検証と残件 | 検証したソース/差分・設定・環境と結果/証跡、仕様更新、残る失敗・未確認・依存、他単位との関係 |
| 許可または保留 | 具体的な対象commit/差分・統合先mainの状態に結びつく主担当の決定、理由、保留の再開条件、許可された単一実行者。許可への変更は主担当が判断する |
| 統合後 | 統合済commit、取り込まれた対象と検証の一致、次の単位と残件、worktreeと生存資源の継続/回収状態 |

管理役はmerge判断用に対象と根拠・残件・推奨を集約し、親/主担当が許可または保留を明示して記録する。許可された単一実行者へ操作は委任できるが、mergeは明示許可された対象と統合先に限定する。統合先がdirty、他作業のindexが存在するなど安全に分離できない場合、未解決の統合は保留して主担当へ戻す。他作業を変更する無断のstash/reset/cleanは禁止する。他作業のworktree・未コミット/未追跡差分・processを保護する。

許可後に対象commit/差分、競合解消内容、依存関係、mainの状態が変わったら、管理役は許可時との影響を確認して親/主担当へ示す。許可範囲と検証がなお有効か不明、または対象・挙動に影響する場合は再判定までmergeを止める。検証も変更の影響範囲で更新し、検証は変更後の対象ソースと対応させる。主担当が判定できる記録を残し、許可の有効性は変更影響と証拠で示す。

保留中は独立した許可済み作業を続けられるが、保留対象は許可時の状態を保持する。新しい単位と対象・所有・検証を分け、必要な範囲判断へ戻す。圧縮/引継ぎではこの表と許可・保留の根拠を復元できるようにする。不要なworktreeは対象のmain統合、未コミット差分・未追跡ファイル、生存process/検証handle、残す証跡を確認してから回収する。未統合・所有不明の作業領域の無断削除は禁止する。

[開発方針](../../../../docs/policies/開発方針.md)のブランチ運用とビルド場所を適用する。通常のXcode Build/Run/Test/Archiveはmainの実projectとXcode既定DerivedDataを入口とする規定を維持し、worktreeは許可された分担と隔離検証の範囲で使う。一方、並行変更に必要な検証をworktreeで行うことと通常buildの入口/設定の変更は区別し、隔離領域での検証は正本の範囲と今回の許可に従って選ぶ。正本の制約との実際の矛盾によって必要な検証を実施できない場合だけ、該当原文・必要な例外と理由・選択肢を主担当へ返す。mainへの統合と方針の変更は主担当の判断・承認に従って進める。
