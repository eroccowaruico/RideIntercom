# 選択の根拠と評価

## 公式情報とこのプロジェクトの初期方針

確認日: 2026-11-01。以下は公開情報の要点と、それを使った運用判断を区別した記録である。モデルの更新、利用可能な設定の変化、実績との不一致があるときだけ再確認する。

| 根拠 | 公式情報で確認したこと | スキルへ適用した判断 |
|---|---|---|
| [モデル選択](https://developers.openai.com/api/docs/guides/model-selection) | Lunaは限定された作業・抽出、Solは複雑な技術作業、Terraは画面操作・提供資料からの文章・限定修正の候補。実際の仕事と同じ入力・思考で比較して調整する | 単純な調査はLuna、検証方法が明確な局所実装はTerra、契約をまたぐ実装はSolを初期候補にする。固定順位や能力保証にはしない |
| [Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)、[Astra](https://developers.openai.com/api/docs/models/gpt-6-astra) | Solは複雑なコードと低コストの両立、Lunaは限定作業、Astraは最難度作業に位置づけられる。対応する思考設定とAPI単価はモデルごとに異なる | 主担当Astraという利用者の選択を維持する。モデル単価と成功までの総費用は分け、Codexの消費をAPI単価で断定しない |
| [思考設定と運用](https://developers.openai.com/api/docs/guides/deployment-checklist) | 低い思考は抽出・定型処理、高い思考は診断・計画・複雑な比較へ使う。高い思考の利益は評価し、成功率・遅延・入力・出力・思考・cache等を含めて判断する | 必要な品質を満たす低い設定から選び、根拠のあるとき上げる。待ち時間や長さだけで思考を上げない |
| [Codexのサブエージェント](https://learn.chatgpt.com/docs/agent-configuration/subagents) | 指定がなければ親のモデル・思考を継承する。狭い仕事と根拠付きの返答で主担当のノイズを減らせる一方、委任自体もトークンと調整コストを使う | 別モデルと思考を明示し、担当と入力を限定する。短いコマンド・コミットは直接実行する |
| [Astra向けのスキルと指示](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) | 無差別なスキル読込、全資料の必読、長い指示、過剰な検証はコンテキストと時間を消費する。必要な詳細だけを段階的に読む | 日常の選択はSKILL.mdだけで行い、この参考資料を毎回読み込ませない。既読資料と成功済み検証の無条件反復を避ける |

Terraの単独モデルページは確認時に取得できなかったため、能力の根拠は取得できた公式モデル選択ページを使う。未取得ページの詳細やベンチマークを補って断定しない。

## 実行環境とモデル自身の申告

作成時の`collaboration.spawn_agent`は、`gpt-6-astra`、`gpt-6.1-sol`、`gpt-6.1-terra`、`gpt-6-luna`を公開している。別モデル・思考指定は`fork_turns: "none"`との組み合わせに限られる。親と同じ全履歴をforkするとモデル・思考の上書きを指定できない。

この環境が受け付ける思考はAstra・Sol・Terraがlow / medium / high / xhigh / max / ultra、Lunaがlow / medium / high / xhigh / max。これは作成時のツール仕様であり、APIの対応値や他クライアントの設定と同一とは限らない。ツールにない`none`等を公式APIの説明だけで指定しない。

モデルの自己認識は、公開された能力・ツール・知識や入力の限界と照合するために使う。担当モデルに不明点や不足入力を報告させるが、「得意」「自信がある」という申告を成功率や安全性の証拠にしない。内部推論や非公開ベンチマークを要求・推測せず、成果物と実行した検証で判定する。

## このチャットの振り返りと評価方法

このスキル作成前のやり取りでは、個人用への誤配置と要求の過剰な要約が手戻りになり、同じ資料の再読や長い出力もあった。対策は最初に配置・範囲・受入条件を合わせ、重要条件は原文へ辿れる形で保持すること。安価なモデルや短い要約を選ぶだけでは、この種の手戻りは解消しない。

そのやり取りではサブエージェントを使っていない。利用者が問題としている過去の高コストや圧縮回数の全履歴・請求・トークン計測値は、この記録では監査していない。公式の役割と本チャットで確認できる失敗を出発点にし、未測定の削減率を実績として扱わない。

| 評価する単位 | 見るもの |
|---|---|
| 調査・検索 | 正しい出典、反証と未解決点、読み取り範囲、再調査の有無、主担当に返す量 |
| コード・テスト | 要求の充足、契約・異常系、実行した回帰検証、統合時の手戻りと見逃し |
| コミット | 対象だけが含まれること、検証内容との一致、余計な再調査や子起動の有無 |
| 長時間の引継ぎ | 要求・数値・禁止事項・決定・対象ソース・失敗・残件・生存handleを再開後も復元できること |
| 費用と速度 | 分担、再入力、思考、統合、再試行、圧縮後の復元を含む成功までの総量と所要時間。取得できた値だけを比較する |

代表作業で失敗がなければ、モデル比較のためだけに同じ実作業を全モデルへ重複実行しない。変更は一度にモデル・思考・入力範囲のどれかを主に変え、実績から選択境界を狭く修正する。比較のために実サービス・実資格を使わない。

## 作成時の机上評価

2026-11-01にTerra / mediumを一つだけ使い、履歴をforkせずSKILL.mdと次の場面を渡して独立に判断させた。実コードの変更、追加agent、テストや外部検索は行わせていない。

| 場面 | 観測した判断 |
|---|---|
| 既知の一行検索、指定済みファイルのコミット | 主担当の直接処理 / 変更可能ならlow。子を起動しない |
| 再現テストと仕様の揃った局所Swift修正 | 短ければ直接処理、独立したまとまりならTerra / medium。機械的なモデル選択はしない |
| codec切替とRTC再接続の競合で原因不明 | 主担当の品質・設計判断を残し、独立した原因切り分けはSol / highを候補にする |
| 圧縮前にagent・test process・未確定要件・失敗が残る | 未確認を完了扱いせず、原文・証跡・handle・所有者・次の完了条件を保存する |

評価で指摘された既存indexの混入リスクと、直接処理／Terraへの委任の優先順位を本文へ明記した。これは選択・引継ぎ指示の机上評価であり、各モデルのコード品質の比較や実料金・速度の削減率の測定ではない。
