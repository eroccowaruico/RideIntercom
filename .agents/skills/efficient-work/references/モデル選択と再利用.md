# モデル選択とコンテキスト再利用

モデルの初期候補・思考を選ぶ担当が必要な節を読む。初回・モデル更新・対応値の不一致時だけ[選択の根拠と評価](選択の根拠と評価.md)も確認する。毎回のモデル調査・比較実験は不要。

## 仕事とモデル・思考の組み合わせ

まず主担当の短い直接処理で済むかを判断し、委任の利益がある場合にだけLuna・Terra・Solを選ぶ。表の仕事名だけで機械的に子を起動しない。

モデルと仕事の初期対応は[入口の表](../SKILL.md#最初の判断)を正本とする。以下はモデル内の思考選択と移管・再利用の判断だけを補う。

### 思考レベルはモデル内の相対指定として扱う

モデル選択と思考設定は区別しつつ、最終的には「モデル×思考×渡すコンテキスト」で選ぶ。同じlow / medium / highでも、モデルをまたいだ能力・思考トークン量・費用・速度の共通尺度ではない。Luna / highとSol / medium、Astra / lowなどの優劣や換算比を固定しない。モデル・版・クライアントで対応値や挙動も異なる。

下表はこのプロジェクトの運用上の初期基準であり、公式が定める能力境界ではない。同じ要求・入力・受入条件で、成功までの時間・費用・手戻りから調整する。

| モデル | lowを候補にする作業 | mediumを候補にする作業 | high以上を検討する条件 |
|---|---|---|---|
| Luna | 対象と答え方が明確な抽出・検索・定型操作 | 与えた背景内で完結する複数手順、条件の揃った小さな修正 | 範囲は狭いが確認すべき条件や推論が多い場合。Sol等への移管で必要な再入力・再調査も含めて比較し、不足情報を思考量で埋めさせない |
| Terra | 提供資料・画面からの抽出や整形、手順が確定した局所操作 | 画面・文章・局所コードの修正と結果確認 | 対象領域内で解くべき曖昧さや境界条件が残る場合。ドメインや契約を横断する判断が増えればSolまたは主担当への移管も比較する |
| Sol | 既に仕様・原因・変更範囲が確定した技術作業、既存担当の短い追従修正 | 調査・実装・検証を伴う通常の技術作業 | 要求の厳密性、複数契約・非同期競合、相反証拠・境界条件、過去の同種失敗からhigh以上が必要と判断できる場合は初めから選ぶ |
| Astra | 十分な背景と確定した方針を使う判断・整形・実行。抽出専用とは考えない | 要求解釈、全体設計、複数担当の統合・品質判断 | 未解決の根本原因や厳密な品質・設計上の対立があり、主担当で深く判断する必要がある場合 |

Sol / mediumは初期候補にすぎず、high以上でなければ必要な品質を満たせない仕事もある。入力と受入条件から判断できるなら、対応するhigh / xhigh / max等を初めから選び、low/mediumで失敗させてから昇格する手順にしない。全Solを高思考へ固定せず、必要な品質を満たす範囲で完了までの費用・速度を比較する。これは運用上の選択条件であり、特定設定での成功やモデル横断の能力換算を保証しない。

xhigh / max / ultraは利用可能というだけで選ばず、そのモデル・仕事で品質改善が見込めるときに使う。ultra等のクライアント固有のモードをAPIの思考設定と同一視しない。長時間のテスト待ちや履歴の長さは、それ自体では思考を上げる理由にならない。

失敗したら、まず入力不足、再現条件、環境・権限、検証方法を切り分ける。モデル能力の問題が示された場合に、同じ受入条件を維持して思考またはモデルを上げる。広い調査を低能力モデルへ無理に押し込むことも、狭い検索を高能力・高思考へ渡すことも避ける。同じ進め方で失敗を反復せず、解決の進展がなければ主担当へ戻す。上位モデルで解けた作業も、次の定型作業まで同じ設定を引きずらない。

## 渡したコンテキストと再利用性で分担を決める

起動前に、既知の担当が持つ目的・モデル・思考・既読資料・確認済みソース・成果を確認する。必要ならagent一覧や結果を見る。初回から関連する検索、原因調査、修正、検証を受入条件の閉じるまとまりとして分け、同じ背景を何度も渡さずに済むようにする。ただしAppとpackage等の工程分離や編集所有は守る。

| 状況 | 再利用・移管の判断 |
|---|---|
| 同じ領域・要求・ソースの続き | 既存担当のモデル・思考が十分なら、その担当へ差分だけを渡して再利用する。検索語や小さな追従修正ごとに新しい担当を作らない |
| 既存担当が高価だが背景を把握済み | 新しい安価な担当へ渡す準備・原文読込・調査再現・統合と比べる。短い追加確認なら既存Sol等で終える方が有利な場合があり、単価だけでLunaへ移さない |
| 別モデル・思考が適切になった | その実行環境で変更できるか確認する。この環境のfollowup_taskは既存担当のモデル・思考を変更する引数を持たないため、指示だけで変更済みと扱わない。新規担当が必要なら検証済みの背景・成果と残件を引き継ぎ、元の探索を繰り返させない |
| 無関係な仕事、古い判断、肥大化した履歴 | 再利用に固執しない。元担当の必要な成果だけを出典付きで取り出し、現行の要求・ソースを基準に新規担当へ渡す。利用者の訂正と矛盾する過去の前提は明示して更新する |
| 他担当が使える成果がある | 調査結果、再現条件、仕様、fixture、検証ログ・手順を参照可能な形で共有する。再利用するのはagentだけではない。検証結果は対象ソース・設定・環境が一致する範囲だけで使う |

渡す情報は、変更されにくい目的・不変条件・資料の参照と、今回の変更点・対象ソース・未解決点・受入条件に分ける。既存担当には訂正・更新差分を明示し、新規担当には必要な原文や参照先を揃える。数値・例外・禁止事項は省かず、検索履歴や不要なログ全体は渡さない。必要な前提が多すぎるなら、安易な要約で子へ押し込まず、背景を持つ担当に残すか分担境界を見直す。

実行管理役（不在時は主担当）の短い担当メモに、agent ID、モデル・思考、担当・編集範囲、渡した要求と参照先、確認したソース、成果・未解決点を保つ。長い作業では既存の引継ぎ文書にも残す。agentの履歴・記憶が圧縮後も完全に残るとは仮定せず、重要な根拠は文書・コード・証跡から再取得できるようにする。

既存担当の再利用でも、保持履歴の再処理や追記で費用・遅延は増え得る。文脈を維持した利点と不要履歴の負担を比較し、cacheが使われることや追加費用ゼロを保証しない。モデル変更の利益は、既に払った費用ではなく、今から完了までの再入力・再調査・検証・統合を含む総負担で判断する。
