# モデル選択とコンテキスト再利用

利用可能なモデル、思考設定、担当の引継ぎを選ぶ必要があるときに該当節を読む。モデル名・設定値は環境で確認し、毎回のモデル調査や比較実験は行わない。[選択の根拠と評価](選択の根拠と評価.md)は当時の環境・評価条件を示す履歴資料であり、現在のモデル選択の正本ではない。

## 仕事に必要な能力から選ぶ

まず主担当の短い直接処理で済むかを判断し、独立して完了できる単位と委任の利益がある場合だけ別担当を使う。選定では次を照合する。

| 判断材料 | 確認すること |
|---|---|
| 仕事 | 範囲、判断の難しさ、失敗時の影響、完了条件 |
| モデル | 必要な推論・コーディング能力、文脈量、速度・費用 |
| 実行環境 | ファイル編集、テスト、ブラウザー、端末、担当間連絡など実際に使えるツールと権限 |
| 引継ぎ | 説明・再読・検証・統合を含めた完了までの総負担 |

特定のモデル名や価格帯を必須にしない。機能・設定が利用できると仮定せず、現在の実行環境で確認する。モデル間で思考設定の名前や強さを換算しない。

### 得意な工程に合わせて渡す

実行管理役は未確定の要求判断と、調査・実装・検証などの実作業を分けて担当を選ぶ。広い範囲の整理、依存追跡、進行・証跡管理には、十分な文脈と調整能力があり、より低コストで使える担当を優先候補とする。複数契約の根本原因、要求の採否、重大な品質トレードオフは必要な推論力を持つ担当へ残す。管理役が全コードを先に読む必要はなく、担当が必要な範囲を判断できる根拠・探索境界・受入条件を渡す。

| 渡す仕事 | 揃える入力と担当の境界 |
|---|---|
| 定型確認・抽出 | 問い、対象パス・検索語・既存手順、条件、返す形式。原因の確定が必要になったら根拠と未解決を返す |
| 局所実装・限定調査 | 期待動作と根拠、対象ファイル/シンボルと関連契約、再現/ログ、決定済み・未確定事項、編集範囲、関連テスト、完了条件。答える問いと探索境界を明示する |
| 複数契約の原因調査・横断実装 | 観測した障害、期待との差、候補仮説と未確認、状態/タイミング、再現条件・証跡、試行上限、採否に必要な結果。原因不明も明示し、切分け自体を成果にする |

担当は最初の読み取りで不足入力・範囲外の判断を見つけたら、その不足と必要な判断を短く返す。管理役は入力の補足、狭い実験、より適切な能力・ツールを持つ担当への移管から選ぶ。限定範囲で十分な場合は、その担当が実装・テストまで一貫して閉じる。詳細な逐行指示より、検証できる契約と必要なソース参照を優先する。

## 実行構成別の選び方

CodexとClaudeのどちらを使う場合も、次の表から仕事に合う候補を選ぶ。モデル名は両方の選択肢として維持し、括弧内のCodexモデルIDはこのスキル作成時に確認できた表記である。FableのID、Claudeモデルの提供名・版は固定せず、実行環境で利用可否・価格・機能を確認する。

| 作業・役割 | Codex | Claude |
|---|---|---|
| 広い範囲の把握・依存整理・進行管理 | Fable (利用可能な場合)、Astra (`gpt-6-astra`)。Sol中心の構成では、文脈と調整能力を満たす低コスト担当へ既定で割り当てる | Sonnet。複数領域の整理・作業者調整を持ち、局所作業を切り分ける |
| 定型抽出・ログ分類・既知の検証実行 | Luna (`gpt-6-luna`)。指定条件・検証入口を正確に扱える場合に選ぶ | Haiku。対象と返答形式が明確な抽出・分類を中心にする |
| 局所実装・限定調査・画面/文書作業 | Terra (`gpt-6.1-terra`)、Sol (`gpt-6.1-sol`)。範囲と必要な編集・実行能力に合わせる | Sonnet。要件と対象が明確な実装・調査を担当する |
| 複数契約の原因調査・複雑な技術実装 | Sol (`gpt-6.1-sol`)。競合・相反証拠・境界条件に必要な能力が不足する場合は、利用可能な上位候補へ切り替える | Opus。Sonnetで受入条件を満たす見込みが低い難しい原因調査・実装に絞る |
| 要求の採否・品質/費用のトレードオフ・最終受入 | 主担当が判断と責任を保持する。Sol中心で始め、必要な能力・費用に応じてAstra等も候補にする。最上位モデルを必須にしない | 主担当が判断と責任を保持する。通常はSonnet、要求の採否や難しい対立にOpusを選ぶ |

モデル名はタスクに対する選択候補であり、能力・品質・価格の保証やモデル間の同等性を示さない。選択前に利用可能な版、ツール権限、文脈量、費用条件を確認する。品質不足や能力差が観測された場合は候補を切り替える。モデル選択や委任機能が使えない場合は、現在の担当が作業範囲を保ち、必要な検証まで直接処理する。

CodexでSolを実装・難しい判断の中心に置く場合、広い文脈整理・依存の把握・作業進行は、利用可能で必要な文脈とツールを扱えるFable/Astra等の低コスト担当へ既定で割り当てる。作業単位・優先順位・受入条件をその担当に明示し、最終受入と要求の採否は主担当が保持する。適した担当が利用できない場合、または追加の調整コストが利益を上回る場合は直接処理か別構成を選ぶ。

ClaudeでSonnetを中心にする場合は、広い範囲の整理・進行をSonnetに持たせ、局所タスクをHaiku等へ渡し、難しい要求判断・根本原因・品質対立にOpusを使う。Sonnetで完了できるか不確かな大きな課題は、小さく検証可能な単位へ分けて受入条件を保つ。タスクを分割しても独立性・編集所有・テスト条件が崩れる場合は分割しない。

モデル固有のeffort/thinking設定は、そのモデル・仕事で品質改善が見込める場合に限り、実環境で利用可能な値から選ぶ。抽象的な「低/中/高」を別モデルへそのまま移さない。思考設定の強さは解くべき判断の難しさを根拠にし、テスト待ち時間は実行管理で扱う。

失敗したら、まず入力不足、再現条件、環境・権限、検証方法を切り分ける。モデル能力の問題が示された場合は、同じ受入条件を維持してモデル・設定・分担を見直す。進展を確認できる試行を選び、進展がなければ証拠と選択肢を主担当へ戻す。難しい課題を解ける担当も、次の定型作業では必要な品質を満たす最小コストの構成を改めて選ぶ。

## 渡したコンテキストと再利用性で分担を決める

起動・追加依頼前に、既知の担当が持つ目的・モデル・思考・管理役・実行中の仕事・対象worktree/branch・既読資料・確認済みソース・成果を確認する。再利用候補は同じ課題または直接つながる継続作業で、保持する背景が今回に直接役立ち、現行要求・対象ソース・編集所有と整合する担当に限る。空き枠や既存のagent IDだけで選ぶ代わりに、この継続性を根拠に選ぶ。必要ならagent一覧や結果を見る。初回から関連する検索、原因調査、修正、検証を受入条件の閉じるまとまりとして分け、同じ背景を何度も渡さずに済むようにする。ただしAppとpackage等の工程分離や編集所有は守る。

| 状況 | 再利用・移管の判断 |
|---|---|
| 同じ領域・要求・ソースの続き | 既存担当のモデル・思考が十分なら、その担当へ差分だけを渡して再利用する。関連する検索と追従修正を同じ担当にまとめる |
| 既存担当が高価だが背景を把握済み | 新しい安価な担当へ渡す準備・原文読込・調査再現・統合と比べる。短い追加確認なら既存担当で終える方が有利な場合があり、移管は入力の再構築と検証・統合を含む総負担で選ぶ |
| 別モデル・設定が適切になった | 継続中の担当を変更できるか、利用環境の機能で確認する。変更できない場合は、検証済みの背景・成果と残件を引き継げる新しい担当への移管と、現在の担当で続ける場合の総負担を比較する |
| 目的・対象が異なり、保持する背景が直接役立たない仕事 | 主担当が直接処理するか、必要な現行コンテキストだけを渡す新規担当を選ぶ。再利用する価値がある成果は出典付きで共有し、agentの無関係な履歴と切り分ける |
| 関連する継続作業だが、古い判断・肥大化した履歴がある | 現行要求・ソースに照合し、訂正と置換対象を明示して受領・理解を確認する。不要履歴の再処理・誤適用を含む総負担が大きければ、新規担当へ必要な成果と残件だけを渡す |
| 他の管理役が所有する担当、実行中の別契約がある担当 | 依頼は所有する管理役へ集約する。独立作業は別担当か主担当の直接処理へ分け、継続作業の移管は[担当契約と連絡](実行管理と指示更新.md#担当契約と連絡)の引渡しを完了してから行う |
| 他担当が使える成果がある | 調査結果、再現条件、仕様、fixture、検証ログ・手順を参照可能な形で共有する。再利用するのはagentだけではない。検証結果は対象ソース・設定・環境が一致する範囲だけで使う |

渡す情報は、変更されにくい目的・不変条件・資料の参照と、今回の変更点・対象ソース・未解決点・受入条件に分ける。既存担当には訂正・更新差分を明示し、新規担当には必要な原文や参照先を揃える。数値・例外・禁止事項を保持し、検索履歴とログは必要な箇所を参照として渡す。必要な前提が多すぎるなら、必要な背景を正確に保持できるよう、背景を持つ担当に残すか分担境界を見直す。

担当情報は[担当契約と連絡](実行管理と指示更新.md#担当契約と連絡)の一つの担当メモを更新する。重要な根拠は文書・コード・証跡から再取得できる形にし、圧縮前の保存は[引継ぎ](品質・レビュー・引継ぎ.md#必要なコンテキストで品質を保つ)へ揃える。

既存担当の再利用でも、保持履歴の再処理や追記で費用・遅延は増え得る。文脈を維持した利点と不要履歴の負担を比較し、cacheが使われることや追加費用ゼロを保証しない。モデル変更の利益は、今から完了までの再入力・再調査・検証・統合を含む総負担で判断する。
