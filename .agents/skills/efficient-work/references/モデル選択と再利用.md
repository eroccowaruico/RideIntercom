# モデル選択とコンテキスト再利用

モデルの初期候補・思考を選ぶ担当が必要な節を読む。初回・モデル更新・対応値の不一致時だけ[選択の根拠と評価](選択の根拠と評価.md)も確認する。毎回のモデル調査・比較実験は不要。

## 仕事とモデル・思考の組み合わせ

まず主担当の短い直接処理で済むかを判断し、委任の利益がある場合にだけLuna・Terra・Solを選ぶ。委任は仕事の境界・入力・統合を含む利益から判断する。

モデルと仕事の初期対応は[入口の表](../SKILL.md#最初の判断)を正本とする。以下はモデル内の思考選択と移管・再利用の判断だけを補う。

### 得意な工程に合わせて渡す

委任する管理役自身が、未確定の判断と局所的な実行を分けてモデルを選ぶ。Solが管理役でも、難しい原因調査をTerraへそのまま下ろす代わりに、自分で仮説と変更境界を絞るか、調査を閉じられるSolへ実作業として任せる。管理役が全コードを先に読む必要はなく、担当が必要な範囲を判断できるだけの根拠と探索境界を揃える。

| 渡す仕事 | 揃える入力と担当の境界 |
|---|---|
| Lunaへの抽出・既知実行 | 問い、対象パス/検索語・既存手順、条件、返す形式。構造全体の理解や原因の確定が必要になったら根拠と未解決を返す |
| Terraへの局所実装・限定調査 | 期待動作と根拠、対象ファイル/シンボルと関係する呼出元・契約、既知の再現/ログ、決定済み事項と未確定事項、編集範囲、関連テストと完了条件を渡す。限定調査なら答える問いと探索の境界を明示する |
| Solへの原因調査・横断実装 | 観測した障害、期待との違い、候補仮説と未確認、関連する契約・状態/タイミング、再現条件・証跡、調査/試行上限と採否に必要な結果を渡す。原因不明も明示した上で、原因の切分け自体を成果にする |

担当は最初の読み取りで不足入力・範囲外の判断を見つけたら、その不足と必要な判断を短く返す。管理役は入力の補足・狭い実験・適切なモデルへの移管から選ぶ。Terraが際限なくリポジトリ全体を読み直す状態は、担当の努力を追加する代わりに契約とモデルの適合を見直す。限定範囲で十分な場合は、その担当が実装・テストまで一貫して閉じる。詳細な逐行指示より、検証できる契約と必要なソース参照を優先する。

### 思考レベルはモデル内の相対指定として扱う

モデル選択と思考設定は区別しつつ、最終的には「モデル×思考×渡すコンテキスト」で選ぶ。同じlow / medium / highでも、モデルをまたいだ能力・思考トークン量・費用・速度の共通尺度ではない。Luna / highとSol / medium、Astra / lowなどの優劣と費用は同じ受入条件の実績で比較する。モデル・版・クライアントで対応値や挙動も異なる。

下表はこのプロジェクトの運用上の初期基準であり、公式が定める能力境界ではない。同じ要求・入力・受入条件で、成功までの時間・費用・手戻りから調整する。

| モデル | lowを候補にする作業 | mediumを候補にする作業 | high以上を検討する条件 |
|---|---|---|---|
| Luna | 対象と答え方が明確な抽出・検索・定型操作 | 与えた背景内で完結する複数手順、条件の揃った小さな修正 | 範囲は狭いが確認すべき条件や推論が多い場合。Sol等への移管で必要な再入力・再調査も含めて比較し、必要な入力は確認・取得してから判断させる |
| Terra | 提供資料・画面からの抽出や整形、手順が確定した局所操作 | 画面・文章・局所コードの修正と結果確認 | 対象領域内で解くべき曖昧さや境界条件が残る場合。ドメインや契約を横断する判断が増えればSolまたは主担当への移管も比較する |
| Sol | 既に仕様・原因・変更範囲が確定した技術作業、既存担当の短い追従修正 | 調査・実装・検証を伴う通常の技術作業 | 要求の厳密性、複数契約・非同期競合、相反証拠・境界条件、過去の同種失敗からhigh以上が必要と判断できる場合は初めから選ぶ |
| Astra | 十分な背景と確定した方針を使う判断・整形・実行。確定した判断・実行も扱う | 要求解釈、全体設計、複数担当の統合・品質判断 | 未解決の根本原因や厳密な品質・設計上の対立があり、主担当で深く判断する必要がある場合 |

Solでhigh以上が必要な仕事は上表の根拠から初めに選ぶ。初期候補を試して失敗する工程を挟む必要はなく、品質を満たすモデル・思考・入力の組み合わせを完了までの総負担で比較する。

xhigh / max / ultraは、そのモデル・仕事で品質改善が見込めるときに使う。クライアント固有のモードとAPIの思考設定はそれぞれの仕様で扱う。思考の強さは解くべき判断の難しさを根拠に選び、テスト待ち時間は実行管理で扱う。

失敗したら、まず入力不足、再現条件、環境・権限、検証方法を切り分ける。モデル能力の問題が示された場合に、同じ受入条件を維持して思考またはモデルを上げる。調査の広さと必要な判断に合うモデル・思考・分担を選ぶ。進展を確認できる試行を選び、進展がなければ証拠と選択肢を主担当へ戻す。上位モデルで解けた作業も、次の定型作業では改めて適切なモデル・思考を選ぶ。

## 渡したコンテキストと再利用性で分担を決める

起動・追加依頼前に、既知の担当が持つ目的・モデル・思考・管理役・実行中の仕事・対象worktree/branch・既読資料・確認済みソース・成果を確認する。再利用候補は同じ課題または直接つながる継続作業で、保持する背景が今回に直接役立ち、現行要求・対象ソース・編集所有と整合する担当に限る。空き枠や既存のagent IDだけで選ぶ代わりに、この継続性を根拠に選ぶ。必要ならagent一覧や結果を見る。初回から関連する検索、原因調査、修正、検証を受入条件の閉じるまとまりとして分け、同じ背景を何度も渡さずに済むようにする。ただしAppとpackage等の工程分離や編集所有は守る。

| 状況 | 再利用・移管の判断 |
|---|---|
| 同じ領域・要求・ソースの続き | 既存担当のモデル・思考が十分なら、その担当へ差分だけを渡して再利用する。関連する検索と追従修正を同じ担当にまとめる |
| 既存担当が高価だが背景を把握済み | 新しい安価な担当へ渡す準備・原文読込・調査再現・統合と比べる。短い追加確認なら既存Sol等で終える方が有利な場合があり、移管は入力の再構築と検証・統合を含む総負担で選ぶ |
| 別モデル・思考が適切になった | その実行環境で変更できるか確認する。この環境のfollowup_taskは既存担当のモデル・思考を変更する引数を持たないため、変更は対応する起動手段で実施し、実際のモデルと思考を確認する。新規担当が必要なら検証済みの背景・成果と残件を引き継ぎ、確定した探索結果を再利用する |
| 目的・対象が異なり、保持する背景が直接役立たない仕事 | 主担当が直接処理するか、必要な現行コンテキストだけを渡す新規担当を選ぶ。再利用する価値がある成果は出典付きで共有し、agentの無関係な履歴と切り分ける |
| 関連する継続作業だが、古い判断・肥大化した履歴がある | 現行要求・ソースに照合し、訂正と置換対象を明示して受領・理解を確認する。不要履歴の再処理・誤適用を含む総負担が大きければ、新規担当へ必要な成果と残件だけを渡す |
| 他の管理役が所有する担当、実行中の別契約がある担当 | 依頼は所有する管理役へ集約する。独立作業は別担当か主担当の直接処理へ分け、継続作業の移管は[担当契約と連絡](実行管理と指示更新.md#担当契約と連絡)の引渡しを完了してから行う |
| 他担当が使える成果がある | 調査結果、再現条件、仕様、fixture、検証ログ・手順を参照可能な形で共有する。再利用するのはagentだけではない。検証結果は対象ソース・設定・環境が一致する範囲だけで使う |

渡す情報は、変更されにくい目的・不変条件・資料の参照と、今回の変更点・対象ソース・未解決点・受入条件に分ける。既存担当には訂正・更新差分を明示し、新規担当には必要な原文や参照先を揃える。数値・例外・禁止事項を保持し、検索履歴とログは必要な箇所を参照として渡す。必要な前提が多すぎるなら、必要な背景を正確に保持できるよう、背景を持つ担当に残すか分担境界を見直す。

担当情報は[担当契約と連絡](実行管理と指示更新.md#担当契約と連絡)の一つの担当メモを更新する。重要な根拠は文書・コード・証跡から再取得できる形にし、圧縮前の保存は[引継ぎ](品質・レビュー・引継ぎ.md#必要なコンテキストで品質を保つ)へ揃える。

既存担当の再利用でも、保持履歴の再処理や追記で費用・遅延は増え得る。文脈を維持した利点と不要履歴の負担を比較し、cacheが使われることや追加費用ゼロを保証しない。モデル変更の利益は、今から完了までの再入力・再調査・検証・統合を含む総負担で判断する。
