# 品質・レビュー・引継ぎ

作業者は品質条件、レビュー役は選択した役の行と共通の返却・終了条件、実行管理役は統合と引継ぎの節を必要に応じて読む。全員に全文読込を要求しない。

## コンテキストを増やさず、品質を保つ

| 場面 | 行うこと |
|---|---|
| 検索・調査 | `rg`や対象を絞った読み取りを先に使う。独立した検索はまとめ、結果は必要な件数・範囲に制限する。大量の全文やログはファイルへ保存し、該当箇所と根拠だけを会話に返す |
| 実装とテスト | 作業前に受入条件と必要なテストを決める。変更内容に合う回帰・境界・失敗ケースで実際の挙動を確かめる。実装と同じ式だけを再現するテストや、テストを弱める修正で済ませない。必要なproject検証は維持する |
| 統合 | 実行管理役は証跡を集約し、主担当は変更差分、契約と状態所有、重要な失敗経路、検証の対象ソースを確認する。低コストの担当でもこの品質条件を変えない。高リスクなら論点を絞ったSolの独立確認を検討し、全員で同じ全体レビューを繰り返さない |
| 検証の再実行 | 合格した検証はソース・設定・環境と紐づける。新しい変更・失敗・未解決点がなければ同じ重い検証を反復しない。失敗・skip・実行時警告・未実行を隠して成功と扱わない |
| コミット | 対象差分・検証・既存indexを確認し、他作業のstaged変更も混入しないパス限定の方法で主担当が決めた単一実行者が実行する。他作業のindexを無断で変更しない。メッセージ作成だけの子を起動せず、実装内容を毎回一から再調査しない |

長い作業は、責務と受入条件が閉じる単位で調査・実装・検証・コミット・仕様更新を終える。完了した単位は現在の仕様と検証記録を正本にし、過去ログを再読して復元する構造にしない。並行中の担当がいるまま、未確認の成果を完了扱いして圧縮しない。

圧縮に備え、節目ごとに次の再開情報をプロジェクト内の既存の引継ぎ文書、なければ用途の分かる文書へ残す。短い作業に不要な文書は増やさない。恒久仕様・検証結果・一時的な作業状態はリポジトリの文書規約に従って分ける。

| 引き継ぐ情報 | 保持する内容 |
|---|---|
| 要求と判断 | 元の目的、今回の範囲、利用者の訂正・禁止事項、決定と理由、根拠の正本。重要な数値・条件と未解決の対立は原文へ辿れる形で残す |
| 確定した成果 | 完了した責務、commit、対象ファイル、仕様・テスト・証跡のパス、検証したソースと結果。未コミット差分や他作業との所有関係も区別する |
| 残る作業と実行状態 | 次の一手と完了条件、失敗と未確認、稼働中のagent・process・test・Simulatorのhandleと所有者。何を待つか、どう結果取得・回収するかを残す |
| 圧縮後の扱い | 完了した探索の生ログは参照先へ退避し、継続に必要な要求・不変条件・未解決点は失わない。要約とコードが食い違えば該当する原文・実装だけを確認し、全調査を再開しない |

圧縮の回数ゼロや圧縮範囲の強制制御を保証しない。圧縮前に完了・文書化できる分担と、途中でも正確に再開できる状態を作り、Astraにノイズを蓄積することと要約しすぎることの両方を減らす。

完了時は、担当モデルと思考、直接処理と委任の理由、品質検証、手戻りと残件を簡潔に報告する。利用量や所要時間が取得できる場合は成功した作業単位で比較し、取得できない金額や削減率を作らない。同種作業の失敗・復元漏れが出たら、その境界のモデル・思考・渡す情報を見直す。

## 必要なレビューだけを選ぶ

管理役は変更のリスクと受入条件から必要な視点を選び、起動理由と対象を担当メモへ残す。短い低影響の変更は主担当の差分確認で閉じることもできる。一人が複数視点を順次扱ってよいが、自分の実装を独立レビュー済みとは呼ばない。独立性が重要な判断は実装者と別担当へ渡す。全役を常時起動せず、同じ全体レビューを反復しない。

以下は役割設定として、選んだ行に担当契約の目的・ソース・編集可否・受入条件・管理役IDを加えて渡す。モデル・思考は初期候補であり、既存担当の知識と総負担も比較する。

| 役割と選択条件 | モデル・思考の候補 | 読ませる範囲と実行する依頼 | 返す証拠 |
|---|---|---|---|
| 敵対的レビュー。認証・保存・状態遷移・競合・回復など、成功経路だけでは壊れ方を見落とす変更 | Sol / high。厳しい設計対立は主担当Astraへ戻す | 原要求の不変条件、対象差分、関係する呼出元・失敗テスト。受入を破る最小反例、取消・再入・順序逆転等を探す。実装者の想定結論を先に渡さない | 破れる条件、再現手順または具体的経路、期待と実際、該当行。問題を捏造せず、仮説と再現済みを区別し、見つからなければ探索範囲と限界を返す |
| 利用者レビュー。UI・操作・状態説明・復旧・アクセシビリティが変わる場合 | Terra / medium。要件対立は主担当へ | 対象の利用目的・画面項目/状態遷移、当該UIまたは画像、操作シナリオ。初回利用、失敗から復帰、入力方法・文字サイズ・VoiceOver等の対象条件で操作の意味と説明を確かめる | どの利用者条件・操作で何が理解/実行できないか、画面・手順・根拠。代理レビューと明記し、実際の利用者試用・実機操作・VoiceOverでの確認を行った証拠とは区別する |
| 保守レビュー。責務・抽象境界・API・共通化・複数ファイルが変わる場合 | Sol / medium、難しい境界対立はhigh | 対象差分と関係する契約・所有、既存抽象、仕様・検証入口。重複、不要な型や分岐、App/package工程混在、将来の修正箇所の増加を確認 | 行と契約に結びつく保守上の問題、具体的な変更時に起きる負担、既存構造で直す案。好みだけの抽象化や将来用の追加構造を要求しない |
| コアドメインレビュー。音声・codec・mixer・VAD・RTC・経路/再接続・送信抑制が変わる場合 | Sol / high。未解決の品質トレードオフは主担当Astra / high候補 | 対象の音声/通信仕様と製品要求の適用条件、差分、タイミング・状態所有・失敗経路、必要な音声E2E等の証跡。遅延、鮮度、連続性、取消、音声同一性、通信/電池負担、認証と保護の該当論点を確認 | 数値・単位・条件付きの証跡、対象ソース・環境、失敗や未計測。通常端末とWatch等の異なる条件を混同しない。Simulator/Mac結果で実機無線・Bluetooth・電池/熱・音響・実Cloudflareを証明しない |
| 検証レビュー。回帰保護・測定方法・skip/失敗・証跡の対応が受入を左右する場合 | 定型の実行/照合はLuna / low、局所的な検証設計はTerra / medium、非同期・測定妥当性はSol / medium～high | 受入条件、差分、関連テストと実行手順、ログ該当箇所。実装と同じ式だけを写すテスト、測定範囲漏れ、旧ソースの成功の流用を確かめる | 実行した対象と条件、結果・保存先、受入条件をどこまで確かめたか、失敗・skip・警告・未実行、必要最小限の追加確認案 |

## 指摘の処理と終了

レビュー役は最初は読み取りのみとし、必要な再現は担当契約の許可範囲・共有資源所有内で行う。主張の根拠は原文・実装・観測で示し、実装者の説明をそのまま証明にしない。必要な資料は追加要求できるが、全資料や全探索履歴を既定入力にしない。

返却の共通形式は「役割と対象ソース・条件、結論、指摘ごとの重要度/影響・根拠のパス/行・再現条件・修正または追加確認案、未確認と限界」。指摘ゼロも範囲を示して返す。確度の低い懸念を確定障害として数えない。

管理役は指摘を再現・根拠確認し、採用、既存条件で解決済み、根拠不足、主担当判断待ちに整理する。作業者へ修正対象と受入条件を渡し、担当所有内で直した差分と関連する回帰・境界・失敗検証を返させる。レビュー役は指摘が最終差分で閉じたかと変更により新たに生じた論点だけを再確認する。テスト緩和や要求削除で指摘を閉じない。

対象ソースに紐づく必要な検証が成功し、採用指摘が解決し、未解決の影響と実機等の未確認が主担当の判断パッケージに明記されたらレビューを終える。未解決を管理役だけで受容しない。新しい変更・失敗・未解決がなければレビューや重い検証を反復しない。根拠が対立するか同じ試行で進展しなければ管理役が整理して主担当へ戻し、無制限に交互レビューしない。
