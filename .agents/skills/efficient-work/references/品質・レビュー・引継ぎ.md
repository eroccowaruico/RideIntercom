# 品質・レビュー・引継ぎ

作業者は品質条件、レビュー役は選択した役の行と共通の返却・終了条件、実行管理役は統合と引継ぎの節を必要に応じて読む。各担当は役割に必要な節を読む。

機能・技術経路の完了と利用者への引渡しは[core-story-firstの実行と完了判定](../../core-story-first/SKILL.md)に従い、固定scope全経路の必要なE2E結果と最終ソースの対応を確認する。部品検証やexit 0の到達点を区別し、必要E2Eの実行と修正を担当側で閉じる。

## 必要なコンテキストで品質を保つ

| 場面 | 行うこと |
|---|---|
| 検索・調査 | `rg`や対象を絞った読み取りを先に使う。独立した検索はまとめ、結果は必要な件数・範囲に制限する。原文と必要なログは適切な証跡保存先で保持し、会話には該当箇所と根拠を返す |
| 実装とテスト | [回帰保護](../../../../docs/policies/開発方針.md#実装と検証)と[GUI実行](../../../../docs/policies/開発方針.md#開発環境の要求)を担当契約へ含める。テストは外部から観測できる要求・契約と受入基準で判定する |
| 統合 | 実行管理役は証跡を集約し、主担当は変更差分、契約と状態所有、重要な失敗経路、検証の対象ソースを確認する。担当モデルによらず同じ品質条件を適用する。高リスクなら論点を絞ったSolの独立確認を検討し、各レビューは役割と未解決の論点へ絞る |
| 検証の再実行 | 合格した検証はソース・設定・環境と紐づける。新しい変更・失敗・未解決点がある範囲を再検証し、それ以外は根拠付きの既存証跡を参照する。失敗・skip・実行時警告・未実行を明示し、受入条件を満たした範囲を成功として扱う |
| コミット | 対象差分・検証・既存indexを確認し、自分の変更だけを含むパス限定の方法で主担当が決めた単一実行者が実行する。他作業のindexの無断変更は禁止する。メッセージ作成は既存担当が行い、実装内容は確定した差分と証跡から取得する |

長い作業は、責務と受入条件が閉じる小さな単位で調査・実装・検証・コミット・仕様更新を終える。worktree利用時は[実行管理と指示更新](実行管理と指示更新.md)のmerge管理に従い、主担当の許可と対象ソースに対応する検証を揃えてmainへ段階的に統合する。完了した単位は現在の仕様と検証記録を正本にし、再開には現行の正本と再開情報を使う。並行担当の未確認成果は進行中として、証跡と生存handleを再開情報へ含める。

圧縮に備え、節目ごとに次の再開情報を既存の引継ぎ・仕様・検証・残課題の適切な節へ残す。新設には正本の配置規約と増設禁止を適用し、短い作業の記録は既存の適切な節へまとめる。恒久仕様・検証結果・一時的な作業状態はリポジトリの文書規約に従って分ける。

| 引き継ぐ情報 | 保持する内容 |
|---|---|
| 要求と判断 | 元の目的、今回の範囲、利用者の訂正・禁止事項、決定と理由、根拠の正本。重要な数値・条件と未解決の対立は原文へ辿れる形で残す |
| 確定した成果 | 完了した責務、commit、対象ファイル、仕様・テスト・証跡のパス、検証したソースと結果。未コミット差分や他作業との所有関係も区別する。worktree/branch・基準main・対象commit・主担当のmerge許可/保留と再開条件・統合済commitも参照可能に保つ |
| 残る作業と実行状態 | 次の一手と完了条件、失敗と未確認、稼働中のagent・process・test・Simulatorのhandleと所有者。何を待つか、どう結果取得・回収するかを残す |
| 圧縮後の扱い | 完了した探索の生ログは参照先へ退避し、継続に必要な要求・不変条件・未解決点を保持する。要約とコードが食い違えば該当する原文・実装だけを確認し、食い違う判断に必要な範囲を再調査する |

圧縮の回数ゼロや圧縮範囲の強制制御を保証しない。圧縮前に完了・文書化できる分担と、途中でも正確に再開できる状態を作り、Astraにノイズを蓄積することと要約しすぎることの両方を減らす。

完了時は、担当モデルと思考、直接処理と委任の理由、品質検証、手戻りと残件を簡潔に報告する。利用量や所要時間が取得できる場合は成功した作業単位で比較し、未取得の金額や削減率は未計測と記録する。同種作業の失敗・復元漏れが出たら、その境界のモデル・思考・渡す情報を見直す。

## 自動テストの実行・解析・修正を閉じる

管理役がある構成では、受入条件・編集範囲・実行資源・費用制約を担当契約へ渡し、通常の実行→失敗分類と再現→許可範囲内の修正→関連再検証を担当側で閉じる。失敗のたびに通常の実行・修正・結果確認を担当側で閉じる。複雑な原因調査も委任でき、主担当は難しい調査の実行そのものを必ず引き取る役ではない。

| 仕事 | モデル・思考の初期候補と依頼 |
|---|---|
| 確定済みの自動テスト実行 | Luna / low。既存の検証入口と指定条件で実行し、対象・終了結果・証跡・process handleを保持 |
| 機械的な分類とログ抽出 | Luna / low～medium。失敗箇所・エラー・警告・skip・timeoutの根拠を該当範囲から抽出し、原因未確定は未確定と返す |
| 限定再現と局所コード・テスト修正 | Terra / medium。要求と期待値が明確な不具合を所有範囲で再現・修正し、関連テストで確認 |
| 複雑な原因調査、非同期競合、音声の測定妥当性 | Sol / medium、必要なら最初からhigh以上。相反証拠・順序依存・時間測定を追い、仮説を区別できる確認と根拠ある修正を行う |

この表は一人の担当が実行・解析・修正を一括して担う際の選択基準である。管理役は既存担当のモデル・思考・保持する背景と、再入力・再現・統合を含む完了までの総負担で一人への一括依頼・再利用・移管を選ぶ。Lunaが未確定の原因に突き当たれば、管理役が根拠と残件を既存Terra/Sol等へ渡せる。利用可能な枠と再委任範囲を守り、作業者は追加分担を管理役へ相談する。管理役不在の短い作業は主担当が直接終える既定を維持する。

| 実行・解析の境界 | 行うこと |
|---|---|
| 開始と資源 | 対象ソースのcommitと未コミット差分、設定、OS/端末・Simulator・toolchain、受入条件、検証入口と実行コマンド、必要な計測条件を揃える。process/test session/Simulatorのhandleと所有者、待機・結果取得・終了/timeout時の回収方法を残す。既存資源を確認し、他作業・所有不明の資源の無断停止・削除は禁止する |
| 証跡 | ログ・xcresult・計測出力の保存先と失敗箇所を対応させる。結論は必要な原文・ログと照合し、終了コード・警告・skip・未実行も記録する。音声は単位、測定の始点/終点、codec・経路等の適用条件を保持し、実機と代替環境の証明範囲を分ける。秘密・音声payloadのログ/返却への出力は禁止する |
| 失敗分類 | 製品実装、テスト/fixture/期待値、環境/資源、権限、実時間条件の不安定さ等を観測で切り分ける。候補と確定原因を分け、原因と条件差を確認してflake・解決を判定する。必要な場合だけ条件を揃えた限定再現や条件差比較を行う |
| 局所修正 | 明確な既知不具合や既存許可内の局所修正は担当側で直す。テスト側も要求・契約・測定方法に反する箇所を根拠付きで修正できる。期待値変更は現行要求から正しいことを示し、閾値緩和・skip・assertion削除・警告隠しを使った成功の偽装は禁止する。App/package工程と編集所有を跨がず、不足する変更は管理役へ戻す |
| 再検証と完了 | 修正箇所の関連テストから必要な回帰・境界・失敗検証へ広げ、projectで必要な検証は維持する。変更後は影響する/影響不明の検証を再実行する。影響しない証拠がある過去結果は元の対象の証跡としてだけ再利用し、[core-story-firstの証跡条件](../../core-story-first/references/優先判断の根拠と実行.md#狭いscopeとe2eの実行・完了判断)と実際の入力指紋検査を守る。重い検証は変更・失敗・未解決の範囲へ絞り、対象外は根拠付きの証跡を再利用する |
| 止めどころ | 原因仮説・入力・観測が変わらず同じ失敗を繰り返す、対象の受入条件に関係しない探索へ広がる、設定した時間/回数/費用の上限へ達する場合はその試行を止める。再現が必要な試行は管理役が目的と上限を先に決め、retryは仮説と上限を定め、実サービスは正本の明示実行条件で扱う。所有する検証process/session等だけを安全に終了・回収し、結果を保持する |

管理役は難しい原因調査をSolへ移すことと、主担当へ判断を求めることを分ける。要求/受入条件の曖昧さ、品質・費用・レイテンシ等のトレードオフ、範囲/権限拡大、根拠対立・改善なし、最終受入が主担当へ戻す条件である。権限不足は既存許可内の安全な代替を確認し、未解消の権限不足は停止条件として記録し、必要な承認・操作を主担当へ返す。実Cloudflare等の検証は正本のローカル成功・明示範囲・費用上限・回収条件と実行権限を満たす場合に限り、失敗解析はローカルの代替環境で先に行う。

判断パッケージは失敗の影響と期待値の正本、対象ソース/設定/環境、確認した仮説と反証・実行結果の参照、修正済みと残件、止めた試行と資源の状態、選択肢・推奨・必要な判断/再開条件に絞る。生ログは参照先を共有する。担当側で解消した通常失敗は成果・検証記録へ残し、主担当の最終受入へは最終差分と最終ソースの検証結果・残る限界を返す。

## 必要なレビューだけを選ぶ

管理役は変更のリスクと受入条件から必要な視点を選び、起動理由と対象を担当メモへ残す。短い低影響の変更は主担当の差分確認で閉じることもできる。一人が複数視点を順次扱ってよいが、自分の実装の確認は自己レビューと明記する。独立性が重要な判断は実装者と別担当へ渡す。必要な役と論点を選び、各レビューの対象を分ける。

以下は役割設定として、選んだ行に担当契約の目的・ソース・編集可否・受入条件・管理役IDを加えて渡す。モデル・思考は初期候補であり、既存担当の知識と総負担も比較する。

| 役割と選択条件 | モデル・思考の候補 | 読ませる範囲と実行する依頼 | 返す証拠 |
|---|---|---|---|
| 敵対的レビュー。認証・保存・状態遷移・競合・回復など、成功経路だけでは壊れ方を見落とす変更 | Sol / high。厳しい設計対立は主担当Astraへ戻す | 原要求の不変条件、対象差分、関係する呼出元・失敗テスト。受入を破る最小反例、取消・再入・順序逆転等を探す。レビュー入力は原要求と生の差分・証跡を渡す | 破れる条件、再現手順または具体的経路、期待と実際、該当行。仮説と再現済みを区別し、結論に観測証拠・探索範囲・限界を添える |
| 利用者レビュー。UI・操作・状態説明・復旧・アクセシビリティが変わる場合 | Terra / medium。要件対立は主担当へ | 対象の利用目的・画面項目/状態遷移、当該UIまたは画像、操作シナリオ。初回利用、失敗から復帰、入力方法・文字サイズ・VoiceOver等の対象条件で操作の意味と説明を確かめる | どの利用者条件・操作で何が理解/実行できないか、画面・手順・根拠。代理レビューと明記し、実際の利用者試用・実機操作・VoiceOverでの確認を行った証拠とは区別する |
| 保守レビュー。責務・抽象境界・API・共通化・複数ファイルが変わる場合 | Sol / medium、難しい境界対立はhigh | 対象差分と関係する契約・所有、既存抽象、仕様・検証入口。重複、不要な型や分岐、App/package工程混在、将来の修正箇所の増加を確認 | 行と契約に結びつく保守上の問題、具体的な変更時に起きる負担、既存構造で直す案。改善提案は現在の契約と具体的な保守負担を根拠にする |
| コアドメインレビュー。音声・codec・mixer・VAD・RTC・経路/再接続・送信抑制が変わる場合 | Sol / high。未解決の品質トレードオフは主担当Astra / high候補 | 対象の音声/通信仕様と製品要求の適用条件、差分、タイミング・状態所有・失敗経路、必要な音声E2E等の証跡。遅延、鮮度、連続性、取消、音声同一性、通信/電池負担、認証と保護の該当論点を確認 | 数値・単位・条件付きの証跡、対象ソース・環境、失敗や未計測。通常端末とWatch等の結果は条件ごとに分ける。実機無線・Bluetooth・電池/熱・音響・実Cloudflareは各実環境の証跡で受け入れる |
| 検証レビュー。回帰保護・測定方法・skip/失敗・証跡の対応が受入を左右する場合 | 定型の実行/照合はLuna / low、局所的な検証設計はTerra / medium、非同期・測定妥当性はSol / medium～high | 受入条件、差分、関連テストと実行手順、ログ該当箇所。実装と同じ式だけを写すテスト、測定範囲漏れ、旧ソースの成功の流用を確かめる | 実行した対象と条件、結果・保存先、受入条件をどこまで確かめたか、失敗・skip・警告・未実行、必要最小限の追加確認案 |

## 指摘の処理と終了

レビュー役は最初は読み取りのみとし、必要な再現は担当契約の許可範囲・共有資源所有内で行う。主張の根拠は原文・実装・観測で示し、実装者の説明は原文・差分・観測と照合して判断する。必要な資料は追加要求できるが、初期入力は判断に必要な資料と範囲へ絞る。

返却の共通形式は「役割と対象ソース・条件、結論、指摘ごとの重要度/影響・根拠のパス/行・再現条件・修正または追加確認案、未確認と限界」。指摘ゼロも範囲を示して返す。懸念と再現済み障害は確度を分けて記録する。

管理役は指摘を再現・根拠確認し、採用、既存条件で解決済み、根拠不足、主担当判断待ちに整理する。作業者へ修正対象と受入条件を渡し、担当所有内で直した差分と関連する回帰・境界・失敗検証を返させる。レビュー役は指摘が最終差分で閉じたかと変更により新たに生じた論点だけを再確認する。指摘は元の要求・受入基準を満たす修正と再検証で閉じる。

対象ソースに紐づく必要な検証が成功し、採用指摘が解決し、未解決の影響と実機等の未確認が主担当の判断パッケージに明記されたらレビューを終える。未解決の受入判断は必要な証拠と選択肢を主担当へ返す。レビューと重い検証は新しい変更・失敗・未解決の範囲を対象にする。根拠が対立するか同じ試行で進展しなければ管理役が整理して主担当へ戻し、次の試行の目的と上限を決める。
