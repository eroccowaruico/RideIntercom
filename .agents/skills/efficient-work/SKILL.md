# モデル・思考・作業分担の選択

## 呼び出しと判断の前提

`$efficient-work 今回の作業を進めて`で適用する。主担当はAstraを前提とし、要求理解・分担・統合・品質判断を持つ。このスキルは主担当のモデル・思考設定や圧縮タイミングを強制変更できない。設定変更の手段がない場合は現在のモデルで続け、Astraへ変更済みとは報告しない。個人設定や他プロジェクトへ設定を広げない。

[AGENTS.md](../../../AGENTS.md)の正本と、今回の対象に必要な仕様を適用する。読了済みで変更されていない文書は繰り返し全文を読まない。下表は初期値であり、公式の能力説明、実行環境が公開する能力・制約、同種作業の実績から調整する。初回・モデル更新・対応値の不一致時は[選択の根拠と評価](references/選択の根拠と評価.md)を確認する。毎回モデル調査や比較実験をやり直さない。

## 仕事とモデル・思考の組み合わせ

まず主担当の短い直接処理で済むかを判断し、委任の利益がある場合にだけLuna・Terra・Solを選ぶ。表の仕事名だけで機械的に子を起動しない。

| 仕事 | 初期の担当・思考 | 選択を変える条件 |
|---|---|---|
| 数回の検索、既知のコマンド実行、コミット、短い修正 | 主担当が直接ツールを使う。思考を変更可能ならlow | 起動・説明・統合の負担を増やさず完了できる場合。主担当が高価でも、短い操作のためだけに子を起動しない |
| 広い検索の絞り込み、出典付き事実抽出、既知ログの分類、決まったテストの実行 | Luna `gpt-6-luna` / low | 判断が必要な狭い作業はmedium。原因が不明な障害や仕様判断まで委ねず、根拠と未解決点を返す |
| 入出力と受入条件が明確な単純コード・テスト、限定した修正、資料からの文書化、画面や画像を確認する作業 | Terra `gpt-6.1-terra` / medium。抽出・整形中心ならlow | 小さく機械的ならLuna / low～medium。複数の契約や不明な挙動にまたがるならSolへ。限定修正も回帰テストと差分確認を伴わせる |
| 複数ファイルを追う調査・実装、設計済みのまとまった変更、原因切り分け | Sol `gpt-6.1-sol` / medium | 非同期・競合・相反する証拠・分かりにくい不具合はhigh。狭い抽出に戻ればLunaへ、局所修正に戻ればTerraへ切り替えを検討する |
| 要求の解釈、全体設計、責務間の判断、統合と最終確認 | 主担当Astra `gpt-6-astra` / medium | 根本原因・安全性・音声やRTCの厳しい品質判断は必要に応じhigh。局所で確定した実行はツールや安価な担当へ渡す |

### 思考レベルはモデル内の相対指定として扱う

モデル選択と思考設定は区別しつつ、最終的には「モデル×思考×渡すコンテキスト」で選ぶ。同じlow / medium / highでも、モデルをまたいだ能力・思考トークン量・費用・速度の共通尺度ではない。Luna / highとSol / medium、Astra / lowなどの優劣や換算比を固定しない。モデル・版・クライアントで対応値や挙動も異なる。

下表はこのプロジェクトの運用上の初期基準であり、公式が定める能力境界ではない。同じ要求・入力・受入条件で、成功までの時間・費用・手戻りから調整する。

| モデル | lowを候補にする作業 | mediumを候補にする作業 | high以上を検討する条件 |
|---|---|---|---|
| Luna | 対象と答え方が明確な抽出・検索・定型操作 | 与えた背景内で完結する複数手順、条件の揃った小さな修正 | 範囲は狭いが確認すべき条件や推論が多い場合。Sol等への移管で必要な再入力・再調査も含めて比較し、不足情報を思考量で埋めさせない |
| Terra | 提供資料・画面からの抽出や整形、手順が確定した局所操作 | 画面・文章・局所コードの修正と結果確認 | 対象領域内で解くべき曖昧さや境界条件が残る場合。ドメインや契約を横断する判断が増えればSolまたは主担当への移管も比較する |
| Sol | 既に仕様・原因・変更範囲が確定した技術作業、既存担当の短い追従修正 | 調査・実装・検証を伴う通常の技術作業 | 非同期競合、相反する証拠、難しい失敗経路など、追加の検討で品質改善が見込める場合 |
| Astra | 十分な背景と確定した方針を使う判断・整形・実行。抽出専用とは考えない | 要求解釈、全体設計、複数担当の統合・品質判断 | 未解決の根本原因や厳密な品質・設計上の対立があり、主担当で深く判断する必要がある場合 |

xhigh / max / ultraは利用可能というだけで選ばず、そのモデル・仕事で品質改善が見込めるときに使う。ultra等のクライアント固有のモードをAPIの思考設定と同一視しない。長時間のテスト待ちや履歴の長さは、それ自体では思考を上げる理由にならない。

失敗したら、まず入力不足、再現条件、環境・権限、検証方法を切り分ける。モデル能力の問題が示された場合に、同じ受入条件を維持して思考またはモデルを上げる。広い調査を低能力モデルへ無理に押し込むことも、狭い検索を高能力・高思考へ渡すことも避ける。同じ進め方で失敗を反復せず、解決の進展がなければ主担当へ戻す。上位モデルで解けた作業も、次の定型作業まで同じ設定を引きずらない。

## 委任するか、直接終えるか

総負担には、主担当と子の入力・思考・出力、履歴の複製、ツール待ち、再試行、統合・再読、圧縮後の復元を含める。単価の低さや並列数だけで決めない。短い作業は直接、独立して完了できるまとまった調査や実装は委任を候補にする。密接な設計判断、同じ共有状態を頻繁に編集する作業、必要な背景を小さく正確に渡せない作業は主担当に残す。

委任に実益がある場合、このスキルは選択したモデル・思考を明示してサブエージェントを使う。全履歴を無条件に複製しない。この環境の`collaboration.spawn_agent`では、別モデル・思考を指定するとき`fork_turns: "none"`を使い、必要な指示・資料・不変条件を明示して渡す。他の環境ではそのツールの実際の仕様に合わせる。指定できないモデルを黙ってAstraの子へ置き換えない。

- 原則は独立した少数の担当から始める。通常は子を同時に二つまでとし、枠を埋めるために増やさない。追加は待ち時間短縮や独立検証の利益があるときだけ、実行環境の上限内で行う。子は再委任せず、追加の分担が必要なら主担当へ戻す。
- 一つの担当に関連する検索・調査をまとめ、検索語ごとに起動しない。同じ背景を使う継続作業は、下記の基準で既存担当と新規担当を比較する。
- 各担当へ目的、対象ファイルと編集の可否、必要な原文・規約・決定、受入条件、実行する検証、終了条件、返す証跡を渡す。要求の否定条件、数値・単位、例外、品質閾値は曖昧に要約しない。
- 書くファイルの所有を分ける。同一ファイル、Appとpackageの異なる工程、共有Simulatorやbuild資源を競合させない。コミットと統合は主担当が一元管理し、他作業の変更を含めない。
- 戻り値は結論、根拠のパス・行・URL、変更箇所、テスト結果とログの保存先、未解決点に絞る。主担当は判断に必要な原文・差分・証跡を確認し、長い探索記録を全部読み直さない。結論や自信だけを根拠に採用しない。

## 渡したコンテキストと再利用性で分担を決める

起動前に、既知の担当が持つ目的・モデル・思考・既読資料・確認済みソース・成果を確認する。必要ならagent一覧や結果を見る。初回から関連する検索、原因調査、修正、検証を受入条件の閉じるまとまりとして分け、同じ背景を何度も渡さずに済むようにする。ただしAppとpackage等の工程分離や編集所有は守る。

| 状況 | 再利用・移管の判断 |
|---|---|
| 同じ領域・要求・ソースの続き | 既存担当のモデル・思考が十分なら、その担当へ差分だけを渡して再利用する。検索語や小さな追従修正ごとに新しい担当を作らない |
| 既存担当が高価だが背景を把握済み | 新しい安価な担当へ渡す準備・原文読込・調査再現・統合と比べる。短い追加確認なら既存Sol等で終える方が有利な場合があり、単価だけでLunaへ移さない |
| 別モデル・思考が適切になった | その実行環境で変更できるか確認する。この環境のfollowup_taskは既存担当のモデル・思考を変更する引数を持たないため、指示だけで変更済みと扱わない。新規担当が必要なら検証済みの背景・成果と残件を引き継ぎ、元の探索を繰り返させない |
| 無関係な仕事、古い判断、肥大化した履歴 | 再利用に固執しない。元担当の必要な成果だけを出典付きで取り出し、現行の要求・ソースを基準に新規担当へ渡す。利用者の訂正と矛盾する過去の前提は明示して更新する |
| 他担当が使える成果がある | 調査結果、再現条件、仕様、fixture、検証ログ・手順を参照可能な形で共有する。再利用するのはagentだけではない。検証結果は対象ソース・設定・環境が一致する範囲だけで使う |

渡す情報は、変更されにくい目的・不変条件・資料の参照と、今回の変更点・対象ソース・未解決点・受入条件に分ける。既存担当には訂正・更新差分を明示し、新規担当には必要な原文や参照先を揃える。数値・例外・禁止事項は省かず、検索履歴や不要なログ全体は渡さない。必要な前提が多すぎるなら、安易な要約で子へ押し込まず、背景を持つ担当に残すか分担境界を見直す。

主担当の短い担当メモに、agent ID、モデル・思考、担当・編集範囲、渡した要求と参照先、確認したソース、成果・未解決点を保つ。長い作業では既存の引継ぎ文書にも残す。agentの履歴・記憶が圧縮後も完全に残るとは仮定せず、重要な根拠は文書・コード・証跡から再取得できるようにする。

既存担当の再利用でも、保持履歴の再処理や追記で費用・遅延は増え得る。文脈を維持した利点と不要履歴の負担を比較し、cacheが使われることや追加費用ゼロを保証しない。モデル変更の利益は、既に払った費用ではなく、今から完了までの再入力・再調査・検証・統合を含む総負担で判断する。

## コンテキストを増やさず、品質を保つ

| 場面 | 行うこと |
|---|---|
| 検索・調査 | `rg`や対象を絞った読み取りを先に使う。独立した検索はまとめ、結果は必要な件数・範囲に制限する。大量の全文やログはファイルへ保存し、該当箇所と根拠だけを会話に返す |
| 実装とテスト | 作業前に受入条件と必要なテストを決める。変更内容に合う回帰・境界・失敗ケースで実際の挙動を確かめる。実装と同じ式だけを再現するテストや、テストを弱める修正で済ませない。必要なproject検証は維持する |
| 統合 | 主担当は変更差分、契約と状態所有、重要な失敗経路、検証の対象ソースを確認する。低コストの担当でもこの品質条件を変えない。高リスクなら論点を絞ったSolの独立確認を検討し、全員で同じ全体レビューを繰り返さない |
| 検証の再実行 | 合格した検証はソース・設定・環境と紐づける。新しい変更・失敗・未解決点がなければ同じ重い検証を反復しない。失敗・skip・実行時警告・未実行を隠して成功と扱わない |
| コミット | 対象差分・検証・既存indexを確認し、他作業のstaged変更も混入しないパス限定の方法で主担当が実行する。他作業のindexを無断で変更しない。メッセージ作成だけの子を起動せず、実装内容を毎回一から再調査しない |

長い作業は、責務と受入条件が閉じる単位で調査・実装・検証・コミット・仕様更新を終える。完了した単位は現在の仕様と検証記録を正本にし、過去ログを再読して復元する構造にしない。並行中の担当がいるまま、未確認の成果を完了扱いして圧縮しない。

圧縮に備え、節目ごとに次の再開情報をプロジェクト内の既存の引継ぎ文書、なければ用途の分かる文書へ残す。短い作業に不要な文書は増やさない。恒久仕様・検証結果・一時的な作業状態はリポジトリの文書規約に従って分ける。

| 引き継ぐ情報 | 保持する内容 |
|---|---|
| 要求と判断 | 元の目的、今回の範囲、利用者の訂正・禁止事項、決定と理由、根拠の正本。重要な数値・条件と未解決の対立は原文へ辿れる形で残す |
| 確定した成果 | 完了した責務、commit、対象ファイル、仕様・テスト・証跡のパス、検証したソースと結果。未コミット差分や他作業との所有関係も区別する |
| 残る作業と実行状態 | 次の一手と完了条件、失敗と未確認、稼働中のagent・process・test・Simulatorのhandleと所有者。何を待つか、どう結果取得・回収するかを残す |
| 圧縮後の扱い | 完了した探索の生ログは参照先へ退避し、継続に必要な要求・不変条件・未解決点は失わない。要約とコードが食い違えば該当する原文・実装だけを確認し、全調査を再開しない |

圧縮の回数ゼロや圧縮範囲の強制制御を保証しない。圧縮前に完了・文書化できる分担と、途中でも正確に再開できる状態を作り、Astraにノイズを蓄積することと要約しすぎることの両方を減らす。

完了時は、担当モデルと思考、直接処理と委任の理由、品質検証、手戻りと残件を簡潔に報告する。利用量や所要時間が取得できる場合は成功した作業単位で比較し、取得できない金額や削減率を作らない。同種作業の失敗・復元漏れが出たら、その境界のモデル・思考・渡す情報を見直す。
