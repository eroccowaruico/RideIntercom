# 優先判断の根拠と実行

優先選択・成立性の実験・継続記録の必要節だけを読む。作業と参照を分けても目的・判断基準と関連機能の整合は共有し、検索履歴や全ログの複製は不要。モデル/役割や検証運用の詳細は[efficient-work](../../efficient-work/SKILL.md)へ委ねる。

## 狭いscopeとE2Eの実行・完了判断

最新訂正は、狭い一つのコアを固定し、実App/実経路の縦実装→利用可能環境でのE2E実行→失敗修正→証拠照合まで確実に閉じることを優先する。以下の利用者原文は方針と指摘の記録であり、このスキル改訂で実際のE2Eを実行した証拠ではない。

> E2Eもやっていないのに、ユーザーに試せとか、できたとかいうのはダメでしょ。そういうことがないように、技術検証だろうと机上でできるのであればシミュレーターなど全てを使って試してよ。そういうことを何もせず、シミュレーター使えました。結合テスト終わりました。なんて言われてもかなり困ります。そういうことが起こらない。シンプルでかなり絞ったスコープを確実にコアから終わらせるスキルにして。今はスコープも指示しないと広がるし、幹の前に枝葉が作られているし、マジで最悪。

| 固定・実行・判断 | 必要な内容 |
|---|---|
| scopeの固定 | 要求者の目的・今回の問い・証拠で決めることから必要な最小実経路を選び、一つの最小storyとして、今回の対象・作らない枝葉・E2E操作と観測先・完了条件を着手前に固定する。未指定なら親が現行ゴールの最重要コアから小さく選び明示。後の追加はstory阻害/重大回帰/後続改善へ分類し、必須だけ根拠と影響を親が示してscope更新する |
| 実行する経路 | 実操作→実Appの制御/処理→必要な通信と相手側→最終出力/副作用→終了/再開/回復の該当全経路を実際に通す。技術検証や試作も、判断したい経路の動く縦実装を使い、「机上でできる」を文章のレビューへ置換しない |
| 利用可能な手段 | 問いに必要なSimulator・Mac・複数process/端末・ローカルserver/代替provider・UI操作・native音声I/O等を組み合わせる。全機能/全環境の総当りにはしないが、狭いstoryの重要境界を削って費用を節約しない。実行前に必要な経路と環境の対応を示し、後から都合のよい合格例だけを選ばない |
| UIと音声 | 技術検証ではUIなしの実行入口や簡易UIから実経路のE2Eを先に成立させ、検証に不要な製品UIを先行させない。要求者がUI操作自体の成立を求めるstoryは実際のUI入口から通し、VM直呼出しだけで完了にしない。音声は送信関数の成功で止めず、相手native出力/render波形、該当する双方向・遅延・連続性・停止/再開を観測。UI省略のnative音声E2Eはその音声経路の根拠にはなるが、UIを含むstory全体の根拠へ拡大しない |
| 本番と代替の境界 | どの本番処理をmock/fixtureで置換し、どのApp/通信/native処理を実行したか明記する。必要な本番処理を置換した部分までE2E済みとしない。既存入口が該当storyを通さなければ、必要最小限のE2Eシナリオを追加して実行。App/package工程分離とTDD・回帰品質は維持する |
| 証跡の照合 | 最終sourceのcommit/未commit差分・設定と実行コマンド、実行日時/環境、操作順・期待/実際、両端と最終出力、xcresult/ログ/波形等の参照を対応させる。件数0・skip・失敗・timeout・実行時警告・crashと結果解析の可否を確認し、exit 0・テスト存在・起動・SDK/build・単体/結合成功・送信受付だけで完了としない |
| 失敗と再実行 | 担当側で原因を切り分け、許可範囲で修正し、最終source/設定/依存と検証対象の対応を確認し、影響する/影響不明の関連E2Eを再実行する。対象・依存・条件が変わらず影響しない根拠がある既存結果は、元の対象の証跡として再利用できる。過去のhashや実行事実を書き換えず、未実行E2Eを推測で通さず、閾値緩和/skip/fakeで通さない。実行可能なE2Eの未実行/失敗を残して枝葉や別storyへ移らない。原因対立・権限/範囲・進展なし等の判断はefficient-workどおり親へ戻す |
| 縮小と停止 | scopeを小さくする場合も目的を失う縮小やfakeで成功へ変えない。親が変更と理由・影響を管理し、元storyの残件を明記。上限や権限で止める場合も成功ではなく、止めた経路・再開条件・所有資源の回収状態を残す |

run中またはその入口がsource-stability/manifestで安定を要求する期間のsource変更は、実際の検査の失敗判定に従う。影響なしという推定で失敗を成功へ変えず、manifestや安定性検査を弱めない。上の再利用は正常に完了した元の対象・依存・条件が維持される範囲だけで、元runの対象を新sourceへ書き換えることではない。

コマンド・成功解析・証跡と資源所有は[自動検証](../../../../docs/development/自動検証.md)の「入口」「環境と出力」「成功判定と異常終了」、音声の経路・計測・代替境界は[音声E2Eテスト](../../../../docs/development/音声E2Eテスト.md)の「通る経路と判定」「証跡」「サーバーモックの範囲」の必要箇所を使う。手順はここへ丸写しせず、実際の入口と固定storyが対応しているかを確認する。既存テストの名称にE2Eとあるだけでそのstoryを網羅したとは扱わない。

実機/Apple/外部条件待ちなら、まず固定scope/問いに必要なデスクトップ上の検証経路と重要条件を省かず実行する。無関係な全環境の総当りは求めない。物理機材だけで証明できる残りを具体的に分け、「未確認」と書くことでローカルE2Eまで省略しない。権限/環境不足で実行不能なら試した手段・具体的不足・残る経路を示して未完/検証待ちとする。設定・承認・機材の必要な依頼はできるが、AIが行える検証の代わりに未検証機能を「試してください」と引き渡さない。真に待ちとなった依存範囲を記録した後は、scopeと所有を守る独立作業を続けられる。

親は固定scope全経路の必要E2Eと最終source/設定との対応と変更影響を完了/引渡しの必須gatewayとして確認する。E2E未実行/失敗なら「できた」「動く」「完成」「使える」「確認してください」等で機能完成・利用可能性を主張しない。これは製品機能・技術経路の成立/利用可能性を主張する作業の条件であり、その主張がない文書/スキルだけの変更に不要なアプリE2Eを強制しない。文書の形式/参照検査は機能の実証ではなく、技術検証という名称も実native App経路の省略理由にはならない。

| 報告する到達点 | 混同しない境界 |
|---|---|
| 部品検証 | 単体・結合・SDK/build・起動等で確認した限定範囲。storyの最終出力や操作成立は別 |
| 技術経路の成立確認 | 判断したい経路を指定環境の実行/計測で確認した証拠。UIや製品品質まで含むとは限らない |
| ローカルE2E完了 | 固定したローカル経路・両端/最終出力・終了等の必要条件を満たす。mock/物理/Apple境界は別 |
| 実機受入未了・製品story完了 | 実機や外部にしかない残条件は未了と明示。製品story完了は固定scopeに必要な操作/品質・受入証拠が揃った場合のみ。ローカル合格を実機/Apple受理の保証にしない |

検証済みの小さなpackage/App部分工程の記録・コミットや、親が具体的な対象を許可した段階的mergeは、全storyのE2E未完だけを理由に一律禁止しない。その部分工程の完了をcore story完了・機能利用可能・ユーザー引渡しへ読み替えず、枝葉へ進む抜け道にせず、関連App接続と必要E2E完了まで幹を継続する。

以下の従来方針・理由は保持するが、関連機能の一体設計や独立検証をscope膨張へ使わず、待ち中の継続も実行可能なコアE2Eから逃げる口実にしない。区切りは検証・現行仕様更新・コミット・main統合/pushまで正本と許可範囲に従って閉じる。本スキルの改訂や適用そのものをアプリ実行・外部操作・pushの許可としない。

## 利用者の理由

次はこのスキルの起点となった利用者の方針と因果関係であり、全作業の損失・費用を実測して証明した結果ではない。

> 大事なのは不確実性を先に潰して、後に残さない。決定する前に判断根拠（条件ではない）を先に揃えることで、それは実装をしないとわからない。細かい改善は後でもできるが、技術的にNGとかApple的にNGはそもそも先に作ってテストしないとわからない。なのに細かいことで時間をかけ、コストをかけている。
>
> それは先物を高く買っているにすぎず、将来のオプションを殺している。だってエージェントはリミットに達するし、コードも使えないコードだらけ。仕様も複雑になるから。

| 利用者の判断 | 後から使う理由と選択への影響 |
|---|---|
| 製品価値・主要課題・後続設計を先にする | 基礎となる経路やApple上の成立が崩れれば、その前提のUI・設定・抽象化も捨て直す。確証のない前提へ費用と時間を固定すると、残予算・agentの実行余力を使い、代替を選ぶ余地が減る。低価値・大きな手戻りを生む実装を先行しない |
| 関連機能を可能な限り一緒に設計・実装する | 孤立した機能ごとの最適化は状態・認可・終了条件の不整合と後待ちを作り得る。複数課題の共通の体験と境界を扱い、条件を足し続けるより仕様を簡単にする。工程・所有・mergeの小分けとは両立する |
| 根拠を決定の前に揃える | 仕様条件と合格基準は「何が欲しいか」であり、「実際に成立するか」の答えではない。実装して対象環境で動かすことで初めて判明する制約は、読み物や内部テストの量で代替できない。AI自身が重大な問題や要実験の前提を認識しながら依存する周辺実装へ進めば、既知の不確実性による手戻りと費用を要求者に負わせる。認識した時点で先行検証へ作業順を変え、実行不能なら依存作業を保留する。「未確認」と報告するだけでは先行実装の根拠にならない |
| 独立作業を待ち時間に進める | 当該scopeで実行可能なデスクトップE2Eを先に行い、真に残る質問や実機・権限待ちを全体停止の理由にせず、後続の大きな採否を変える独立検証を早く行う。一方で未回答の前提を恒久化しない |

これは全ての不明点や細部の先行解消を命じるものではない。主storyの成立・重大回帰・後続採否を覆す不確実性から選ぶ。固定の機能順、常にWatchから始めること、簡単なチケットから順に片付けること、backlog件数/テスト件数を成果指標とすることは導かない。この依頼から別チャットの実進捗・ゴール遵守や過去損失を監査済みとは主張しない。

## 選択と後回し

| 着手・区切り・追加依頼で親が見ること | 判断 |
|---|---|
| 小さな縦storyと価値 | 要求者が何を実現・判断したいかを先に定め、その判断に必要な実経路・最終出力・必要な終了/回復を選ぶ。利用者操作は問いに必要な場合に含め、常にUI開始を前提にしない。現行ゴール・製品要求と結びつける。部品・API・ボタンだけの実装をstory完了にしない |
| 不確実性と誤判断の損失 | 何が成立を根本から覆すか、それがNGなら後続のどの仕様・コード・費用が無駄になるか。根拠が不足している重大論点を先に取り出す |
| 今やるか・後にするか | story成立、重大な回帰、後続の採否に必要な作業を先にする。細かなpolish・設定増設・抽象化や再点検は、その価値と依存を示し、今不要なら保留理由と再開条件を残す。アクセシビリティ・安全性等、必要な品質を見栄えの細部として後回しにしない |
| まとめる範囲 | 関連機能の体験・共通状態・認可・終了/失敗境界を合わせ、可能な関連実装を一緒に計画する。全機能を巨大な一括実装にせず、App/package工程は分けて契約と検証から順につなぐ |
| 並行と主軸の数 | 一つの主軸を基本に親が進めるもの/保留を管理する。固定scopeの完遂を妨げず、他storyを含め独立した重大不確実性の検証は早期に並行でき、全機能を完全直列にする規則にしない。依存・編集所有・共有資源・費用を確認し、未完の主軸を増やしすぎない |

現行の[未実装課題](../../../../docs/backlog/未実装課題.md)「依存関係と取り組む順序」はその時点のstory順の実例であり、スキルへ固定順をコピーしない。後続の独立した重大論点を先に検証する場合も親が主軸と依存・保留を明示し、実際に衝突する指示は原文と選択肢を親へ戻す。抽象化や再点検は当該story成立・品質維持に必要な範囲に絞り、必要なTDDや回帰検証は省かない。

## 判断根拠と証明の範囲

| 根拠の種類 | 記録して判断できること・限界 |
|---|---|
| 公式一次情報 | Apple等の公式仕様・API/権限・配布条件の該当箇所、対象OS/版と確認日。資料上の支援と実アプリの成立を区別し、文書では未確定の背景動作や実音声経路を読み物だけで閉じない |
| 実装と実行の観測 | 対象source/差分・設定・OS/機器・起動/終了状態、利用者の操作、期待と実際、失敗を含む証跡。コーディング・単体・Simulator成功は実機の無線/音響・OS背景・権限・審査/配布の成立を証明しない |
| 代表条件の計測と失敗 | 代表条件を選んだ理由、計測の始点/終点・単位・結果、再現条件と反証した仮説。未計測・未実行・skipを成功にせず、限定した成功を全条件に一般化しない |
| 採用判断 | 上の根拠がどの案を支持/否定したか、残る不明点、後で覆る条件を示す。実装成功でもApp Store受理・審査通過・全配布先での動作は保証できず、必要な別の受入証拠が揃うまで未確認とする |

利用者方針、設計上の仮説、公式情報の記述、実際の観測を区別する。受入条件表・仕様条件・計画・テスト件数を埋めただけで根拠が揃ったと扱わない。判断の根拠が足りなければ、下記の最小実験、必要な質問、または未確認としての保留を選ぶ。

## 実験を小さく閉じる

重大な技術・プラットフォーム/Apple・配布・API権限・実音声経路は、後続へ大量投資する前に小さな動く縦実装/試作で反証を探す。実装の必要性は、制約を回避したり事前権限を超える理由にはならない。実サービスのローカル検証先行・人数/時間/回数上限・回収などの費用制約と実行許可は[開発方針](../../../../docs/policies/開発方針.md)を維持する。秘密・音声payloadを証跡へ残さず[ログ記録規約](../../../../docs/policies/ログ記録規約.md)を守る。

| 実験の担当契約に残すもの | 内容 |
|---|---|
| 問いと覆る判断 | 解消したい重大不明点、NGなら採用/仕様/設計のどこを変えるか、誤判断で失うもの |
| 必要証拠と最小実装 | 判断を支える公式一次情報・実行の観測・代表計測/失敗のうち必要なもの。開始から目的・終了/回復までを確かめられる最小経路と、作らない周辺機能。試作の成功を製品品質の完了と混同しない |
| 対象条件と資源 | source/差分、設定、OS/機器、背景/画面状態や実音声経路など問いに必要な条件、所有するprocess/sessionと証跡保存先。対象環境が使えなければ未確認と記録 |
| 上限と停止 | 時間・費用・試行回数の上限、反証/必要証拠が得られた時点、進展なし/権限不足等の停止条件と回収。全不確実性の解消を続行条件にしない |
| 結果と次の選択 | 成功は適用範囲付きの採用根拠、失敗は簡素化・代替・不採用の根拠として残す。足りない証拠と次の一手を分け、使い捨て試作を未整理の製品経路へ残さず、不要な経路・設定・仮抽象を整理して選択肢を残す |

## 継続と記録

親は開始・区切り・追加依頼で現行ゴールと優先順位の適合を見直す。途中の小さな追加にも費用・速度・品質と主軸への影響を判断し、単純調査や操作に安価なモデルと既存担当を使えるか[efficient-work](../../efficient-work/SKILL.md)で選ぶ。追加を即時実装して主軸を圧迫せず、今やる/保留/次の単位へ移す理由を示す。実行中の仕事を無計画に捨てず、小さく閉じる境界と次に進む条件を決める。

scope内の実行可能なE2Eを先に行ったうえで、質問・判断・機材/権限・Apple/実サービス待ちの間は、仮置き・質問内容・影響範囲・待つ証拠と担当・再開条件を残す。独立作業は継続し、返答が来たら前提と影響する仕様/実装/検証を訂正する。回答なしを承認や恒久仕様にせず、証拠のない境界は未受入・未確認として残す。

| 残す場所 | 情報 |
|---|---|
| backlogと判断用の引継ぎ | 未実装の設計・残課題、仮置きと質問・影響、親の選択/保留理由、依存と次の完了条件。重要な数値・例外・禁止を落とさず必要な原文へ辿れるようにする |
| 現行仕様・manual | 成立した実態と操作、採用した契約、現在の制限/非対応。完了分をbacklogから移し、目的を削って完了扱いにしない |
| validation | 条件と対象sourceに紐づく観測・計測・失敗の証跡。未受入・実機/背景/Apple等の未確認は未確認事項へ分ける。過去結果を新条件の成功へ書き換えない |

文書の分類は[文書作成規約](../../../../docs/policies/文書作成規約.md)に従う。新発見を消してbacklog件数を減らした扱いにせず、未実装/未受入/新発見を正しい分類に移す。区切り・引継ぎ・圧縮後にも、主story、判断と根拠、関連機能の共通境界、未解決の重大な妨げ、次に止め/進める対象を復元可能にする。テスト成功や多commitだけではstory成立・受入の代わりにならない。
