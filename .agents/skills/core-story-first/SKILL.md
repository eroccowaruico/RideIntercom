# 重大な不確実性を先に試し、コアを証拠で閉じる

[AGENTS.md](../../../AGENTS.md)の必須正本と現行ゴール・要求者の目的と訂正を適用する。親/主担当は要求者の目的に照らし、NGならコア・採否・後続設計を覆す未解消の不確実性を優先し、小さな主軸と範囲・完了を管理する。成果は要求者の判断が進んだこととコアの成立で示す。

AI自身が「問題がある・試さないと分からない」と認識した、採否や設計を左右する前提は、その時点で最小の実経路で先に試す。その前提に依存するUI・設定・抽象化は検証結果を得てから進める。実行不能なら具体的な不足と影響を示して依存作業を保留し、独立した作業だけを進める。

順序は「重大な不確実性→最小の実装・E2E→観測による採用/簡素化/代替/不採用→必要な製品実装」。仕様条件・合格基準と、成立を判断する実際の観測結果を揃える。未確認の前提に周辺実装や設計見直しを積むと、手戻りに加え、残予算・agentの実行余力・代替を選ぶ余地を失うため、この順序を守る。

## 前提を確認してから決める

設計・仕様や「こうあるべき」を決める前、回避策・分岐・設定を追加する前、試行が進展しない時は、要求者の目的・明示された制約・観測事実と、AIが置いた仮定を分けて前提を見直す。正本・コード・最小実験で確認できる事実を先に確かめ、前提の変更・簡素化・別案でコアを成立させる方法を比較する。

要求者の意図・優先順位・許容範囲など、採否や仕様を左右する前提が未確定なら、主担当が要求者へ質問してから判断する。質問には疑う前提、根拠となる観測や不明点、選択肢と影響を簡潔に添える。返答待ちは依存する判断・実装を保留し、独立して進められる作業を継続する。回答に合わせて前提と仕様・実装・検証範囲を更新する。

## 着手前に固定する

| 固定するもの | 担当へ渡す内容 |
|---|---|
| 一つの最小コアstory | 要求者の目的→今回確かめる問い・その証拠で決めること→最小の実経路と観測結果、今回の対象・保留する周辺機能。未指定なら現行ゴールの最重要コアから主担当が小さく選んで明示 |
| 判断根拠と検証の上限 | NGなら捨て直すもの、既存証拠と不足する観測、必要最小限の実験、時間/費用/試行の上限。観測が採否をどう変えるかを定め、有効な既存証拠で判断できる場合は、その根拠を再利用して次の判断へ進む |
| 共通の必須条件 | [開発方針の実装と検証](../../../docs/policies/開発方針.md#実装と検証)に従い、不足テストの変更前追加・実行と変更後の回帰実行を固定する。[開発環境の要求](../../../docs/policies/開発方針.md#開発環境の要求)に従い、技術検証もXcode GUIから実行できる入口を使う |
| E2Eと完了条件 | 問いに必要な入口（UIなし/簡易UIも可）→実処理→必要な通信/相手側→最終出力・副作用→終了/再開/回復の操作と観測先、必要環境と証跡 |
| 範囲の変更 | 発見をstory阻害・重大回帰・後続改善へ分け、必須追加だけ親が根拠と影響を示して更新。設定・UI polish・抽象化・別機能の追加はコア成立への必要性で選び、保留分は再開条件とともに記録する |

## 動作を保ってコミットできる範囲に絞る

**[開発方針の小さく動く単位](../../../docs/policies/開発方針.md#小さく動く単位で検証・コミットする)を着手・区切りの必須条件とする。** コアの最小実経路も、ビルド・動作・回帰を確認してコミットできる範囲へ着手前に分割する。未コミットの滞留と保留を含む進行中単位は親が正本どおり管理し、部分工程のコミット後もstory全体の必要E2E・受入まで主軸を継続する。

## 実装・E2E・修正を閉じる

問いに必要な最小実装と実経路のE2Eを先に通す。製品UIなし・簡易UIでよいが、製品Appへの接続が問いなら実Appを通す。利用可能なSimulator・Mac等で必要な経路と重要境界を実行し、文章の確認・起動・build・単体/結合・送信受付の結果は部品の証拠として扱い、コア成立は必要な実経路の最終出力で確かめる。詳細は[実行と証跡](references/優先判断の根拠と実行.md#狭いscopeとe2eの実行・完了判断)の必要節だけを読む。

UIのstoryはUI入口、音声は相手native出力/波形と該当する双方向・遅延・連続性・停止/再開まで確かめる。既存入口で通らない経路は必要最小限のE2Eを追加/実行する。製品実装の不具合は担当側で原因切分け→修正→関連E2E再実行し、採用を続ける経路のE2Eを閉じてから次のstoryや改善へ進む。App/packageの工程分離と必要なTDDは維持する。

技術検証でNGを再現した場合は、その証拠で不採用/簡素化/代替を判断して実験を閉じられる。報告は不成立の証拠と採否判断として示し、試行は決めた時間・費用・回数の範囲で閉じる。判断に必要な証拠が揃ったら試行を止める。

実機/Apple/外部待ちでも、実行可能な固定範囲の検証を先に閉じる。残る環境・権限不足と試した手段は未完/検証待ちとして記録し、AIが行える検証を自分で実施し、利用者の操作は必要な受入範囲へ絞る。

## 親の完了・引渡し判定

正本の回帰保護要件を満たしたことも親が確認する。既存機能の維持は影響範囲の回帰結果で判断する。

機能・技術経路の成立を主張する前に、[証跡照合と完了判定](references/優先判断の根拠と実行.md#狭いscopeとe2eの実行・完了判断)の該当節を必ず適用する。親は必要E2Eと最終ソース・設定、両端/最終出力と失敗・skip等を照合し、固定scopeに必要なE2Eと回帰がすべて成功した時に、そのstoryを完成・利用可能と報告する。部分的な成功は部品・経路の確認として報告し、残る必須検証があるstoryは未完として記録する。mockで置換した本番経路も未検証として分ける。

技術経路の成立、部品検証、ローカルE2E完了、実機受入未了、製品story完了を分ける。「成立した操作・判断を変える観測・重大な妨げ・次に止め/進めるもの」を示す。区切りは仕様更新・commit・main統合/pushまで開発方針と許可範囲で閉じ、backlogは情報を保持して現行仕様・残課題・未確認へ整理する。

## 必要な参照だけ読む

[優先判断の根拠と実行](references/優先判断の根拠と実行.md)の「狭いscopeとE2Eの実行・完了判断」は実装/検証/完了時、「利用者の理由」「選択と後回し」「判断根拠と証明の範囲」「実験」「継続と記録」は各判断時に必要節だけ読む。モデル・役割・文脈再利用・小さなmerge・検証資源は[efficient-work](../efficient-work/SKILL.md)を適用する。関連機能の設計整合と重大不確実性の先行確認を保ち、待ち中も実行可能なE2Eを先に閉じてから独立作業を進める。スキル/文書のみの変更は形式・参照の検証で受け入れ、アプリの機能実証とは到達点を分ける。アプリ実行・修正・外部操作は依頼と承認の範囲で行う。
