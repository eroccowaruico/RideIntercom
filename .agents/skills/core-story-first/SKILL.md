# 製品価値と成立の根拠から作業を選ぶ

[AGENTS.md](../../../AGENTS.md)の必須正本と現行ゴール・利用者の訂正を適用する。作業の選択・計画・着手、区切り、追加依頼で親/主担当が優先順位を確認し、採用・保留と理由を管理する。固定の機能順や常にWatch優先とする規則ではない。

細かな実装より製品価値・主要課題・後続仕様/設計へ影響する課題を先にする。重大な成立不明を残したままUI・抽象化・設定を大量に積まない。合格条件を並べても判断根拠にはならず、必要な実装・実行の観測を決定より先に揃える。

## 作業単位と順序

| 判断 | 行うこと |
|---|---|
| 何を成立させるか | 利用者が開始し、目的を達成し、終了または回復できる小さな縦のコアストーリーを示す。根本から成立を覆す未確定事項と誤判断後の損失を添える |
| 何を先に確かめるか | 重大な技術・Apple/OS・配布・API権限・実音声経路等は、小さな動く縦実装/試作と必要な対象環境のテスト・計測で反証を試みる。判定不能な境界は未確認として独立作業を継続する。公式資料だけでも、単体/Simulator成功だけでも不明点を閉じない |
| 何を合わせるか | 連携機能の体験・状態・認可・終了と失敗境界を一緒に設計し、可能な範囲で関連実装をまとめて不整合・待ち・仕様の複雑化を減らす。App/packageは別工程、小さな検証・merge単位を守る |
| 何を後にするか | story成立・重大回帰・後続採否を覆す論点に関係しない改善は理由付きで保留。全不確実性をゼロにする研究へ拡大せず、必要なTDDと品質検証は維持 |
| 何を並行するか | 依存・編集衝突を避け、独立した重要不確実性の検証や他storyの作業も進められる。親が主軸を選択・保留管理し、未完の主軸を増やしすぎない |

## 必要な詳細だけ読む

[優先判断の根拠と実行](references/優先判断の根拠と実行.md)から、優先順位の判断には「利用者の理由」と「選択と後回し」、成立性の検証には「判断根拠」と「実験」、追加依頼/待ち/引継ぎには「継続と記録」の必要節だけ読む。全員へ参照全文を渡さない。

モデル・思考・既存担当の再利用、実行管理と担当間連絡、worktree・親のmerge許可/保留、テスト実行・解析・修正は[efficient-work](../efficient-work/SKILL.md)の該当手順を適用する。単純作業/調査は安価なモデルを候補にし、品質・費用・速度の判断を追加依頼にも適用する。本スキルで実行/承認権限や依頼範囲を増やさない。

## 継続と報告

今の作業を無計画に捨てず、小さく閉じる境界と次に進む条件を示す。判断・質問・機材/権限・Apple/実サービス待ちでも独立作業は続け、仮置き・問い・影響・再開条件を残し、返答で訂正する。回答なしを承認や恒久仕様にしない。

区切りでは「成立した利用者操作」「判断を変えられるようになった観測」「未解決の重大な妨げ」「次に何を止め/進めるか」を示す。テスト/commit/消化チケットの件数をcore story成立の代わりにしない。

区切りは検証・現行仕様更新・コミット・mainへの統合とpushまで、開発方針と利用者の許可範囲に従って閉じる。実験で採用根拠を得たことと製品のstory完了を区別し、本スキルの作成や適用だけを実サービス操作やpushの許可としない。

完了分は現行仕様へ移し、未実装・未受入・新発見は文書規約の分類へ残す。情報を消してbacklogを減らさず、分割や圧縮後も判断根拠と関連機能の整合を保持する。実機・背景・審査/配布の未確認境界を明記し、実装しただけでAppleの受理を保証しない。
