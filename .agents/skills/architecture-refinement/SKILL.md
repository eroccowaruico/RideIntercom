# RideIntercomの責務分離と共通化

## 目的と呼び出し

`$architecture-refinement`、または「今回の変更に責務分離の見直しを適用して」で、指定範囲の点検・必要な修正・検証・段階的コミットまで行う。対象が未指定なら今回の変更と影響する共通経路を対象とする。「確認だけ」「修正しない」「コミットしない」など、その呼び出し時の制約を優先する。

## 作業の前提

[AGENTS.md](../../../AGENTS.md)と、そこから指定される製品要求・開発方針・文書作成規約・ログ記録規約を読み、適用する。[文書入口](../../../docs/README.md)から対象の現行仕様と検証範囲を確認する。既存の抽象と実装を調べ、作業ツリーの他作業の変更を保護する。

作業の優先と完了は[core-story-first](../core-story-first/SKILL.md)、実行管理は[efficient-work](../efficient-work/SKILL.md)を適用する。二巡とも指定範囲と影響経路に絞り、重大不確実性の検証を全面整理より先に行う。App/packageの工程分離は[開発方針の実装と検証](../../../docs/policies/開発方針.md#実装と検証)に従う。

## 責務分離で確認・修正すること

| 対象 | 満たす要求 |
|---|---|
| Xcode GUIからのビルド・テスト・自動化 | [開発環境の要求](../../../docs/policies/開発方針.md#開発環境の要求)を適用。指定範囲の既存入口も棚卸しし、GUI起点で全機能・結果判定・終了処理まで動くか点検する。CLIとの不一致は修正・再検証する。指定範囲の全入口・全機能が必要な検証を満たした時に点検完了とし、残る必須検証がある場合は対象全体を未完、部分結果を確認済み/未確認に分けて記録する |
| ファイル・ディレクトリの配置 | [配置・設定の増設禁止](../../../docs/policies/開発方針.md#作業完了時の整理と回収)を適用。既存の不適切な配置も点検し、必要な統合・移動・削除と参照・target所属・文書・検証の更新まで閉じる |
| 状態 | 同じ状態の保持・更新を一つの所有元へ集約し、更新経路を明確にする。複数画面やモードから同じ状態・操作を利用できるようにする。画面表示用の投影にも元の状態との関係を持たせる |
| 画面とのI/F | 処理・ドメインと画面のインターフェースを抽象化し、処理は画面構成やUIフレームワークと独立した契約へ依存させる |
| 複数画面・モード | 複数の画面構成を持てる設計にし、画面自体はモードごとに分離する。状態・業務処理は各画面から共通の所有元を参照する |
| 画面コンポーネント | 意味の同じコンポーネントの共通化を進める。テーマや体験の違う部分は特性に合わせて分離し、共通部分とテーマ固有部分を明確にする |
| ドメイン | ドメインごとの責務を分離し、処理・画面・ライブラリ・フレームワークの依存境界を守る。OSやフレームワークの具体的なAPIへの依存を境界に閉じ込める |
| 共通処理と差分 | 共通化した上で、どこがなぜ違うかを明確にする。値だけが違う場合は共通処理へ値を渡し、単一の値では表せない違いは関連する数値・設定・条件をパラメーターセットとして渡せる土台を作る |
| 本当に固有の処理 | 個別に必要な処理は固有であると分かる名前のファイルで管理する。方式固有の処理は各固有実装へ集約する。共通化は意味と特性の同一性を根拠とし、固有の特性は個別実装で保つ |
| プラグインの抽象化 | 既存の差し替え境界が維持され、呼び出し側が個々の実装詳細を知らずに扱えるか確認し、崩れていれば修正する。プラグインに関係なく行える処理は共通化し、固有の処理だけを各実装に残す。点検対象は既存の差し替え境界とする |
| 保守性 | 再利用性に加え、アプリ内の結合度と変更の影響範囲を減らす。複数箇所に影響する問題は共通経路で解決し、人間とAIの双方が追いやすいシンプルな実装にする |
| 設計パターン | 実績があり、現在のSwift・SwiftUI・Concurrencyにも適切な設計を採用する。既存の抽象を活用し、層・型・protocolは現在の責務に必要な最小範囲で用いる。不要になった重複や旧経路は整理する |
| Xcode | Xcodeの設定は標準の構成と約束に従い、Run・Build・Test・Archiveが通常の操作で成立するようにする。設計上の問題は標準の構成で成立する責務へ整理する。詳細は[開発環境](../../../docs/development/開発環境.md)を参照する |

## 設定切り替えとRTCを横断して確認すること

| 対象 | 点検と修正の基準 |
|---|---|
| 各種設定の切り替え | コーデック切替、サンプリング周波数変更、ビットレート変更を含め、同じ役割の反映処理を横断して比較する。入力の正規化、状態反映、実処理への適用、通知・表示などに同じ処理があれば共通化し、利用者・実装者の双方にとって挙動を安定させる |
| 設定ごとの特性差 | 方式の特性により数値を固定・統一できない場合も、処理は共通化して数値と設定をセットで渡す。共通処理の中でも違いが分かる形にし、方式固有の値と条件を保持する |
| RTCの差分 | RTC方式ごとの同じ役割の処理を横断して比較する。開始・停止・設定反映・経路切替・復旧などで共通に扱える部分は共通化し、方式に依存する処理だけを固有実装へ残す。固有の順序・数値・条件が必要なら設定セット等で表し、特性を保つ |
| 条件の根拠 | 個別要件から抽出した条件や例外は、理由が分かるインラインコメントまたは現行仕様に残す。数値や分岐の意味を後から追え、共通化や別方式への展開後も固有の契約を維持する |

音声やRTCが今回の対象外なら、点検は指定された対象ドメインに絞る。上記の共通化・差分分離の考え方を対象ドメインへ適用する。

## 品質・費用・異常終了の確認

- 作業中は常に、コスト、音声品質、レイテンシの品質を維持する。既存の受入条件と変更前の挙動を確認し、共通化による余分な処理・待機・再接続・通信の増加を調べる。合格判定には既存の受入基準を維持する。
- [回帰保護の正本](../../../docs/policies/開発方針.md#実装と検証)に従い、変更前の不足テスト追加・実行と、各巡の変更後の関連リグレッション・必要な結合/E2Eを必須とする。基準結果と最終結果を照合し、完了には必要な検証の成功を揃え、未実行・失敗は未完として記録する。設定切替は値だけでなく適用後の音声品質・連続性・遅延も確認する。
- 起動・対象操作・設定切替・停止を実行し、失敗・timeout・実行時警告・crash reportを確認する。意図的な試験終了と強制終了を区別し、実用時にも起こる障害は製品側の原因を修正して再検証する。
- 費用を伴う実サービスの検証は開発方針の条件に従う。ローカル/Simulatorと実機の無線・Bluetooth・電池・発熱・外部サービスの品質は、それぞれの条件と証拠で確認する。未実行・失敗・未確認は成功と区別して残す。

## 最低二巡の改善と段階的コミット

指定範囲で「点検→必要な修正→回帰検証」を最低二巡行う。初回は上記の要求と現行コードを照合し、二巡目は変更後のコードと責務を改めて横断して同じ観点で再点検し、必要な修正を行う。問題がない場合は確認結果を記録して閉じる。

検証済みの自分の差分だけを責務・依存関係の小さな単位で段階的にコミットする。統合・許可・index保護はefficient-workの担当手順に従う。

完了時は、改善した責務と共通処理、残した固有差分と理由、二巡それぞれの結果、実行した検証と品質の根拠、コミット、残る未確認事項を簡潔に報告する。「綺麗で問題がない」は確認した範囲に基づいて述べ、結論には確認した範囲と未確認の境界を添える。
