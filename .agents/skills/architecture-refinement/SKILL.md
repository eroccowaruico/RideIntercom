# 責務分離と共通化の改善

利用者が指定した範囲を対象に、現行の要求・仕様・開発規約と作業ツリーを確認し、既存変更を保護してから実装まで進める。音声やRTCに限らず適用し、対象外の機能には広げない。

- 状態の所有元と更新経路を明確にし、同じ状態を各所で独立に持たない。処理・ドメイン・画面・ライブラリ・フレームワークの境界を整理し、画面とのインターフェースを抽象化する。複数画面から扱える状態・操作を設計し、モードごとの画面は分離する。
- プラグインや実装方式を横断して、共通の流れを共通化し、固有処理は識別しやすい場所に隔離する。設定変更や異なる実装経路も対象に含めて調べる。差が値や条件の組なら設定・パラメーターセットで表し、意味の異なる処理やテーマは無理に統合しない。共通化後も差異とその理由が分かるよう、必要な条件の根拠をコメントまたは現行仕様に残す。
- 再利用だけでなく、結合度と変更の波及を減らし、同じ不具合が複数箇所で再発しにくい構造を目指す。既存の抽象を優先し、理解や保守を難しくする不要な層・汎用化を避ける。環境やツールの標準設定に従い、実績があり現在も適切な設計を選ぶ。
- 対象が音声・通信なら、コーデック、サンプリング周波数、ビットレートなどの切替とRTC方式間の共通経路・固有条件を点検する。音声品質、遅延、通信・電力・サービス費用を損なわないことを検証し、測定できない品質は推測で保証しない。

実装と適切なテスト・ビルドを行い、対象に応じてアプリを起動・操作して異常終了や実行時の問題を確認し、実用時にも起こり得る問題を修正する。初回の改善・検証後、境界、重複、差異、品質、異常終了を少なくとももう一度点検し、必要な修正と再検証を行う。各段階で検証できた自分の変更を、利用者の指示・リポジトリ規約・権限に従って区切りよくコミットし、無関係な変更を含めない。未実施の検証、残るリスク、コミットできない事情は明示する。
