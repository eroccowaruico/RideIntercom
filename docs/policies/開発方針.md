## 品質と開発プロセス

### ブランチ運用

- 継続開発と統合の基準は`main`一本とし、短期branchも統合先を`main`へ揃える。
- PR運用は行わず、検証済みの変更をmainへコミットして直接pushする。
- 作業を隔離する必要がある場合だけmainから短期の作業ブランチを作り、検証後はmainへ統合する。
- 長い作業でも、検証が完了した作業の区切りごとにmainへ統合してpushし、リモートのmainとコミットが一致することを確認する。統合対象は検証済みの自分の変更へ限定する。
- 開発はmainと現行の短期branchで進め、過去作業の保全branch・worktreeは履歴として扱う。回収は未統合差分の所在と保全を確認してから行う。
- 隔離作業は区切りごとにmainへ統合し、不要なworktreeを整理する。削除前に未コミット差分・未追跡ファイルの統合、稼働process、残す検証証跡を確認する。実装済みの契約は仕様へ移し、課題一覧には残作業を保持する。 保全する旧projectやpackage sourceは、Xcodeの同期フォルダから開発用のproject／packageとして再検出されないアーカイブ形式で保存する。
- 継続作業では共通正本に加え、対象機能の現行仕様・残課題・必要な証跡だけを読む。引継ぎには現在の作業領域・基準commit・未統合差分・生存中の検証handle・次の完了条件を絞って残し、継続に必要な情報は現行の正本と再開情報から取得する。

### 公開バージョンとビルド番号

- 公開バージョンは可能な限りSemantic Versioningの`major.minor.patch`を適用する。利用者に公開する機能・招待や保存形式・通信契約の互換性を基準に、非互換変更はmajor、互換性を保つ機能追加はminor、不具合修正はpatchを変更する。major変更時はminor・patch、minor変更時はpatchを0に戻す。
- 公開バージョンは利用者の明示指示で変更し、通常のビルド・Archive・アップロードでは現在値を維持する。
- ビルド番号はXcode標準の`CURRENT_PROJECT_VERSION`、公開バージョンは`MARKETING_VERSION`を使い、projectの共通設定をApp・Widget・Watch・テスト対象が継承する。通常ビルド・Run・Test・Archiveを含む全scheme・全構成でビルド番号を自動的に進める。採番は既存の共通設定と標準ツールで扱う。
- Xcode標準のBuild後処理とAppleの`agvtool`で次回用の番号を更新する。次回用設定が進むことを完了条件とし、開始時への反映タイミングと欠番を許容する。保存先の見直し後も自動インクリメントを維持し、Xcodeを開いたまま標準操作で実行できる構成を保つ。
- Build後処理で`CURRENT_PROJECT_VERSION`が更新されたら、ビルドの目的や担当者の作業内容に関係なく、番号変更を独立した小さな単位として速やかにコミットする。関連作業や次の作業単位の完了まで保留せず、コミット前に差分が番号更新だけであること、App・Widget・Watch・各構成の共通値が揃っていること、既知の配布・Archive番号を下回らないことを確認する。他の未コミット変更は同じコミットへ含めない。
- 同一ビルド・Archive内のApp・Widget・Watchの番号を一致させる。成果物の番号とBuild後処理で進んだ次回用設定値を区別する。配布時は既存の最大ビルド番号を超える番号を確認し、Organizerが配布時に番号を管理する場合もArchive内の番号と配布物の番号を区別して記録する。
- 並行作業・実行中のアプリやビルドを維持し、自分の検証に必要な実行資源を所有範囲で調整する。番号は全構成と既知の配布・Archiveにある最新最大値を基準に単調増加させる。設定の欠落・破損時は記録済みの最大値と履歴から復旧する。別checkoutや別Macからの配布は担当者間で番号を共有する。
- 配布用`CFBundleVersion`はAppleの規定する数字とピリオドの形式を使い、その形式で10進値を保存する。Apple OSの英字入りbuild-versionは別の識別子である。旧公式資料にある開発段階の`a`・`b`・`d`・`fc`接尾辞も16進数ではなく、製品配布時には除く。SemVerの`+build`などの付加情報は必要に応じて別の説明項目で扱う。Xcodeでの設定と配布手順は[開発環境](../development/開発環境.md)を参照する。

### 実装と検証

- 開発はTDDを前提とする。
- 注入した音声入出力で再現できる音声TDDを維持し、音声品質・安定性・拡張性を確保する。
- 接続性や暗号化などの非音声処理も、可能な限りTDDで実装する。
- テストは実装・実行・結果解析を一単位とし、成功を確認する。
- コアの成立や重大な不確実性の先行検証を優先しても、既存機能を回帰テストで保護する。変更前に共通処理・状態・呼出元・依存先を含む影響範囲と、その既存動作を保護するテストの有無・網羅性を確認する。不足する回帰テストは製品コードの変更前に実装・実行し、変更前の基準結果と既存の失敗を区別して残す。
- 機能実装・修正後は、最終のソース・設定に対して影響範囲のリグレッションテストを必ず実行する。影響する結合経路・E2Eも対象とし、既存機能の維持は影響範囲の回帰結果で判断する。新規の回帰は修正・再実行し、必要な検証が成功した範囲を完了・引渡し対象とする。未実行・失敗は未完として記録する。検証範囲は影響する領域へ絞り、選定根拠と結果を残す。
- 各実装工程の変更対象はAppまたはpackageの一方に限定する。両方に変更が必要なら、packageの独立した契約・実装・検証を閉じ、次の工程でAppを追従させる。
- 常にビルド・テストが成功し、ワーニングを解消した状態を維持する。
- パッケージライブラリは独立性を保ち、Appの都合は無視して、OS差異や通信方式差異だけでなく継続可能な準異常系もいい感じに処理を吸収する設計して、実装の詳細に依らず環境差異のある呼び出しは全て無視しつつ同じ設計・同じ呼び出し方で使えるようにする。
- パッケージライブラリ修正時は現在の要求に合う契約へ直接更新し、呼出元も新APIへ揃える。旧契約専用のalias・wrapperは整理する。
- パッケージライブラリは必要な情報は実行時の確認情報含めて必要な情報は全てリアルタイムで渡せて、必要な設定は受け取れるようにする。
- パッケージライブラリごとの責務を再定義し、App都合ではなく通話音声基盤として整理する。
- Appから見たpackageの不足は、packageの責務と設計から見直して根本解決する。
- Appがやるべきことは UI、設定入力、package lifecycle 呼び出しだけにする。

### 小さく動く単位で検証・コミットする

**着手する範囲を、小さく実装し、ビルド・最低限の実動作・影響範囲の回帰を確認してコミットできる単位に限定する。検証済みの単位を閉じてから次へ進み、未コミット変更を積み上げない。**

| 判断する時点 | 必須の進め方 |
|---|---|
| 着手前 | 一つの挙動・契約または判断を閉じる最小単位を選び、対象・依存先・維持する動作・必要検証・コミット境界を決める。その単位で閉じられない範囲は着手前に分割・縮小し、切り出せない依存部分は保留する。関連機能を一緒に設計する場合も実装はこの単位へ分け、App/packageの工程分離を守る |
| 変更の大きさ | 対象ファイルと変更行を目的に必要な最小範囲へ絞り、無関係な整形・移動・改善は別単位へ分ける。必要な実装・呼出元・テスト・仕様は一体として成立させる。行数やファイル数だけで切る代わりに、各コミットが単独で動作・検証条件を満たす境界を選ぶ |
| 実装・検証中 | 各編集担当の未コミット変更は原則一単位とし、既存の呼出元・設定・保存/通信契約を維持して、修正→ビルド→最低限の実動作→影響範囲の回帰・必要E2E→結果解析まで閉じる。TDDの失敗再現から修正までは担当の所有範囲で短く行い、新しい回帰は修正・再検証する。検証対象のソース・設定を固定して証跡を対応させる |
| コミット時 | 必要な検証・レビュー・仕様更新が揃ったら、別機能や全体整理の完了を待たず、許可された単位をコミットする。対象が別の未コミット/未追跡ファイルやローカル専用設定に依存せず成立することも確認する。未完成の大きな差分から事後的に一部だけを選ぶ運用より、着手自体を小さく分ける。後続の大量変更までビルド・動作を回復できない範囲をまとめて進めることは禁止する |
| 滞留の確認 | 単位の終了時・別変更の着手前・原則30〜60分の継続作業時に、所有する未コミット/未追跡差分、未完了単位数、継続時間、依存と検証/許可待ちを確認する。膨張・長期化した場合は追加着手より分割・動作回復・検証・コミットを優先する。時間経過は見直しの契機であり、コミット条件を省く理由にはしない |
| 保留と並行作業 | 質問・環境・検証/許可待ちは理由・担当・対象差分・再開条件を残し、保留分も未完了として数える。独立作業へ進む場合は所有と作業領域を分け、親/主担当が保留を含む進行中単位の上限と再開・回収順を管理する。単位の新設や担当の増加で未完了の滞留が増える場合は、既存単位を閉じることを先に行う |

ビルド・最低限の動作確認は部分工程のコミット条件であり、必要な回帰・E2Eや製品story全体の受入条件を維持する。部分工程のコミット・main統合と製品機能の完成を分ける。スキル/文書だけの変更は形式・参照・指示の整合を検証する。差分・index保護と単一実行者は[efficient-work](../../.agents/skills/efficient-work/references/実行管理と指示更新.md#統合とコミットの単一実行者)に従い、mainへのmerge許可・保留は親/主担当が管理する。

### 実サービスを使う検証の費用制約

- 単体・結合・Worker/DO・端末間契約・UI・音声E2Eの通常検証は、ローカルの代替provider・fixture・mockを使用する。通常検証とCIの接続先・資格はローカルfixtureに固定し、実Cloudflareへの接続は次項の明示実行で行う。
- 実Cloudflareを使う検証は、単体・結合を含む必要なローカル検証がすべて成功し、失敗・未実行・skipがなく、検証対象のソースと設定が一致することを確認した後に限る。原因調査と設定組合せの検証はローカル環境で閉じる。
- 実サービスの検証を既定の自動実行から分離し、目的・対象・最大人数・最大時間・最大回数を決めた明示実行にする。短い疎通から段階的に進め、再接続・retry・polling・反復は目的と上限を定め、判断に必要な証拠が得られた時点で試行を終える。実HTTP認証確認と媒体/SFU/TURN確認は区別する。
- 検証終了・失敗・timeoutで、この検証が作ったsession・channel・TURN資格等を回収する。費用・利用量を記録し、上限や停止条件に達した場合は追加試行を止める。金額の上限は参加者秒に加えて実利用量・単価・回収結果で確認する。
- 開発用の既定接続値はDebugの手動試用に限定する。Release・Archive・隔離検証には専用の資格境界を適用し、unit/UI/音声E2Eにはfixture資格を使う。実資格のログ・検証レポート・Gitへの出力は禁止する。
- GitHub連携のCloudflare buildも費用対象として扱い、実サービス検証の起動対象をサーバー関連の監視pathまたは明示実行へ絞る。本番用CIと試用用の入口はそれぞれの役割を維持する。

### VS Code でのテスト実行環境（macOS）

- `xcodebuild` や `xcresulttool` は、`xcode-select -p` が `CommandLineTools` を向いていると UI テスト実行や結果解析に失敗することがある。
- Xcode本体がインストール済みでも、向き先が `CommandLineTools` のままだと同様に失敗するため、テスト実行時は Xcode本体の Developer ディレクトリを明示する。
- 原則として、環境全体を変更する `sudo xcode-select -s ...` ではなく、まずはその場限りの `DEVELOPER_DIR` を使う。

#### 推奨手順

- Xcode本体の場所を確認する。
```bash
ls /Applications | rg 'Xcode'
```

- 現在の向き先を確認する。
```bash
xcode-select -p
```

- `DEVELOPER_DIR` を一時指定してテストを実行する。
```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcodebuild test \
  -project RideIntercom.xcodeproj \
  -scheme RideIntercom \
  -destination 'platform=macOS'
```

- `xcresulttool` を使うときも同じ `DEVELOPER_DIR` を明示する。
```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcrun xcresulttool get test-results summary --path <path-to.xcresult>
```

- `<path-to.xcresult>` は通常 `~/Library/Developer/Xcode/DerivedData/.../Logs/Test/` 配下に生成される。

#### 恒久対応が必要な場合

- ローカル環境を常に Xcode本体へ向けたい場合のみ、明示的に切り替える。
```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

- 向き先変更後は、`xcode-select -p` で確認してから `xcodebuild test` を再実行する。

## プラットフォーム共通化

- macOSとiOSの処理は、可能な限り同一の実装経路を通す。
- 最新APIでも共通化できない限定部分のみ抽象化し、OS差分を最小化する。
- ViewModelロジック、画面構造、状態管理、アクセシビリティIDは共通化する。
- OS依存点は抽象境界へ集約し、実処理は共通の契約を使う。
- 音声処理と通信処理のフロー全体はパッケージライブラリ化で共通化し、改善の横展開を可能にする。

## 抽象化設計原則

- 抽象化の目的は、OS差分や通信方式、その他の差分の吸収だけでなく、機能改善を全プラットフォームへ同時展開できる構造を維持することに置く。
- 現時点の主要な境界は「OS依存API」「コーデック差分」「通信方式差分」とする。将来の要件で新たな差分軸が見つかった場合は、同じ原則で境界を追加する。
- 境界を追加する条件は、共通フローを崩さずに差分を隔離でき、重複削減・変更容易性・テスト容易性のいずれかを明確に改善できることとする。
- 音声処理・通信処理ともに、入出力点を除いた中核フローは単一の設計として維持する。
- 抽象化は重複削減・変更容易性・テスト容易性の向上を根拠として、必要な範囲へ導入する。

## UI・UX方針

GUIの新規実装・変更・リファクタリングでは、[Scott HurffのUI Stack](https://www.scotthurff.com/posts/why-your-user-interface-is-awkward-youre-ignoring-the-ui-stack/)を設計・検証の観点として適用する。通常表示だけでなくIdeal・Empty・Error・Partial・Loadingの5状態と、その間の遷移を対象画面ごとに確認する。適用する状態・成立条件・表示・可能な操作・復帰先を画面仕様に残し、該当しない状態は理由を示す。

具体的な表示と本プロジェクトの状態種別との対応は[デザインシステムのUIスタック](../design/デザインシステム.md#uiスタック)を正本とする。変更対象に関係する状態と遷移を再現して検証し、既存の回帰保護と小さな検証済みコミットを維持する。重大不確実性の先行検証とコア優先の順序を保ち、必要な状態を実装する範囲へ絞る。


- UIはSwiftUIのネイティブコントロールを標準とし、必要な機能は他のネイティブ標準UIで補う。この開発で扱うUIはこれらの標準部品に限定する。
- UIは最新のApple Human Interface Guidelinesに準拠し、実装前にAccessibility、Layout、Iconsの該当箇所を確認する。
- iOSはHIG準拠を必須とし、標準SwiftUIコンポーネント、safe area、Dynamic Type、VoiceOver、ライト/ダークモード、Reduce Motionを前提に設計する。
- macOSでは操作環境の特性に合わせ、同一の構造・状態管理・アクセシビリティIDを維持しながら、ウィンドウサイズ変更、キーボード操作、VoiceOver、macOSのクリック対象サイズ、重要操作をウィンドウ内で安定して操作できる配置を最低条件として満たす。
- すべてのアイコン単体ボタンにVoiceOverで意味が分かるaccessibility labelを付け、状態を持つ操作にはaccessibility valueも付ける。accessibilityIdentifierはUIテストで使い、VoiceOverには専用のlabel/valueを設定する。
- 状態表示は色に加えて、テキスト、SF Symbols、accessibility label/valueでも同じ意味を伝える。音量メーター、通信状態、ミュート状態、エラー状態は必ず色以外でも判別可能にする。
- 主要操作のタップ/クリック対象はiOSで44pt以上、macOSで28pt以上を下限とし、隣接コントロールには操作対象を識別しやすい余白を確保する。
- 文字サイズに追随する高さと必要な複数行表示を使う。長い診断値はDiagnosticsへ配置する。
- レイアウトはsafe areaとシステム余白に従い、主要操作にはシステム標準の適切な幅と余白を設ける。iPhone portrait/landscape、iPad regular width、macOS window resizeで各操作の表示領域と操作領域が確保されていることを確認する。
- UIアイコンはSF Symbolsを優先し、outline/fillなど用途に合うvariantを選ぶ。アプリアイコン・ロゴ・商標的表現には用途に適した独自素材を使う。
- Call画面は通話に必要な状態と操作に限定し、TX/RX/JIT、ID、groupHash、transport詳細などの診断情報はDiagnosticsへ集約する。
- SettingsはForm/Sectionなどプラットフォーム標準の設定UIに寄せ、Audio I/O、Codec、Audio Checkなどを意味単位で分ける。
- 体験を最優先し、UIの使いやすさと音声品質を継続的に改善する。
- レイテンシ最小化、ノイズ低減、VAD調整など、体験に直結する要素を優先する。
- 参照: https://developer.apple.com/design/human-interface-guidelines/accessibility
- 参照: https://developer.apple.com/design/human-interface-guidelines/layout
- 参照: https://developer.apple.com/design/Human-Interface-Guidelines/sf-symbols

## UIテスト方針

- UIテストは1回の起動で複数ケースを実行できる構成を基本とし、状態の初期化が必要な境界で再起動する。
- テスト安定性と実行時間を継続的に改善する。

## 技術選定方針

- Swiftバージョンはプロジェクトで利用可能な最新安定版を使う。
- 現行の最低対応OSはiOS/iPadOS/macOS/watchOS 27.0とする。Xcode project、各local Swift Package、同梱binary、build・検証script、現行の仕様・操作文書で最低版を一致させる。projectで明示的に有効な他のApple platformも同じ最低版を使う。
- 今後は可能な限り現行と直前のメジャーOSまでの最大2世代を支援する。最低版を上げるときはすべての対象設定・依存binary・検証入口・現行文書を同じ作業単位で更新し、下位OSだけのavailability分岐、fallback、劣化経路を整理する。OS内のAPI実装差ではなく、iOS/macOS/watchOS等のplatform差、権限、機器・hardware能力による実際の差は必要な境界として維持する。
- 現在の開発段階は現行OS・アプリ版・API・データ形式を基準とし、旧版専用の互換処理は整理する。プラットフォーム固有の必要な処理分離とは区別する。
- 将来の更新でマイグレーションが発生する前提とする。将来必要になるデータ・設定・通信契約等の移行は、変更時に対象・適用条件・失敗時の復旧を定める。将来の移行でも利用者データを保護し、対象・条件・復旧を確認した操作だけを行う。利用者データの無断削除は禁止する。
- Swift Concurrencyを積極採用し、既存の非同期処理も可能な限りasync/awaitへ移行する。
- SwiftUIを積極採用し、既存UIKitコードも可能な限り置き換える。

## 音声処理方針

- 全ての音声処理はパッケージライブラリ化して共通化し、改善の横展開を可能にする。
- AVAudioEngineなどApple標準の音声エフェクトとVADを優先利用し、独自実装は最小限に留める。
- 音声品質は実運用環境（実マイク・実スピーカー）での結果を最優先評価とする。

### コーデック方針

- 音声コーデックは差し替え可能な設計にする。
- AudioCodecIdentifierやAudioEncodingなどの抽象化を導入する。
- AVFoundationのハードウェアアクセラレーションが使えてレイテンシの低いコーデックを優先候補とする。
- 将来の追加・変更でも既存の実音声TDD経路を維持する。

## 通信処理方針

- 全ての通信処理はパッケージライブラリ化して共通化し、改善の横展開を可能にする。
- ルーティング、接続確立、暗号化、転送などの通信処理は、実装の詳細に依らず同じ設計・同じ呼び出し方で使えるようにする。
- 通信方式は差し替え可能な設計や自動でのハンドオーバーを可能にする設計にする。
- 通信品質は実運用環境での結果を最優先評価とする。

### サーバー機能

- サーバー機能は cloudflare の無料範囲で構築することを検討する。

## 実装判断の優先順位

要求者の目的に対し、採否や後続設計を覆す重大な不確実性を最小の実経路で先に検証し、観測から採用・簡素化・代替・不採用を判断する。周辺実装や設計整理は、その前提の検証結果を得てから進める。コア優先と「実装と検証」の変更前後の回帰保護を両立する。

- 実運用で安定して動作する実装を優先する。
- 現在の契約を基準に実装し、互換性対応は利用者が指定した範囲で扱う。
- シンプルさと将来拡張性を優先し、必要な責務を最小の構造で表す。
- 本番機能・抽象化は製品の責務に必要な範囲へ絞る。回帰保護に必要なテスト・fixture・Test Supportの追加は「実装と検証」に従って行う。
- 目的に必要なコードと構造へ絞り、不要になったものは削除する。
- 電池消費・通信量は提供機能に対する無駄を減らし、機能に必要な消費は品質・費用との釣り合いで判断する。削減と必要な機能の両立が難しい場合は、トレードオフと選択肢を整理して利用者の指示を仰ぎ、回答待ちの間は独立した作業を続ける。

### 設計判断の補足

- 設計判断では「短期の安定運用」と「中長期の拡張性」を両立させる。
- まず単純で検証可能な実装を成立させ、その後に抽象境界を段階的に拡張する。
- 抽象化の導入や変更は、テストで保護された経路を維持できることを必須条件とする。
- 責務・差分・テスト容易性に寄与する最小の抽象化を導入する。
- 常に実装のシンプルさとコード量の少なさ、可読性の高さと保守のしやすさを優先する。
- コード量を増やす変更は、機能維持・重複削減・テスト容易性のいずれかに直接寄与する場合のみ許可する。
- 既存コードの小さな修正で成立する場合は、変更対象を既存ファイル・型・protocol・adapterの必要箇所に限定する。
- 抽象化を追加する前に、既存の抽象・Port・Factory・Test Supportの適用可能性を確認する。
- 新規経路を追加した場合は、同じ変更内で不要になった旧経路、重複実装、一時的な補助コードを削除する。
- 同じ処理は積極的に共通化し、重複する処理は共通の経路へ集約する。
- 拡張点・設定・helper・fallback分岐は、現在の具体的な要求と利用経路を根拠に採用する。
- 本番コードの抽象化は製品の責務を基準にし、必要なテスト専用実装はTest Supportへ閉じ込める。
- 実装完了時は、追加行数・追加型数・追加ファイル数が目的に対して最小かを確認し、過剰な構造を削る。

<a id="一時物を残さない開発"></a>

### 作業完了時の整理と回収

作業の完了には後片付けを含める。成功・失敗・中断・案の不採用のいずれでも、その作業で不要になったものを回収し、担当交代や次の課題へ移る前に回収を閉じる。必要な検証証跡と再利用する資源は保ち、失敗や残課題の記録は保持する。 現在の参照先・明示した再利用目的がない一時物は、用途終了を確認して削除する。

| 対象 | 作成・維持と片付けの規則 |
|---|---|
| 配置根拠のない増設禁止 | 対象を問わず、必要性・責務・命名・配置の根拠を説明できないディレクトリやファイルの作成は禁止する。Xcode・言語・frameworkの標準と、既存のドメイン・依存境界・リポジトリの配置規則を先に確認する。一時的な都合や抽象化そのものを理由に汎用の格納場所・層・設定を増やさず、既存構造で扱う。既存の不適切な配置も対象範囲内で統合・移動・削除し、参照・target所属・文書・検証を同時に更新する。判断理由は既存規則で説明し、非自明な例外だけを既存の適切な仕様・コメントへ残す。説明は既存の適切な仕様・コメントへ集約する |
| 設定の増設禁止 | 設定管理や一時的な都合を理由に、独自の設定ディレクトリ・設定ファイル・Build Configurationの増設は禁止する。Xcode標準の既存Build Settings・scheme・Test Planを使い、標準の形式と配置に従う。役割・配置規則のない`Configuration`等の格納場所や、採番用target・別カウンタの追加は禁止する。不要になった既存設定は参照と生成物まで同じ作業で整理する |
| ビルド構成 | Xcode標準の構成とOSごとの出力を基準に、目的上必要な組合せだけを維持する。構成は目的に必要な最小の組合せへ揃え、既存scheme・Test Plan・テスト起動引数で表せる条件はそこへ置く。配布と検証の資格・保存先の分離は維持する |
| 一時コード・設定 | 調査用コード、fixtureの仮配線、フラグ、xcconfig、scheme、Test Plan、スクリプトは用途が終わった時点で削除する。恒久的な検証として採用するものだけを必要最小限で残し、不要な構成を消す際はproject・スクリプト・テスト・現行手順の参照も同時に除く |
| 生成物・一時ファイル | 不要になった構成のbuild生成物、診断用xctestrun、profile、コピー、重複ログ、作業所有の一時ファイルを確認して削除する。DerivedDataは標準の場所で再利用し、不要な生成物の作成元も同時に整理する。通常使用中のbuild cacheは再利用する |
| 実行資源・作業領域 | 自分の検証用process・session・lockを終了時に回収し、Simulatorとworktreeは上記の再利用・統合規則に従って整理する。実行中・所有不明・他作業の資源や未統合差分は、無断で停止・削除することは禁止する |
| 証跡と保留 | 判断と再現に必要なsource差分・条件・結果だけを既存の検証記録へ残す。依存する実行が続いている等の理由で片付けを保留する場合は、対象・残す理由・担当・削除する時点を既存の残課題または引継ぎへ記録する。保留には再開・削除の時点を定める |
| 完了確認 | commit・引渡し前に差分と未追跡ファイル、設定の参照、所有生成物・稼働資源を確認する。不要物の除去と影響する構成・検証入口の確認までを同じ作業単位で閉じる。対象と参照の状態を確認して片付け完了を記録する |
