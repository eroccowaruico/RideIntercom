## 品質と開発プロセス

### ブランチ運用

- 継続開発と統合の基準は`main`一本とし、常設の`dev`との二重管理は行わない。
- PR運用は行わず、検証済みの変更をmainへコミットして直接pushする。
- 作業を隔離する必要がある場合だけmainから短期の作業ブランチを作り、検証後はmainへ統合する。
- 長い作業でも、検証が完了した作業の区切りごとにmainへ統合してpushし、リモートのmainとコミットが一致することを確認する。未検証の変更や他の作業の未コミット変更を一緒に含めない。
- 過去作業の保全ブランチや検証記録用worktreeは開発先として使わず、未統合の作業を確認せずに削除しない。
- 隔離作業は区切りごとにmainへ統合し、不要なworktreeを整理する。削除前に未コミット差分・未追跡ファイルの統合、稼働process、残す検証証跡を確認する。実装済みの契約は仕様へ移し、課題一覧には残作業を保持する。 保全する旧projectやpackage sourceは、Xcodeの同期フォルダから開発用のproject／packageとして再検出されないアーカイブ形式で保存する。
- 継続作業では共通正本に加え、対象機能の現行仕様・残課題・必要な証跡だけを読む。引継ぎには現在の作業領域・基準commit・未統合差分・生存中の検証handle・次の完了条件を絞って残し、過去経緯の全文を毎回読み直す前提にしない。

### 公開バージョンとビルド番号

- 公開バージョンは可能な限りSemantic Versioningの`major.minor.patch`を適用する。利用者に公開する機能・招待や保存形式・通信契約の互換性を基準に、非互換変更はmajor、互換性を保つ機能追加はminor、不具合修正はpatchを変更する。major変更時はminor・patch、minor変更時はpatchを0に戻す。
- 公開バージョンの変更は利用者の明示指示に従い、ビルド・Archive・アップロードを理由に自動変更しない。
- ビルド番号はXcode標準の`CURRENT_PROJECT_VERSION`、公開バージョンは`MARKETING_VERSION`を使い、projectの共通設定をApp・Widget・Watch・テスト対象が継承する。通常ビルド・Run・Test・Archiveを含む全scheme・全構成でビルド番号を自動的に進める。採番専用の設定ファイル・別カウンタ・常設lockファイルは設けない。
- Xcode標準のBuild後処理とAppleの`agvtool`で次回用の番号を更新する。同じビルドの開始に更新が間に合うことや、厳密な連番を必須にしない。保存先の見直しを自動インクリメントの廃止へ読み替えず、「通常ビルドでは自動変更しない」という制限は設けない。専用の事前コマンドやXcodeの終了を必要としない。
- 同一ビルド・Archive内のApp・Widget・Watchの番号を一致させる。成果物の番号とBuild後処理で進んだ次回用設定値を区別する。配布時は既存ビルドと重複しない番号を確認し、Organizerが配布時に番号を管理する場合もArchive内の番号と配布物の番号を区別して記録する。
- 並行作業・実行中のアプリやビルドを停止せずに変更・検証する。番号は全構成と既知の配布・Archiveにある最新最大値を基準に進め、古い設定やcheckoutの値へ戻さない。設定の欠落・破損を低い番号への自動初期化で補わない。別checkoutや別Macからの配布は担当者間で番号を共有する。
- 配布用`CFBundleVersion`はAppleの規定する数字とピリオドの形式を使い、16進表記（`0x`や`A`〜`F`）を入れない。Apple OSの英字入りbuild-versionは別の識別子である。旧公式資料にある開発段階の`a`・`b`・`d`・`fc`接尾辞も16進数ではなく、製品配布時には除く。SemVerの`+build`も入れない。Xcodeでの設定と配布手順は[開発環境](../development/開発環境.md)を参照する。

### 実装と検証

- 開発はTDDを前提とする。
- 実マイクや実スピーカーに依存しない音声TDDを維持し、音声品質・安定性・拡張性を確保する。
- 接続性や暗号化などの非音声処理も、可能な限りTDDで実装する。
- テストは記述だけで終わらせず、必ず実行して成功させる。
- App実装を行う際にパッケージライブラリの修正は許可しない。同様に、パッケージライブラリの修正時にApp実装の変更も許可しない。
- 常にビルドエラー、ワーニング、テストエラーがない状態を維持する。
- パッケージライブラリは独立性を保ち、Appの都合は無視して、OS差異や通信方式差異だけでなく継続可能な準異常系もいい感じに処理を吸収する設計して、実装の詳細に依らず環境差異のある呼び出しは全て無視しつつ同じ設計・同じ呼び出し方で使えるようにする。
- パッケージライブラリ修正時に互換性維持は優先しない。typealias / thin wrapper / 旧API温存は入れない。
- パッケージライブラリは必要な情報は実行時の確認情報含めて必要な情報は全てリアルタイムで渡せて、必要な設定は受け取れるようにする。
- パッケージライブラリごとの責務を再定義し、App都合ではなく通話音声基盤として整理する。
- Appから見たパッケージライブラリの不足を単純に充足することはしないが、そもそも不足があるというのは、パッケージの設計に課題があるということなので、設計から見直して根本解決する
- Appがやるべきことは UI、設定入力、package lifecycle 呼び出しだけにする。

### 実サービスを使う検証の費用制約

- 単体・結合・Worker/DO・端末間契約・UI・音声E2Eの通常検証は、ローカルの代替provider・fixture・mockを使用する。実Cloudflare資格を自動注入せず、標準のテストやCIから実SFU/TURNへ接続しない。
- 実Cloudflareを使う検証は、単体・結合を含む必要なローカル検証がすべて成功し、失敗・未実行・skipがなく、検証対象のソースと設定が一致することを確認した後に限る。ローカル失敗の原因調査や大量の設定組合せを実サービスへ持ち込まない。
- 実サービスの検証を既定の自動実行から分離し、目的・対象・最大人数・最大時間・最大回数を決めた明示実行にする。短い疎通から段階的に進め、不要な再接続、無制限リトライ、定期polling、同じ確認の反復を避ける。実HTTP認証確認と媒体/SFU/TURN確認は区別する。
- 検証終了・失敗・timeoutで、この検証が作ったsession・channel・TURN資格等を回収する。費用・利用量を記録し、上限や停止条件に達した場合は追加試行を止める。アプリの参加者秒上限を金額の厳密な上限とは扱わない。
- 開発用の既定接続値はDebugの手動試用に限定する。Release・Archive・隔離されたローカル検証用buildへ含めず、unit/UI/音声E2Eで保存済み実資格を流用しない。資格をログ・検証レポート・Gitへ出力しない。
- GitHub連携のCloudflare buildも費用対象として扱い、サーバー検証に不要なApp・文書だけの変更で実サービス検証を起動しない。監視pathや明示的なbuild省略を使い、本番用CIを試用用へ置換しない。

### VS Code でのテスト実行環境（macOS）

- `xcodebuild` や `xcresulttool` は、`xcode-select -p` が `CommandLineTools` を向いていると UI テスト実行や結果解析に失敗することがある。
- Xcode本体がインストール済みでも、向き先が `CommandLineTools` のままだと同様に失敗するため、テスト実行時は Xcode本体の Developer ディレクトリを明示する。
- 原則として、環境全体を変更する `sudo xcode-select -s ...` ではなく、まずはその場限りの `DEVELOPER_DIR` を使う。

#### 推奨手順

- Xcode本体の場所を確認する。
```bash
ls /Applications | rg 'Xcode'
```

- 現在の向き先を確認する。
```bash
xcode-select -p
```

- `DEVELOPER_DIR` を一時指定してテストを実行する。
```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcodebuild test \
  -project RideIntercom.xcodeproj \
  -scheme RideIntercom \
  -destination 'platform=macOS'
```

- `xcresulttool` を使うときも同じ `DEVELOPER_DIR` を明示する。
```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcrun xcresulttool get test-results summary --path <path-to.xcresult>
```

- `<path-to.xcresult>` は通常 `~/Library/Developer/Xcode/DerivedData/.../Logs/Test/` 配下に生成される。

#### 恒久対応が必要な場合

- ローカル環境を常に Xcode本体へ向けたい場合のみ、明示的に切り替える。
```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

- 向き先変更後は、`xcode-select -p` で確認してから `xcodebuild test` を再実行する。

## プラットフォーム共通化

- macOSとiOSの処理は、可能な限り同一の実装経路を通す。
- 最新APIでも共通化できない限定部分のみ抽象化し、OS差分を最小化する。
- ViewModelロジック、画面構造、状態管理、アクセシビリティIDは共通化する。
- OS依存点は抽象化して、実処理に持ち込まない。
- 音声処理と通信処理のフロー全体はパッケージライブラリ化で共通化し、改善の横展開を可能にする。

## 抽象化設計原則

- 抽象化の目的は、OS差分や通信方式、その他の差分の吸収だけでなく、機能改善を全プラットフォームへ同時展開できる構造を維持することに置く。
- 現時点の主要な境界は「OS依存API」「コーデック差分」「通信方式差分」とする。将来の要件で新たな差分軸が見つかった場合は、同じ原則で境界を追加する。
- 境界を追加する条件は、共通フローを崩さずに差分を隔離でき、重複削減・変更容易性・テスト容易性のいずれかを明確に改善できることとする。
- 音声処理・通信処理ともに、入出力点を除いた中核フローは単一の設計として維持する。
- 抽象化は増やすこと自体を目的にせず、重複削減・変更容易性・テスト容易性の向上が確認できる場合のみ導入する。

## UI・UX方針

- 原則Swift UIのネイティブコントロールのみを使用し、どうしても必要な場合のみその他ネイティブの標準UIを利用する。カスタムUIは使用しない。
- UIは最新のApple Human Interface Guidelinesに準拠し、実装前にAccessibility、Layout、Iconsの該当箇所を確認する。
- iOSはHIG準拠を必須とし、標準SwiftUIコンポーネント、safe area、Dynamic Type、VoiceOver、ライト/ダークモード、Reduce Motionを前提に設計する。
- macOSはiOSの単純移植で済ませず、同一の構造・状態管理・アクセシビリティIDを維持しながら、ウィンドウサイズ変更、キーボード操作、VoiceOver、macOSのクリック対象サイズ、下端に重要操作を固定しない配置を最低条件として満たす。
- すべてのアイコン単体ボタンにVoiceOverで意味が分かるaccessibility labelを付け、状態を持つ操作にはaccessibility valueも付ける。accessibilityIdentifierはUIテスト用であり、VoiceOver文言の代替にしない。
- 状態表示は色だけに依存せず、テキスト、SF Symbols、accessibility label/valueでも同じ意味を伝える。音量メーター、通信状態、ミュート状態、エラー状態は必ず色以外でも判別可能にする。
- 主要操作のタップ/クリック対象はiOSで44pt以上、macOSで28pt以上を下限とし、隣接コントロールには誤操作を避ける余白を確保する。
- 文字サイズ変更で表示が切れないよう、固定高さを避け、必要な箇所は複数行表示とする。長い診断値は通常UIに混ぜずDiagnosticsへ分離する。
- レイアウトはsafe areaとシステム余白に従い、端に張り付いた全幅ボタンを避ける。iPhone portrait/landscape、iPad regular width、macOS window resizeで操作不能や重なりが起きないことを確認する。
- UIアイコンはSF Symbolsを優先し、outline/fillなど用途に合うvariantを選ぶ。SF Symbolsはアプリアイコン、ロゴ、商標的表現として使わない。
- Call画面は通話に必要な状態と操作に限定し、TX/RX/JIT、ID、groupHash、transport詳細などの診断情報はDiagnosticsへ集約する。
- SettingsはForm/Sectionなどプラットフォーム標準の設定UIに寄せ、Audio I/O、Codec、Audio Checkなどを意味単位で分ける。
- 体験を最優先し、UIの使いやすさと音声品質を継続的に改善する。
- レイテンシ最小化、ノイズ低減、VAD調整など、体験に直結する要素を優先する。
- 参照: https://developer.apple.com/design/human-interface-guidelines/accessibility
- 参照: https://developer.apple.com/design/human-interface-guidelines/layout
- 参照: https://developer.apple.com/design/Human-Interface-Guidelines/sf-symbols

### デザインシステムの利用

- AppleのHIGに準拠したUIを構築するだけでなく統一感を持たせるため、デザインシステムのアイコン、色、テキストスタイルの規約を遵守する。
- デザインシステム: docs/design

## UIテスト方針

- UIテストは毎回アプリを再起動せず、1回起動で複数ケースを実行できる構成を基本とする。
- テスト安定性と実行時間を継続的に改善する。

## 技術選定方針

- Swiftバージョンはプロジェクトで利用可能な最新安定版を使う。
- OSバージョン差への対応が必要な機能は、原則として対象のApple OSのバージョン27以降のみを支援する。下位OSのための代替API・機能縮退・互換分岐は設けない。当面Android互換は考慮しない。
- 現在の開発段階では後方互換機能はすべて不要とし、旧OS・旧アプリ版・旧API・旧データ形式のためだけの互換処理を追加・維持しない。プラットフォーム固有の必要な処理分離とは区別する。
- 将来の更新でマイグレーションが発生する前提とする。将来必要になるデータ・設定・通信契約等の移行は、変更時に対象・適用条件・失敗時の復旧を定める。現在の後方互換不要という方針を、将来の移行不要や利用者データを無条件に消してよいという意味にしない。
- Swift Concurrencyを積極採用し、既存の非同期処理も可能な限りasync/awaitへ移行する。
- SwiftUIを積極採用し、既存UIKitコードも可能な限り置き換える。

## 音声処理方針

- 全ての音声処理はパッケージライブラリ化して共通化し、改善の横展開を可能にする。
- AVAudioEngineなどApple標準の音声エフェクトとVADを優先利用し、独自実装は最小限に留める。
- 音声品質は実運用環境（実マイク・実スピーカー）での結果を最優先評価とする。

### コーデック方針

- 音声コーデックは差し替え可能な設計にする。
- AudioCodecIdentifierやAudioEncodingなどの抽象化を導入する。
- AVFoundationのハードウェアアクセラレーションが使えてレイテンシの低いコーデックを優先候補とする。
- 将来の追加・変更でも既存の実音声TDD経路を維持する。

## 通信処理方針

- 全ての通信処理はパッケージライブラリ化して共通化し、改善の横展開を可能にする。
- ルーティング、接続確立、暗号化、転送などの通信処理は、実装の詳細に依らず同じ設計・同じ呼び出し方で使えるようにする。
- 通信方式は差し替え可能な設計や自動でのハンドオーバーを可能にする設計にする。
- 通信品質は実運用環境での結果を最優先評価とする。

### サーバー機能

- サーバー機能は cloudflare の無料範囲で構築することを検討する。

## 実装判断の優先順位

- 実運用で安定して動作する実装を優先する。
- 指示がない限り後方互換性は考慮しない。
- シンプルさと将来拡張性を優先し、不要な複雑性を増やさない。
- テストのための実装は許可しない。
- 不要なコードや構造は追加せず、必要なものだけを追加し、不要になったものは削除する。
- 電池消費・通信量は提供機能に対する無駄を減らし、機能に必要な消費まで一律に禁止しない。削減と必要な機能の両立が難しい場合は、トレードオフと選択肢を整理して利用者の指示を仰ぎ、回答待ちの間は独立した作業を続ける。

### 設計判断の補足

- 設計判断では「短期の安定運用」と「中長期の拡張性」を両立させる。
- まず単純で検証可能な実装を成立させ、その後に抽象境界を段階的に拡張する。
- 抽象化の導入や変更は、テストで保護された経路を維持できることを必須条件とする。
- 無駄な中間層や複雑なパターンは避け、必要な抽象化だけを導入する。
- 常に実装のシンプルさとコード量の少なさ、可読性の高さと保守のしやすさを優先する。
- コード量を増やす変更は、機能維持・重複削減・テスト容易性のいずれかに直接寄与する場合のみ許可する。
- 既存コードの小さな修正で成立する場合は、新規ファイル・新規型・新規protocol・新規adapterを追加しない。
- 抽象化を追加する前に、既存の抽象、Port、Factory、Test Supportで代替できないか確認する。
- 新規経路を追加した場合は、同じ変更内で不要になった旧経路、重複実装、一時的な補助コードを削除する。
- 同じ処理は積極的に共通化し、重複コードを増やさない。
- 「将来使うかもしれない」だけの拡張点、設定、helper、fallback分岐は追加しない。
- テストのためだけに本番コードの抽象化を増やさず、必要なテスト専用実装はTest Supportへ閉じ込める。
- 実装完了時は、追加行数・追加型数・追加ファイル数が目的に対して最小かを確認し、過剰な構造を削る。

## 開発環境の要求

| 項目 | 要求 |
|---|---|
| エディタの必須要件 | VS CodeとXcodeの両方の利用を必須の要件とする。両方から同じ実ファイルを編集し、同じビルド・検証入口を使用できること |
| AIのビルド・テスト・自動化 | AIが行うすべてのビルド・テストは、同じソース・設定・fixture・前提条件でXcodeのUIから再現できること。AIが利用する自動化も、XcodeのUIからの操作を起点としてすべての機能が動作すること。CLIだけで成立する実装や、UI経由では実行されない処理、CLI専用の事前操作を必要とする構成にしない。CLIとUIで処理・検証条件・判定を共通化し、UIからの起動やビルド成功だけを同じテスト・自動化の再現確認に代えない |
| ファイル表示 | Xcodeは各編集フォルダを同期参照し、その内部の新規項目に追随する。新しいroot直下の項目は標準のAdd Filesで参照を追加する。project自身を含むrootの再帰同期や自己project参照は置かない。VS Codeはroot全体を開き、両エディタともGit追跡済みかどうかを表示条件にしない |
| ビルド分離 | 全体を閲覧するための参照をAppのcompile / resource copyへ混入させないこと |
| ビルド場所 | mainの通常作業フォルダにある実projectからBuild・Run・Test・Archiveし、Xcode既定のDerivedDataを使う。projectコピー・別worktree・一時フォルダを通常buildの入口にせず、専用DerivedDataへ切り替えない。検証用データ・fixture・ログの隔離は維持すること |
| 継続性 | 必要な同期フォルダの削除・閲覧用参照のtargetへの誤所属・再帰同期による自己projectの再検出を自動検出すること。画面確認と構造検査を区別すること |
| 開発リソースの節約 | Simulator・検証用プロセス・build cacheは作成前に既存資源を確認して再利用する。新規Simulatorが必要な場合も、過去の専用検証端末を確認し、使わない重複・非対応端末を削除してから作成する。実行中や所有不明の端末・他作業のプロセスは停止・削除しない。通常検証と音声E2Eで資源管理を共通化し、管理記録の消失でも端末を増やし続けない |
| Xcode単独の操作 | Xcodeのみで編集・Build・Run・Test・Archiveを行い、OrganizerからApp Store／TestFlightへ提出できる構成と分かりやすい手順を継続して保つ。CLI専用の事前操作を必須にせず、テスト用の保存先・fixtureと通常実行・配布を区別する。Apple側のアカウント・署名・商品設定は別途必要とする |
| 正本 | [開発環境](../development/開発環境.md)に設定・操作を記載し、検証結果・確認待ちはvalidationへ分けること |

### 一時物を残さない開発

作業の完了には後片付けを含める。成功・失敗・中断・案の不採用のいずれでも、その作業で不要になったものを回収し、担当交代や次の課題へ放置しない。必要な検証証跡と再利用する資源は保ち、片付けのために失敗や残課題を消さない。 現在の参照先・明示した再利用目的がない一時物は、別の場所への移動やarchiveだけで済ませず削除する。

| 対象 | 作成・維持と片付けの規則 |
|---|---|
| 配置根拠のない増設禁止 | 対象を問わず、必要性・責務・命名・配置の根拠を説明できないディレクトリやファイルを作らない。Xcode・言語・frameworkの標準と、既存のドメイン・依存境界・リポジトリの配置規則を先に確認する。一時的な都合や抽象化そのものを理由に汎用の格納場所・層・設定を増やさず、既存構造で扱う。既存の不適切な配置も対象範囲内で統合・移動・削除し、参照・target所属・文書・検証を同時に更新する。判断理由は既存規則で説明し、非自明な例外だけを既存の適切な仕様・コメントへ残す。説明用の文書や設定をさらに増設しない |
| 設定の増設禁止 | 設定管理や一時的な都合を理由に、独自の設定ディレクトリ・設定ファイル・Build Configurationを増設しない。Xcode標準の既存Build Settings・scheme・Test Planを使い、標準の形式と配置に従う。役割・配置規則のない`Configuration`等の格納場所や、採番用target・別カウンタを追加しない。不要になった既存設定は参照と生成物まで同じ作業で整理する |
| ビルド構成 | Xcode標準の構成とOSごとの出力を基準に、目的上必要な組合せだけを維持する。テスト名・実行回・一時調査ごとに構成を増やさず、既存scheme・Test Plan・テスト起動引数で表せる条件はそこへ置く。配布と検証の資格・保存先の分離は維持する |
| 一時コード・設定 | 調査用コード、fixtureの仮配線、フラグ、xcconfig、scheme、Test Plan、スクリプトは用途が終わった時点で削除する。恒久的な検証として採用するものだけを必要最小限で残し、不要な構成を消す際はproject・スクリプト・テスト・現行手順の参照も同時に除く |
| 生成物・一時ファイル | 不要になった構成のbuild生成物、診断用xctestrun、profile、コピー、重複ログ、作業所有の一時ファイルを確認して削除する。DerivedDataの場所を増やす回避策や、不要な設定が生成物を再作成する状態を残さない。通常使用中のbuild cacheは再利用する |
| 実行資源・作業領域 | 自分の検証用process・session・lockを終了時に回収し、Simulatorとworktreeは上記の再利用・統合規則に従って整理する。実行中・所有不明・他作業の資源や未統合差分は、まとめて停止・削除しない |
| 証跡と保留 | 判断と再現に必要なsource差分・条件・結果だけを既存の検証記録へ残す。依存する実行が続いている等の理由で片付けを保留する場合は、対象・残す理由・担当・削除する時点を既存の残課題または引継ぎへ記録する。保留を恒久化しない |
| 完了確認 | commit・引渡し前に差分と未追跡ファイル、設定の参照、所有生成物・稼働資源を確認する。不要物の除去と影響する構成・検証入口の確認までを同じ作業単位で閉じる。記録の追記だけで片付け済みとしない |

## 品質と保守の受け入れ

| 要求 | 判断基準 | 具体化する文書 |
|---|---|---|
| 責務分離と差し替え可能性 | 責務を分離し、必要な差し替え境界を持つこと | [アーキテクチャ](../spec/アーキテクチャ.md)。動的plugin loaderは対象外 |
| 自動検証を繰り返せる | UIなし・UIあり・端末間契約を再実行できること | [自動検証](../development/自動検証.md)。実機と自動結果を区別 |
| 説明と操作が一致する | 要求 → 仕様 → source → manual → 検証をリンク | [文書案内](../README.md)。情報を保持して矛盾を修正 |

開発環境の構造検査と画面での確認を区別し、結果・確認待ちは[検証](../validation/README.md)で管理する。
