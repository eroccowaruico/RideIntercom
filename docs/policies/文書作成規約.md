# 文書作成規約

本書は文書・計画・要求管理の作り方を定める。アプリが利用者へ提供する価値と機能は[製品要求](../requirements/製品要求.md)、実装の制約は[開発方針](開発方針.md)へ分ける。

## 望ましい行動を示す書き方

本リポジトリの文書全体に適用する。規約・要求・計画・README・AGENTS.md等のエージェント入口・スキルと参照資料も、次の基準で記述・更新する。

| 記述の種類 | 書き方 |
|---|---|
| 通常の指針・優先順位 | 望ましい行動・選択・配置・完了状態を肯定形で具体的に示す。「何を、いつ、どの範囲で行うか」と判断根拠を記す。例: 「周辺を先に作らない」→「重大な不確実性を最小実装で先に検証する」 |
| 条件・未完了時の対応 | 適用条件と次の行動を示す。例: 「未検証で完了にしない」→「必要な検証と回帰が成功した範囲を完了とし、残りは未確認として記録する」 |
| 真の禁止事項 | 機密漏えい、無断のデータ破壊・権限拡大、検証結果の捏造など重大な害を防ぐ境界と、利用者が明示した禁止は「禁止」と明示する。対象・理由・適用範囲と、許可範囲内の代替行動を併記する。通常の好みや優先順位は上の指針として記す |
| 事実・仕様の境界・履歴 | 非対応、失敗、未実行、能力上の限界は事実として正確に記録する。過去の引用・証跡・コード例は意味と原文を保持する。否定形の解消と、事実や制約の変更を区別する |
| 表現変更の受入 | 変更前後で適用対象・必須/推奨の強さ・実行順序・数値と単位・例外・権限・完了条件を対照する。同じ状況で同じ判断になることを受入条件とし、曖昧さや情報差があれば補ってから反映する |
| 正本と参照 | 共通ルールは正本へ集約し、スキル・入口には担当する判断と必要な節への参照を置く。意味・強制力・条件・例外を保持して表現を整える |

## 記述規則

| 項目 | ルールと理由 |
|---|---|
| 基本ルール | [開発方針](開発方針.md)を適用する |
| 採番禁止 | ルール、要求、見出し、表の識別に採番ID・番号の付与は禁止する。識別には内容の分かる見出しを使い、参照の安定性を保つ |
| 表現 | 条件・対象・行動・完了状態が実装時に判断できる文で記述する |
| 図表優先 | 認識齟齬を防ぐため、仕様は図表を使う。特に画面・状態・設定は表を優先する |
| 文章の扱い | 仕様の構造と比較は図表で示し、背景や意図を文章で補足する |
| 詳細度 | 実装者が迷わないよう、背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点をできる限り詳しく説明する |

## プランの策定

- 要件を満たすための具体的な実装ステップを示す。
  - 実装の依存関係を明確にした上で、実装が円滑に進む順序や優先順位を明確にする。
- 経験や前提知識の少ない実装者やモデルでも、そのまま実装に入れる具体的な内容とステップを示す。
- 背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点などをできる限り詳細に説明する。
- プランは作業手順や指示だけではなく、設計書や仕様書のような形式で、実装者が完了条件を理解できるように記述する。
- 実装者が判断に迷わない、実装をストレートに進められる内容とする。
- プラン冒頭に指示内容と背景を記載する。修正時は特に指示がない限り既存の内容・情報量を維持して指摘を反映する。

## 更新責任

| 対象 | ルール |
|---|---|
| 実装 | [製品要求](../requirements/製品要求.md)を満たすこと |
| 仕様 | 実装前の設計案は`docs/backlog`に置く。実装と同じ変更で`docs/spec`を更新し、常に現行実態と一致させること |
| 画面 | 画面設計案は課題へ置き、実装と同じ変更で画面項目定義を更新すること |
| 構想メモ | 未採用案は`docs/backlog/改善候補.md`へ置き、採用済みの恒久方針と分ける |
| 差分整理 | 未実装の作業は`docs/backlog/未実装課題.md`、未確認は`docs/validation/未確認事項.md`へ分ける。現行の制限・非対応時の挙動は仕様に残す。目的と情報を保持したまま、現行仕様・残課題・未確認へ正しく分類する |

## バックログの分類と全体優先順位

バックログは「改善」「デザイン」「機能」に分けて管理する。改善は既存品質・不具合・性能・構造の修復や向上、デザインは画面・表示・操作体験の判断と調整、機能は未実装の振る舞いや契約を扱う。複数に関わる課題は主たる区分に詳細の正本を置き、関連区分から相互参照する。情報を重複して独立管理せず、目的・経緯・未決事項・受入条件を保持する。

`docs/backlog/README.md`を区分横断の優先順位の入口とし、各課題の区分、状態、全体での着手順、優先理由、依存・阻害条件、次の行動、詳細の参照先を一覧で管理する。区分内だけの順位で作業を選ばず、利用者の明示した優先順位、コア体験の阻害・デグレ、重大な不確実性、依存関係と利用者価値を全体で比較する。状態・依存・判断が変わった際には全体の着手順も見直す。採番IDを付けず内容の分かる見出しで参照する。

デザイン残項目には、機能側の仮実装からデザイナーへ渡す判断材料を保持し、バックログのデザイン区分へ概要と参照を置く。デザインから生じた未実装機能は機能区分へ記録する。引継ぎの内容とタイミングは[開発方針](開発方針.md#機能実装とデザイン判断の引継ぎ)を適用する。機能実装済み・デザイン未確定・機能未実装・検証待ちを区別して追跡する。

既存バックログをこの分類へ整理する際は、現行項目の情報とリンクを保持して移行する。規約の追加だけでは分類移行済みと扱わず、既存項目の再編は別の作業として行う。

## 構造・命名・履歴の管理

| 対象 | 規則 |
|---|---|
| 製品要求 | `docs/requirements/製品要求.md`に、目的、利用者の価値、背景、統一方針をまとめる。Howは最小限にし、API・処理順はspec、実装状態・作業一覧はbacklogやvalidationへ置く |
| packageの恒久要求 | `docs/requirements/パッケージ要求.md`へ共通基盤の恒久的な責務・判断基準を記録。API詳細は仕様、完了条件は課題、証跡は検証へ分ける |
| 作り方の制約 | `docs/policies`へ集約。ツール操作や執筆規則はpoliciesへ置く |
| 仕様と要求 | specは現行のAPI・動作・設定・制約。要求はWhy/Whatと統一方針。未実装設計はbacklog、未確認一覧はvalidationへ置く |
| ファイル名 | 日本語文書は内容と役割が分かる名前にする。App/RTC等の実装上の固有名は維持。内容・役割・保存期間を説明できる具体名を使う |
| 移動 | 同じ変更で参照と索引を更新。空になった旧文書ディレクトリはrmdirで除く。文書清掃の対象は所有する文書と参照へ絞り、生成物・依存・Xcode内部の状態は専用の資源管理工程で扱う |
| 過去計画 | `docs/development/history`に旧計画として原文を保持し、現行との差と現在の参照先を添える。現行の実行用promptには最新の正本を参照する |
| ツール入口 | AGENTS.md / CLAUDE.md / .github/copilot-instructions.mdは共通正本への必須参照だけにし、規約本文は正本へ集約する |
| 継続検査 | scripts/check_documentation.pyで参照、到達性、空文書ディレクトリ、Settings記載を検査する。過去原文のコードブロックは履歴のリンクとして区別する |

過去資料の採番・旧パスは原文保全のため引用内に残す。現行規約の識別には説明的な見出しを使う。

## パッケージ要求の管理

対象は[パッケージ要求](../requirements/パッケージ要求.md)。packageが持つ恒久的な責務と判断基準を記録する。現状との差は課題、確認待ちは検証へ分ける。Appの暫定実装や既存コードの棚卸しはspec・backlogへ分類する。

| 工程 | ルール |
|---|---|
| パッケージ更新 | 要求を参照してApp側で回避している内容が解消されているか確認する。この工程での要求文書の扱いは参照と適合確認に限定する。要求の改訂は独立した要求判断の工程で扱う |
| App追従 | package APIを適用後、App仕様を実態に揃え、課題を更新する。未確認事項と証跡は検証へ記録。恒久要求は責務と判断基準として維持する |
| 追加判断 | 共通の責務方針は要求、実装すべき差分は課題へ記録する |

### 追記する内容

| 記録する項目 | 内容 |
|---|---|
| package | 変更対象package |
| packageが所有する責務 | Appではなくpackageが持つべき責務 |
| 責務をpackageへ配置する理由 | package独立性、OS差分吸収、準異常系処理、runtime情報通知、設定受け取りのどれに関わるか |
| 要求を満たす判断基準 | 利用者やAppが何を同じ意味で扱える必要があるか。具体的なAPI・処理順は仕様または課題の設計案へ分ける |

### App追従時の扱い

| 項目 | 方針 |
|---|---|
| App 側暫定実装 | App側の都合として扱い、Appの仕様や課題へ記録する |
| package に既にある責務 | `docs/spec/packages` と `docs/spec/App/Configuration/Bindings` を参照し、App 仕様から該当の正本を参照する |
| 新しい不足の判断 | App が OS 差分、継続可能な準異常系、runtime report/event、設定受け取りを自前で補う必要が出た場合だけ追記する |


## 分類の判断と完了時の移動

| 問い | 置き場所 |
|---|---|
| なぜ必要か・何を統一して求めるか | requirements。作り方への共通制約はpolicies |
| 今のコードは何を行うか | spec。設定値、API、例外・制限も実態として記録 |
| これから何を作るか | backlog。未採用案と実装課題を分け、完了条件・設計案を置く |
| 実装したが何をまだ確かめていないか | validation/未確認事項 |
| どの条件で何を確認したか | validation/history。過去の条件と結果を保持し、現在の結果を別の記録として追加する |
| どう設定・操作・再実行するか | manual / development。試算は前提と確認日付きの開発資料 |

分類は文書名だけでなく本文にも適用する。要求・仕様には他分類への参照を置けるが、課題表・未確認表・試験結果は各分類の正本へ置く。実装後は課題から作業を外し、実態を仕様へ、確認待ちを検証へ移す。達成済みでも恒久要求は維持する。APIが値を取得できないことや非対応OSでのエラーは現在の仕様であり、現行仕様へ記録する。
