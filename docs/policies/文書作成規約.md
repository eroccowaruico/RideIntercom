# 文書作成規約

本書は文書・計画・要求管理の作り方を定める。アプリが利用者へ提供する価値と機能は[製品要求](../requirements/製品要求.md)、実装の制約は[開発方針](開発方針.md)へ分ける。

## 記述規則

| 項目 | ルールと理由 |
|---|---|
| 基本ルール | [開発方針](開発方針.md)を適用する |
| 採番禁止 | ルール、要求、見出し、表の識別に採番IDや番号を付けない。番号ズレによるメンテナンス負荷を避ける |
| 表現 | 曖昧な表現を避け、実装時に判断可能な文で記述する |
| 図表優先 | 認識齟齬を防ぐため、仕様は図表を使う。特に画面・状態・設定は表を優先する |
| 文章の扱い | 仕様を文章だけで説明することを極力避け、背景や意図を文章で補足する |
| 詳細度 | 実装者が迷わないよう、背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点をできる限り詳しく説明する |

## プランの策定

- 要件を満たすための具体的な実装ステップを示す。
  - 実装の依存関係を明確にした上で、実装が円滑に進む順序や優先順位を明確にする。
- 経験や前提知識の少ない実装者やモデルでも、そのまま実装に入れる具体的な内容とステップを示す。
- 背景、理由、現状との違い、明確な仕様、体験の差、実装方針、注意点などをできる限り詳細に説明する。
- プランは作業手順や指示だけではなく、設計書や仕様書のような形式で、実装者が完了条件を理解できるように記述する。
- 実装者が判断に迷わない、実装をストレートに進められる内容とする。
- プラン冒頭に指示内容と背景を記載する。修正時は特に指示がない限り既存の内容・情報量を維持して指摘を反映する。

## 更新責任

| 対象 | ルール |
|---|---|
| 実装 | [製品要求](../requirements/製品要求.md)を満たすこと |
| 仕様 | 実装前の設計案は`docs/backlog`に置く。実装と同じ変更で`docs/spec`を更新し、常に現行実態と一致させること |
| 画面 | 画面設計案は課題へ置き、実装と同じ変更で画面項目定義を更新すること |
| 構想メモ | 未採用案は`docs/backlog/改善候補.md`へ置き、採用済みの恒久方針と分ける |
| 差分整理 | 未実装の作業は`docs/backlog/未実装課題.md`、未確認は`docs/validation/未確認事項.md`へ分ける。現行の制限・非対応時の挙動は仕様に残す。目的や情報を消して整合した扱いにしない |

## 構造・命名・履歴の管理

| 対象 | 規則 |
|---|---|
| 製品要求 | `docs/requirements/製品要求.md`に、目的、利用者の価値、背景、統一方針をまとめる。Howは最小限にし、API・処理順・実装状態・作業一覧を入れない |
| packageの恒久要求 | `docs/requirements/パッケージ要求.md`へ共通基盤の恒久的な責務・判断基準を記録。API詳細は仕様、完了条件は課題、証跡は検証へ分ける |
| 作り方の制約 | `docs/policies`へ集約。製品要求にツール操作や執筆規則を混在させない |
| 仕様と要求 | specは現行のAPI・動作・設定・制約。要求はWhy/Whatと統一方針。未実装設計や未確認一覧をどちらにも混ぜない |
| ファイル名 | 日本語文書は内容と役割が分かる名前にする。App/RTC等の実装上の固有名は維持。log・requirementsのような分類の分からない汎用名や作り直し前提の名前を避ける |
| 移動 | 同じ変更で参照と索引を更新。空になった旧文書ディレクトリはrmdirで除く。生成物・依存・Xcode内部の状態フォルダは文書清掃で触らない |
| 過去計画 | `docs/development/history`に旧計画として原文を保持し、現行との差と現在の参照先を添える。現行の実行用promptへ残さない |
| ツール入口 | AGENTS.md / CLAUDE.md / .github/copilot-instructions.mdは共通正本への必須参照だけにし、規約の本文を三重管理しない |
| 継続検査 | scripts/check_documentation.pyで参照、到達性、空文書ディレクトリ、Settings記載を検査する。過去原文のコードブロック内は現行リンクと扱わない |

過去資料の採番・旧パスは原文保全のため引用内に残す。新しい現行規約へ採番を持ち込むことは認めない。

## パッケージ要求の管理

対象は[パッケージ要求](../requirements/パッケージ要求.md)。packageが持つ恒久的な責務と判断基準を記録する。現状との差は課題、確認待ちは検証へ分ける。Appの暫定実装や既存コードの棚卸しは要求にしない。

| 工程 | ルール |
|---|---|
| パッケージ更新 | 要求を参照してApp側で回避している内容が解消されているか確認する。要求文書自体は編集・更新しない |
| App追従 | package APIを適用後、App仕様を実態に揃え、課題を更新する。未確認事項と証跡は検証へ記録。恒久要求は状態表にせず維持する |
| 追加判断 | 共通の責務方針は要求、実装すべき差分は課題へ記録する |

### 追記する内容

| 記録する項目 | 内容 |
|---|---|
| package | 変更対象package |
| packageが所有する責務 | Appではなくpackageが持つべき責務 |
| Appに暫定実装しない理由 | package独立性、OS差分吸収、準異常系処理、runtime情報通知、設定受け取りのどれに関わるか |
| 要求を満たす判断基準 | 利用者やAppが何を同じ意味で扱える必要があるか。具体的なAPI・処理順は仕様または課題の設計案へ分ける |

### App追従時の扱い

| 項目 | 方針 |
|---|---|
| App 側暫定実装 | App側の都合として扱い、要求一覧には残さない |
| package に既にある責務 | `docs/spec/packages` と `docs/spec/App/Configuration/Bindings` を参照し、App 仕様へ重複定義しない |
| 新しい不足の判断 | App が OS 差分、継続可能な準異常系、runtime report/event、設定受け取りを自前で補う必要が出た場合だけ追記する |


## 分類の判断と完了時の移動

| 問い | 置き場所 |
|---|---|
| なぜ必要か・何を統一して求めるか | requirements。作り方への共通制約はpolicies |
| 今のコードは何を行うか | spec。設定値、API、例外・制限も実態として記録 |
| これから何を作るか | backlog。未採用案と実装課題を分け、完了条件・設計案を置く |
| 実装したが何をまだ確かめていないか | validation/未確認事項 |
| どの条件で何を確認したか | validation/history。過去の記録を書き換えて現在の成功にしない |
| どう設定・操作・再実行するか | manual / development。試算は前提と確認日付きの開発資料 |

分類は文書名だけでなく本文にも適用する。要求・仕様には他分類への参照を置けるが、課題表・未確認表・試験結果を重複掲載しない。実装後は課題から作業を外し、実態を仕様へ、確認待ちを検証へ移す。達成済みでも恒久要求は維持する。APIが値を取得できないことや非対応OSでのエラーは現在の仕様であり、単なる確認待ちへ移さない。
