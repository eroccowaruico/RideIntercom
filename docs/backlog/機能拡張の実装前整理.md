## 完全終話後の24時間条件

起算点はグループで最後に「購入者あり」で通話が開始した時刻とする。購入者本人が開始操作を行うことまでは要求しない。24時間は利用権自体の有効期限とは別の再開条件であり、購入者の毎日の手動確認やサーバーへの定期照会を意味しない。

追加回答により、通信断からの復帰もこの再開条件を使う。24時間以内は自動再開し、超過後は購入者相当を必要とする。通信断がなく継続している通話と、他経路で維持できている通話は24時間経過だけで切らない。会話相手がいなくなれば終了扱いとし、全端末の終話合意は求めない。

| 状態・操作 | 今回明確になった扱い |
|---|---|
| 通話が継続している | 起算点から24時間を超えただけでは切断しない |
| 完全終話後、起算点から24時間以内に未購入者だけで再開 | この24時間条件による制限はしない。再開しても起算点は変わらない |
| 完全終話後、起算点から24時間を超えて未購入者だけで再開 | 開始できない。直前に未購入者だけで再開していても同じ |
| 通信断からの復帰 | 24時間以内なら自動再開。超過後は購入者相当がいる状態で再開する。接続の再試行だけで起算点を更新しない |
| 完全終話後、購入者ありで新しく開始 | 開始でき、新しい購入者ありの開始時刻を起算点とする。購入者が開始ボタンを押すことは必須にしない |
| 購入者がグループ一覧に登録されているだけ | 「購入者ありの開始」にはならない。有効な権利を持つ人を含む参加者同士の認証と通話接続の成立を必要とする。途中参加では起算点を更新しない |
| 起算点の記録がない、取得できない、端末間で食い違う | 無条件に新しい24時間を与えない。初回開始・移行・復旧時の扱いを別途決める |

例えば、購入者ありで月曜08:00に開始して完全終話し、未購入者だけで月曜20:00と火曜07:00に再開しても、起算点は月曜08:00のままである。再び完全終話した後、火曜08:00を超えて購入者なしで開始することはできない。火曜07:00に始まった通話が続いている場合は、08:00を超えただけでは切断しない。「24時間を超えたら」という要望に合わせ、ちょうど24時間は超過前として表に置く。時刻精度と端末間の差は設計時に定める。

この表は24時間条件だけの整理であり、グループ作成権、所属・認証、利用権自体の失効等を免除するものではない。以前の「購入者の確認または発信」という曖昧な表現はこの条件に置き換える。

## 権利と発信の設計前に決めること

以下の決定を課金・権利判定の実装より先に行う。商品価格を未定のまま検討を進めることはできるが、何を購入・付与すると何ができるかは先に揃える必要がある。

| 論点 | 抜け・矛盾が生じる条件 | 決めること |
|---|---|---|
| 購入者と利用権保持者 | 有料・有効な試用・無料券・TestFlightはグループ作成と購入者ありの開始で同等と回答を得た | [共通判定](利用権とデータ保持の設計.md#開始再開の共通判定)を適用する。実購入、独自付与、配布環境による権利を区別する。試用・無料券の期間と付与方法、製品版との混在時の検証方法は課金連携で決める。内部テストの迂回は別枠にする |
| 作成者・管理者・購入者 | 課金した人が常に作成者・所有者とは限らない。現在の詳細画面を「管理者向け」と呼んでも操作権限は確定しない | グループを作る人、構成を変更する人、利用権を提供する人を同一にするか分けるか。必要な管理権限の範囲と引継ぎを決める。[Owner選出候補](改善候補.md)全体の採用を自動的に意味しない |
| 終了・通信断と操作の意味 | 会話相手がいなくなれば終了扱いとし、通信断からの復帰にも同じ24時間条件を使うと回答を得た | 無音・マイクOFF・音声機器停止だけでは再開判定をしない。別の経路で通話が続いていれば継続。全端末の完全終話を合意する仕組みは加えず、既存の接続・参加者情報と共通の開始処理へ接続する |
| 購入者ありの開始成立 | 有効な権利を持つ人を含む参加者同士の認証・通話接続の成立時点と確定。途中参加は更新対象にしない | 認証済みの制御通信で購入者相当状態と開始日時を共有。複数購入者がいても割合を要求せず、重複通知で更新しない。ログイン・復元・呼出し・無応答・失敗・未購入者だけの再開では更新しない |
| 24時間経過後の再開と履歴共有 | 購入者ありなら新しく開始できる。各端末が別々の起算点を持つと、同じグループで可否が食い違う | 初回開始、起算点の保存先、参加者間の共有、再インストール・新端末・同時開始時の扱いを決める。既存の制御通信と端末保存で共有する低コスト案を先に評価する。購入者への参加依頼や購入復元は開始可否と分け、再開条件の回復手段を残す |
| 権利失効と24時間の残り | 期限切れ・返金・購入者離脱後も、成立済み通話と残り24時間を維持すると回答を得た | 過去の開始成立と現在の権利を別に保持する。失効した権利では新しいグループを作成・起算点を更新できない。他の有効な権利は使える。離脱だけで本人の購入権利まで失効させない |
| 1対1の内部グループ | 同じ利用権・24時間条件を適用し、初回は片方以上に権利が必要。同じ二人のグループを再利用すると回答を得た | 未購入者から購入者への呼出しを許し、応答と有効な権利の確認後に共通処理で内部グループを解決する。両方未購入の初回開始は不可。成立済みの起算点から24時間以内なら両方未購入でも再開できる。端末追加・同時生成・削除後の扱いを共通設計で定める |
| Localとオフライン | 毎回独自サーバーで購入検証するとLocal通話とコストの希望に反する。一方、オフラインでは返金・失効等の最新情報を即座に知ることはできない | StoreKitで検証済みの購入状態と期限をアプリに保持する前提で、初回購入・復元と以後の通話を分ける。期限・時計変更、状態取得不能時、改変への対処、許容する失効反映の遅れを決める。通信失敗を購入取消や永久有効へ自動変換しない |
| 判定と強制の所有者 | 緩やかな利用条件とし、正規アプリ同士の協調を前提にする。改変クライアントによるInternet費用の濫用防止は別の問題 | 端末の共通判定を全入口から使う。自分の購入はStoreKitで検証し、相手の状態は認証済み通信で交換する。相手の購入証明の再検証や独自の購入検証サーバーを追加しない。既存の認証・暗号化・利用枠を維持し、公開時のabuse対策は別課題のまま扱う |
| 期間商品の意味 | 1週間は購入時からと回答を得た。復元時に購入日時から確認しやすいことが理由 | [期間と復元の設計](利用権とデータ保持の設計.md#期間と復元)を適用する。復元や初回使用で期限を延長せず、重複する権利を独立に評価する。具体的な商品種別、同一商品の追加購入、試用・無料券の期間、月額の更新失敗・猶予は課金連携前に決める |
| 購入とアカウントの結び付け | App Storeの購入用アカウントとAppleログインで識別するアプリ内ユーザーは同一とは限らない。切替や復元で別のユーザーへ権利を重ねて付与する可能性がある | 購入時・復元時の対応、StoreKitの取引更新、サインアウト、再作成時の扱いを決める。iPhoneとmacOS間、同一ユーザーの複数端末も対象にする。端末でのStoreKit検証・手動復元を先に設計でき、ログイン基盤やサーバー通知の完成を必須にしない |
| TestFlightの同等扱い | sandboxの購入環境だけでは開発版も含み、購入操作の有無からもTestFlightを一意に判別できない | TestFlightは購入なしで同等扱いとし、自動判別は端末側の配布環境情報と開発構成の分離を第一候補にする。判別不能時、製品版への移行、混在グループで購入者相当となる期間を決める。実購入・試験取引・配布環境による権利を別に管理する |
| 内部テストの限定迂回 | 開発版を常に購入者扱いすると、無権利・期限切れの試験ができず、権利判定の不具合を隠す | 試験ごとに必要な利用権・時刻条件だけを指定し、迂回が不要な箇所は通常判定を通す。課金機能そのものはStoreKit Testingやsandboxで購入・失効・復元を検証する。一般向け製品版から内部用の迂回を使えないようにする |

## 端末での購入検証とテスト環境

2026-10-30のApple公式資料では、購入検証用の独自サーバーは必須ではない。購入状態・期限の端末内保持と利用者操作による復元を基礎に、StoreKitの検証と更新通知を使う構成を第一候補とする。下表は方式選定の調査結果であり、実装・実機検証は未着手である。

| 対象 | 確認結果と低コストで進める方針 |
|---|---|
| 購入の検証 | Appleはサーバーで検証する方法と、[StoreKitの検証を使う方法](https://developer.apple.com/documentation/storekit/in-app-purchase)を選べると説明している。検証済み取引に基づく権利と期限を端末で扱い、任意に書いた購入済みフラグだけを根拠にしない。独自の検証API・購入台帳DB・定期照会を初期構成に追加する必要はない |
| 状態更新と手動復元 | 起動時等に現在の権利を取得し、動作中はStoreKitの取引更新を反映する。[AppStore.sync](https://developer.apple.com/documentation/storekit/appstore/sync%28%29)は利用者が復元を選んだときに呼ぶ。通常はStoreKitが状態を更新するため、毎回の同期や定期的な復元操作は不要。Appleとの購入・復元等の通信まで不要になるわけではない |
| 1週間チケット | 非更新型の期間商品を候補にできるが、[currentEntitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements)には終了済みの非更新型取引も含まれ、消費型は含まれない。存在だけで有効と判定せず、期間を計算する必要がある。その後の回答で、復元時に確認しやすい購入日時からの1週間に決定した。利用開始まで保管する方式にはしない。同一商品の追加購入を許す条件や残期間との扱い、商品種別は課金連携で確定する |
| 月額とオフラインの限界 | 月額は検証済み取引・購読状態と期限を反映する。取消、返金、更新失敗、猶予等の扱いを決める。端末が最新状態を取得できない間の反映遅れは残るため、既知の期限と状態不明を区別する。即時失効のためだけに常時サーバー照会を採用せず、必要な正確さと費用を比較する |
| グループへの反映 | 自分の購入は端末で確認し、購入者相当状態と最後の購入者ありの開始時刻は既存の認証済み制御通信と端末保存で扱う。複雑な仕組みを避けるという追加指示により、購入証明の端末間検証や通話履歴の中央台帳は加えない。改変クライアントに対する厳密な課金強制は保証しない |
| 無料チケットと試用 | StoreKitの購入復元だけで独自の無料チケットや試用履歴まで復元できるわけではない。発行・期間・使い回し防止・復旧の要件を決め、端末だけで許容する範囲と管理が必要な範囲を比較する。有料購入の検証に独自サーバーが不要であることを、すべての付与方式に追加管理が不要との結論へ広げない |
| TestFlightの判別候補 | [AppTransaction](https://developer.apple.com/documentation/storekit/apptransaction)はアプリ取得の検証結果を提供し、その[environment](https://developer.apple.com/documentation/storekit/apptransaction/environment)から署名環境を取得できる。アプリ内購入の有無とは別の情報である。ただし[課金sandbox](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)は開発署名版とTestFlightの双方で使うため、sandboxだけを購入者扱いの条件にはしない。検証済みの環境情報と開発・配布構成を組み合わせる端末側の判別を候補とし、TestFlightだけに適用できるかを実機で確認する |
| TestFlightを明示的に区別する方式 | [App Attestのサーバー検証資料](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server)には、配布区分でTestFlight、開発署名、App Store等を区別する情報がある。自動判別の手段自体はあるが、サーバー検証・対応OS・保守の負担が増えるため、この区別だけのために初期採用するとは決めない。端末側の候補で不足する場合の比較対象に留める |
| 判別の受入条件 | TestFlight、App Store、開発版sandbox、XcodeのStoreKit Testing、ad hoc等の対象配布方法、審査時の動作、初回起動・圏外・取得失敗、製品版への切替を確認する。取得不能をTestFlight扱いにせず、過去のTestFlight判定で製品版へ永続的な権利を残さない。TestFlight購入者同等の体験と、課金状態を直接試験する経路を分ける |
| 開発時の試験 | [StoreKit Testing](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox)は実課金なしで、ローカル設定・オフラインでも購入の試験ができる。課金経路の検証ではこれを使い、音声やUI等の試験では必要な権利判定だけをテスト用入力に置き換える。内部用迂回で認証・グループ所属・費用制限等まで無効化しない |

独自サーバーの追加を再検討する条件は、端末判定では不足する濫用対策、即時失効、無料券の一元管理等が具体的に必要になった場合とする。導入するなら、得られる効果と保守・運用・通信・処理の増分を並べて判断する。既存の通話サービスや今後のログイン・通知に必要なサーバーと、購入検証用サーバーは分けて考える。

## 認証とグループの設計前に決めること

| 論点 | 抜け・矛盾が生じる条件 | 決めること |
|---|---|---|
| 「個人情報を一切保持しない」の範囲 | メール・本名を保持せず、必要最小限の認証識別子・端末資格・通知先のサーバー保存を認めると回答を得た。IDを非個人情報とみなす決定ではない | [データ保持表](利用権とデータ保持の設計.md#データ保持表)を適用する。表示名・ユーザー一覧・グループ情報・購入状態は端末中心。現行Workerには表示名やowner別の利用枠記録があるため、その差分とproviderのアクセス記録も整理し、「データ収集なし」と断定しない |
| Apple認証と端末・ユーザー | 現行の端末メンバーと新しいユーザーIDを一対一と決めつけると、機種変更や複数端末で別人になり得る | アプリ内ユーザーID、Apple認証の識別子、端末ID、通知宛先を区別する。初回登録、再ログイン、認証取消、端末紛失、端末追加を定義する。ログインを全通話で必須にするか、導入前の利用をどう移行するかも決める |
| 表示名と未接続時の操作 | 表示名とユーザー一覧は端末で保持する方針が確定。現行Workerの通話用表示名保存との差分がある | 未取得・変更・重複時の表示、通知の表示方法を設計する。表示名による相手識別と認証済みIDを区別し、通知に表示名を載せる方式が中央保存の範囲を広げないか確認する |
| 相手の登録・同意・通知 | 既知IDがあることと、相手を新グループへ参加させる権限や通知を送る権限は同じではない | ユーザーをどう知るか、追加・招待・参加同意の導線、通知できる相手、ブロック・退出・招待取消を決める。既存ユーザーの再登録を不要にする要望と、認証を省略することを混同しない。ID列挙や繰返し呼出しを抑える方法も公開運用課題につなげる |
| グループと鍵の寿命 | 現行は端末からグループを削除しても、配布済み招待や他端末の鍵を失効させない。ユーザーを残すだけでは全体の退会・アクセス禁止にはならない | 端末からの削除、グループ退出、全体の解散、メンバー除外、鍵・招待の失効を分ける。作成者の退出・削除と、他の購入者の継続可否も決める。公開identity課題にある招待形式維持の条件との整合を確認し、変更が必要ならその条件も見直す判断を行う |
| 保存移行と複数端末 | 既存グループには表示名と端末メンバーが保存される。利用権やログイン追加だけで既存の同一人物を確実に統合できるとは限らない | 既存グループ・ユーザー・鍵の保持、重複候補の扱い、失敗時の復旧、旧版との接続条件を決める。ユーザー一覧の人数と、現行の自分を含む8人のグループ枠、同一ユーザーの複数端末を区別する |
| アカウント削除と購入 | グループを消すこと、Appleログインを解除すること、アカウントを削除すること、サブスクリプションを解約することは別 | アプリからのアカウント削除、認証・通知先の失効、所属・ハンドルネーム・権利記録の扱い、購入の管理・復元導線を用意する。削除しても自動更新の解約が完了したと表示しない。試用の再取得防止と削除後の記録保持が衝突する場合も判断する |

## iCloudへの保存と自分の端末間同期

候補の範囲は、同じ利用者が保有する端末でのデータ保存・同期・復旧とする。自分が保存したグループや相手のユーザー情報を扱い、別の利用者への自動公開やグループ全体の所属・認証を管理する仕組みにはしない。通話・マイク状態の自動引継ぎも今回の要望に含めない。

| 論点 | 実装前に整理する内容 |
|---|---|
| 共有対象と端末固有情報 | 個人の設定、グループの識別子・表示情報、登録した相手のID・ハンドルネーム等から同期対象を列挙する。音声機器、OS権限、端末ID、通知token等は端末固有として分ける。音量や音声設定は全端末共通にしたいものと機種ごとの値を区別する。音声・録音・診断ログのクラウド保存へ範囲を広げない |
| アカウントの対応 | iCloudのアカウント、Appleログインで識別するアプリ内ユーザー、App Storeの購入アカウントを同一と決めつけない。iCloud未使用・変更・サインアウト、アプリ内ユーザー切替時にデータが混ざらない保存単位を決める。Appleログイン機能の完成を同期方式の調査条件にはしない |
| グループ情報と参加資格 | グループが一覧に復元されることと、新端末が通話へ参加できることを分ける。グループ鍵・招待・端末資格を安全に移行するか、再認証・再招待するかを決め、通常の設定レコードへ秘密をそのまま複製しない。復元で退出・除外・失効した参加資格を復活させない |
| 課金と24時間条件 | 購入権利はStoreKitの検証・復元を基準とし、同期された購入済み表示だけで権利を付与しない。最後の購入者ありの開始時刻を同期対象とするかは別途決める。同期の遅延・古い復元・時計の違いによって24時間を延長せず、グループ参加者間の開始状態の伝達を個人用iCloud同期へ依存させない |
| 競合と保存形式 | 同時編集、重複登録、削除と編集の競合、端末ごとの旧版データに対する統合規則を決める。安定したユーザー・グループID、保存形式の版、削除記録の扱いを先に設計する。後着の古い情報で削除した相手やグループを自動復活させない |
| 同期と復旧の違い | 同期で削除や誤変更も他端末へ伝わるため、過去版へ戻せるバックアップまで提供するかは別途決める。初回の端末データと既存クラウドデータの統合、機種変更、再インストール、同期OFF、端末だけの削除・クラウドからの削除・アカウント削除を区別する |
| 圏外・容量不足・障害 | 端末内の保存を維持し、iCloud未使用・圏外・容量不足・同期失敗で基本通話を待たせない。未同期と保存失敗を区別して表示し、再試行・復旧条件を決める。読み出せないデータを空の一覧として同期して既存データを消さない |
| 個人情報と保存範囲 | メールアドレス・本名等を保持しない方針を維持する。自分の私的なiCloud領域に保存する相手のID・ハンドルネーム・グループ関係も、保存先・目的・保持期間・削除の一覧に含める。自社サーバーに置かないことだけを理由にプライバシー上の整理を省略しない |
| 費用と一般向け体験 | 独自の同期サーバーを増やさない案から比較し、通信量・起床頻度・電池消費・利用者の保存容量・保守作業を評価する。採用時の有効化方針、最終同期・同期失敗・復旧の表示を一般向け英語・日本語の対象にする |

2026-10-30に確認した[CloudKitのprivate database](https://developer.apple.com/documentation/cloudkit/ckcontainer/privateclouddatabase)は、原則として本人だけがアクセスでき、端末のiCloudアカウントを必要とし、データは本人のiCloud保存容量を使う。この範囲の方式候補として調査する。採用APIや保存方式は未決であり、独自サーバー不要の可能性と、同期の実装・保守・通信が不要であることを混同しない。

順序は、保存対象・アカウント対応の決定 → ユーザー／グループの共通モデルと端末内保存・復旧 → 同期の採否と競合・削除・移行設計 → 採用時の同期機能 → 一般向け画面・複数端末での受入とする。課金・通知の開発とは並行でき、ウィジェットやWatchの実装が終わるまで待つ必要もない。全体の[依存順](未実装課題.md#依存関係と取り組む順序)と合わせて扱う。

受入では同一利用者のiPhone・Mac等、オフライン後の再同期、同時編集・削除、iCloud切替、容量不足、旧版・再インストール、資格が失効したグループの復元を確認する。個人の端末間同期が成功することと、他の参加者へ通知・参加・通話できることを別の成功条件にする。

## 画面とのIF抽象化と一般向けの情報設計

新しい一般向け画面の実装に先立ち、画面が依頼する操作と、処理側から受け取る状態・結果のインターフェースを整備する。Diagも抽象化の対象とし、一般向け画面に診断情報を載せない方針と、Diag自体を処理から分離する工程を両立させる。今回は順序・設計条件の記録までであり、具体的な型・API・実装はまだ確定しない。

| 画面の系統 | 用意する内容・利用者体験 |
|---|---|
| 既存のアドバンスド・開発者向け画面 | 詳細な設定・状態とDiagを扱う。ユーザー一覧とグループ一覧も共通のデータとIFから利用する。既存画面も画面と処理の分離対象にする |
| 新しい一般向け画面 | ユーザー一覧とグループ一覧を利用でき、少ない情報と分かりやすい説明で操作を完結させる。Diagは含めない。特定ユーザーとの通話では相手を選んで操作でき、内部のグループを意識させない |

両系統は同じデータ・処理を利用し、表示する情報量や説明を目的に合わせる。既存画面をそのまま縮小したものに一般向け画面を固定せず、一般向けの利用体験を成立させる境界を設計する。


現行の[アーキテクチャ](../spec/アーキテクチャ.md#大きな実装の責務分解)では、DiagnosticsInputの値snapshotと純粋な表示導出が既に分かれている。この境界を含め、実装前に既存の分離状況を棚卸しして不足箇所を整理する。既存の分離を作り直すことや、抽象化の数を増やすこと自体を目的にはしない。

| 境界・論点 | 整備する内容・完了条件 |
|---|---|
| ユーザー一覧・グループ一覧 | 両系統の画面が共通のID・表示情報・所属等に基づいて一覧を取得・更新できるIFを設ける。保存処理や将来の同期方式を画面へ露出させず、画面別のユーザー台帳・グループ台帳を持たない。情報の詳しさ・配置・説明は各画面に合わせる |
| ユーザー指定とグループ指定の通話 | IFでは特定ユーザーへの通話と指定グループへの通話を表現できるようにする。ユーザー指定から内部グループを作成・再利用・解決する責務を画面から分離し、一般向けで内部グループの選択や管理を求めない。通話相手の表示・履歴・直近の相手もユーザー指定の意味を保つ |
| 内部グループの権利と寿命 | 同じ相手との再利用、作成者・所属・認証・終了・削除と、利用権・24時間条件の適用を共通モデル・処理で決める。グループを一般向けに見せないことを、グループ作成権や認証の無条件な免除にはしない。[1対1の権利の未決事項](#権利と発信の設計前に決めること)を先に解決し、画面側で例外を足さない |
| 画面からの操作要求 | 通話先の選択、開始・応答・終了、マイクのON/OFF、必要な設定変更等を、画面部品や画面遷移に依存しない意味で依頼できるようにする。ユーザー・グループ管理、購入・復元、採用時の同期操作も、対応する機能を追加するときに同じ原則で接続する |
| 処理からの表示状態 | 相手とユーザー／グループの区別、呼出中・接続中・通話中等の状態、実際のマイク状態、操作可否とその理由を一般向けの表示入力として整理する。押した操作の希望値と実際の状態を分け、接続できたことだけで音声も正常に届いていると見せない |
| 結果・失敗・復旧 | 処理中・成功・失敗・取消等の結果を受け取り、一般向けには何が起きたかと次にできる操作を短く示す。権利不足、24時間条件、権限不足、音声機器消失、保存・同期の失敗を、画面側で技術エラーから再判定しない。表示文言の英語・日本語対応と、生の診断詳細を分ける |
| Diag向けのIF | 詳細な通信・音声・codec・pipeline等の診断情報は専用の表示入力として渡し、Diag画面が実処理や測定を直接実行して表示値を組み立てないようにする。必要な診断操作にも明確な操作の接点を設ける。既存の診断情報や開発用の確認能力を一般向けの簡略化に合わせて減らさない |
| 状態と処理の管理 | 一般向けとDiag向けの表示入力は必要に応じて分け、同じ通話・保存・利用権等の状態から導出する。画面ごとの通話処理、権利判定、タイマー、二重の可変状態を増やさない。通信・音声・OS差分等の処理は[開発方針](../policies/開発方針.md)で定めた責務に置き、画面都合をpackage内部へ持ち込まない |
| 一般向けの情報量 | 通常表示は、誰と話すか、通話・マイクの状態、今できる主要操作を中心にする。失敗理由や購入・権限・復旧が必要な案内は必要な場面で示す。詳細な統計値や内部ID・経路・pipeline等はDiagへ置き、一般向けの通常操作がDiagを開かなくても完了するようにする |
| 既存画面と外部操作 | 新画面の追加前に、対象となる既存画面をIFへ接続して操作の意味と実処理の継続を確認する。一般向け・既存画面・通知・Siri・ウィジェット・Watch等が同じ操作判定を使い、入口ごとの24時間条件や通話処理を実装しない。画面の構造・文言・遷移は各表示側の責務として扱う |
| 更新負荷と検証 | Diagを開いていないときに一般向けの表示のためだけに詳細診断を高頻度取得しない。表示入力と操作結果を与えて画面を確認できるようにし、画面を使わず共通操作も検証できる境界にする。既存画面と新画面で対象・操作可否・実行結果が一致すること、二重開始・遅れた終了操作等の扱い、既存の通話・音声の継続性を受入条件にする |

順序は、両系統の画面で必要な一覧・情報・操作の整理 → 既存IFと処理の責務の棚卸し → 共通のユーザー・グループモデルとユーザー指定からの内部グループ解決・権利条件の設計 → 一覧・操作・状態とのIF整備 → Diagを含む既存画面の接続・検証 → 一般向け画面の追加と英語・日本語対応とする。画面案や文言の検討は先行できるが、新画面の処理実装が先に増えないようにする。課金・通知・iCloud等は機能ごとにIFへ追加でき、全機能の完成待ちにはしない。package変更が必要ならpackage単独の検証とApp追従を別工程にする。

## 画面と端末機能の設計前に決めること

| 論点 | 抜け・矛盾が生じる条件 | 決めること |
|---|---|---|
| 呼び出しと応答の状態 | 現行は接続後に相手を認証して音声を開始する。新しい「発信・応答」には、呼出中・拒否・取消・不在・期限切れ等の状態が足りない | 呼び出しと通話接続の関係、複数端末への着信、最初の応答、応答待ちの期限、遅れて届いた通知、通知拒否時の操作を定める。「通常メッセージ」は通知手段として扱い、別のチャット機能の追加を意味するかは決めつけない |
| 通話中の別着信・再接続 | 外部操作で既存通話を意図せず切らないことと、通信断からの復帰にも24時間条件を使うことを両立する | 閲覧・着信・応答・明示的な通話先変更を分ける。通信断の復帰は24時間以内なら自動再開、超過後は購入者相当が必要。残る経路で通話が続いている場合や音声機器だけの復旧は新規開始とせず、既存の停止理由と復旧動作を保つ |

## 音声品質と節電の実装前に決めること

| 論点 | 現状との差・条件 | 決めること |
|---|---|---|
| 現行の下限と低ビットレート | 点検時の[Codec実装](../../RideIntercom/packages/Audio/Codec/Sources/Codec/Codec.swift)ではOpusを48〜128kbpsへ正規化する。[設定値一覧](../spec/App/Configuration/設定値一覧.md)にも同じ下限がある | 希望するcodec・周波数・bitrateを列挙し、要求値と実適用値を確認する方法を定める。下限を下げる場合は既存の品質基準との関係を先に決め、設定だけ変えて低bitrateを試したことにしない |
| ビットレートだけの影響か | 非可逆圧縮の波形差と、配送・復号・再生で生じる欠落・余分な待ち・クリックは分けて評価する必要がある | 同一入力、codec、sample rate、効果、通信条件でbitrateだけを変え、codec往復と実通信を比較する。許容する歪み、明瞭度、連続性、遅延を別の判断軸にする。低bitrateを許すために標準設定や連続性の合格基準まで一律に緩めない |
| 設定統一の対象と決定権 | 統一対象に端末ごとの音量・音声機器・補助設定まで含めると、個人の聞こえ方や利用環境を損ねる可能性がある | codec・bitrate・音声サンプリング周波数などの共有設定と端末固有設定を列挙する。誰が変更できるか、非対応端末、途中参加、途中変更、fallback・不同意時の扱いを決める |
| 節電の採用基準 | 設定一致だけではCPU・無線・バッテリーの削減を保証できない。端末や人数で効果が変わる | 同じ人数・入力・効果・経路・実時間で、統一／混在の電池消費・処理負荷・通信量を比較する。品質・継続性と、[製品要求](../requirements/製品要求.md)の良好な通信条件で標準設定は125msを満たす遅延要求を維持できる条件、採用に必要な改善幅を定める。効果未確認のまま必須設定にはしない |
| Watchの長時間利用 | 「長時間」と「タップでマイクON」だけでは受入時間や消費電力を判定できない | 目標時間、発話／待受比率、使用機種、音声出力先、iPhone・Watchそれぞれの電池消費、許容中断を定める。Simulatorと実機の確認を分け、音声分離・音楽共存の影響も扱う |

### 低帯域向けの候補と推奨の決め方

2026-10-30の追加要望。端末のマイク・スピーカーは48kHzが多いという利用想定を起点に、通信状況に応じて48kHz・32kbpsと、さらに帯域が厳しい場合の24kHz・16kbpsを選べるようにする。32kbpsや16kbpsでも実通信には多い可能性を考慮し、8〜12kbps付近も含めて聞こえとのバランスから推奨下限を決める。ここでの電話・VoIPの数値は利用者が示した比較の手掛かりであり、RideIntercomで同じ値が使えることや、その値を推奨することはまだ確認していない。冒頭の「16bps」は後続に合わせ16kbpsとして記録する。今回は文書化のみであり、設定値・codec・処理の実装は変更しない。

| 区分 | 評価・保持する候補 | 判定の扱い |
|---|---|---|
| 現行の波形・品質を維持する推奨 | 現行の推奨設定、codec・周波数・bitrate等の実適用値と基準波形 | 必ず保持する。低帯域向けの推奨を追加しても置き換えず、現行の品質判定条件を残す。波形維持の判定範囲も基準と一緒に記録する |
| 低帯域向けの候補 | 通信用48kHz・32kbps | 端末入出力の実際のformatを確認し、codecと端末・OSでこの組合せが使えるか、聞き取りと実通信量が要求を満たすか評価する |
| さらに帯域が厳しい場合の候補 | 通信用24kHz・16kbps | 48kHzの端末入出力と組み合わせる場合の変換・帯域制限・処理負荷も評価する。利用者が選べる候補とし、通信状況による自動切替まで今回の確定要件に加えない |
| 推奨下限を探る候補 | 8〜12kbps付近を含む低bitrate。周波数・codecは未決 | 8kbps、10kbps、12kbps等は比較の候補であり、選択可能・推奨・最下限のどれも未確定。最も低く設定できる値と、実用上勧められる最下限を区別する。必要な比較範囲と適用条件は評価時に定める |

| 評価の論点 | 残す判断・証拠 |
|---|---|
| 実際に設定が効いているか | 現行Opusの下限は上の表のとおり48kbpsであり、32kbps以下は値を指定するだけでは試験にならない。codec・OS・周波数別の対応範囲、要求値・実適用値・実際の符号化データ量を確認する。未対応時の代替適用や拒否を区別し、比較条件に残す |
| bitrateと周波数の切分け | まずcodec・周波数・入力・効果等を固定してbitrateだけを比較し、別に周波数と再サンプリングの影響を比較する。48kHz・32kbpsと24kHz・16kbpsの直接比較だけで、差をbitrateだけの影響としない。端末入出力、mixer、codec、RTC、出力までのformatと変換を追えることを条件にする |
| 実通信の負荷 | 音声payloadだけでなく、ヘッダー、暗号化、制御情報、該当経路で発生する冗長化・再送等を含む送受信量を測る。Local／Internet／混在、人数、発話中・無音時、通信条件を記録する。codecの設定bitrateをそのまま回線に必要な通信量と扱わない |
| 聞こえと通話の品質 | 同一音源に加え、実機のマイク・スピーカーで明瞭度、短い相槌、話頭・語尾、雑音下の聞き取り、波形差、欠落・クリック、遅延を確認する。波形維持を求める推奨と、圧縮・帯域制限の劣化を許容する低帯域推奨を別々に判定し、配送・再生の不具合を許容する理由にはしない |
| 推奨として残す情報 | codec・周波数・bitrate・音声処理、適した通信条件と人数、実通信量、許容する聞こえの変化を記録する。現行波形を維持する推奨と低帯域用の推奨下限を両方残し、一般向けに目的と選び方を分かりやすく説明する |
| 遅延・電力との両立 | 通信量を減らすために音声をためて遅らせず、既存の連続性・標準設定の遅延要求を維持する。低帯域側の遅延・変換負荷・電池消費も別途測り、最小bitrateだけで採否を決めない |

依存順は、現行推奨・基準波形の保持 → codec・OS・周波数別の成立条件整理 → 必要なpackage変更と単独検証 → App側の設定選択と共通IFへの反映 → 自動比較・実通信量測定・実機での試聴 → 現行品質と低帯域の推奨値・適用条件の確定とする。package変更とApp追従は別工程とし、設定値だけ先に広げて対応済みとしない。認証・課金・iCloudとは並行でき、一般向け画面の追加前に抽象化する操作・状態IFには、採用候補の設定値と実適用結果を渡せる境界を整理する。

| silent push | [背景通知](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)は配信保証がなく、遅延・抑制がある。これを常時の呼出し待受や即時接続保証にしない | 届かなくても既存Local通話を止めず、通知サーバー不達を通話資格の失効へ変換しない |
| PTT / PushKit | PTT tokenは参加channelの寿命に依存する。未参加者への一般的な呼出しを置き換える根拠にしない。[PushKit](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit)を採用する場合はCallKitで着信を報告する。通常通知を希望する要望は維持し、単なる起動用にPushKitを使わない | 方式が必要になった時点で着信UI、音声sessionの所有、中断・終了を実機確認。現時点では採用済みにしない |
| ショートカット・Siri・Widget | 通話先（ユーザー／グループ）、開始、指定した通話の終了、明示的なマイク状態設定を共通操作にする。AppEntityに鍵・購入証明・全保存モデルを露出しない。[supportedModes](https://developer.apple.com/documentation/appintents/appintent/supportedmodes)等で前面移行を設計し、背景実行の指定だけで録音開始が保証されるとみなさない | 相手削除、古いWidget、同時実行、ロック解除が必要な場面、起動前後の引継ぎ、権利不足、別通話へ切替後に届いた終了を検証。二重toggleで逆転しないよう「ONにする／OFFにする」を渡す |
| 音声操作用Intent | [AudioRecordingIntent](https://developer.apple.com/documentation/appintents/audiorecordingintent)には録音中のLive Activity維持という条件がある。通話の背景起動手段として無条件に流用せず、上部表示OFF・長時間通話との整合を先に確認する | 上部表示OFFでも通話要件を保てる方式を選ぶ。録音Intentの採用で必須になる表示を、利用者設定で隠せると説明しない |
| 上部表示 | Live Activityは任意の通話状態表示として扱う。8時間の上限、利用者による終了、表示OFFを通話終了へ結び付けない。相手名のロック画面表示は必要最小限にする | Dynamic Island対応・非対応、表示OFF、OS側無効化、8時間経過、通話だけ継続する場合を確認。終話操作の手段を表示だけへ依存させない |
| CarPlay | [WidgetKit](https://developer.apple.com/documentation/widgetkit/adding-standby-and-carplay-support-to-your-widget)の小型Widgetではtouch有無で操作可否が違う。専用CarPlayアプリの起動とWidgetのボタン操作を区別する。Live Activityは表示用途とし、そこへ開始・終了操作を割り当てない | touch対応・非対応のスマートモニターで対象と可否を表示。Widgetの操作成立をCarPlay Simulatorと実機で別に確認。専用アプリが必要な場合はentitlementと対応カテゴリの条件を満たす |
| Watchの操作 | [WCSession](https://developer.apple.com/documentation/watchconnectivity/wcsession)でiPhoneへ操作要求を送り、実行結果を受け取る候補。即時messageには到達性が必要で、背景転送は即時ではない。遅れて届いたマイクONや開始を実行しないよう、対象通話・要求ID・期限を持たせる | iPhone到達可／不可、Watch画面消灯、途中切断、再接続、同時操作、結果未確認の表示を検証。送信成功だけでマイクONと表示しない |
| Watchの音声 | 操作転送と連続音声を別経路として設計・実証する。[TN3135](https://developer.apple.com/documentation/technotes/tn3135-low-level-networking-on-watchos)は低レベル通信を音声streaming中やCallKit通話等に制限し、BSD socketsを非対応とする。Watch Connectivityを連続音声配送の代用に決めない | iPhoneに依存する構成でWatchのマイク・出力を扱えるか実機試作が必要。Simulatorは低レベル通信制限を再現しない。iPhone不在時の停止理由、再接続時に送話を勝手に再開しないこと、無音・画面消灯・Bluetooth切替・長時間の電池消費を測る |
| macOS・iPad | 共通の権利・ユーザー・通話先・操作は維持。iPhone固有の表示・Watch連携の成立を他OSへそのまま適用しない | 各targetのAPI availabilityとUI、通知応答、音声中断・復旧を個別確認。現行のmacOS支援を後退させない |

資料上の制限と、RideIntercomでの方式選定を分けている。先行調査の到達点は、通常通知を第一候補にできる範囲と、CarPlay・上部表示・Watchの成立条件を特定したこと。Watch音声、OSによる背景起動、実機の長時間動作は未確認であり、機能完了・対応保証ではない。必要な実機と受入時間を揃えて後続の試作で確認する。

## 公開前に決めることと残す受入条件

| 対象 | 具体化する内容・必要な証拠 |
|---|---|
| 価格と提供価値 | 金額、販売地域、試用・無料配布の具体的な期間、付与するグループ数・人数・同時利用を確定する。期間の意味、重複・切替、返金・失効時の権利は課金連携前に決めた内容と一致させる。有料権利が現行のサービス利用枠や費用上限を解除するかは別判断とし、無制限利用を暗黙に約束しない |
| 一般向けの購入・復旧 | 購入済み、購入待ち、取消、権利不明、失効、復元失敗、24時間経過を区別し、次に何をすればよいか表示する。価格が未決でも権利状態と画面の設計は先に行える |
| 判定表と状態遷移 | 権利の出所×有効性×グループ関係×操作種別の判定表を作る。完全終話の前後、最後の購入者ありの開始から24時間直前・ちょうど・直後、未購入者だけの再開で期限が延びないこと、継続中に24時間を超えても切断しないことを確認する。購入者が不在・失効・復帰する場合、複数購入者、無料ユーザーだけの1対1も含める。採用していないルールの期待値は実装者が推測しない |
| 経路と環境 | Localのみ、Internetのみ、混在、圏外、サーバー障害、時計変更、開始時刻の不一致、再インストール、ログイン変更、複数端末、TestFlightと製品版の混在・切替、旧版接続について、許可・拒否・復旧の期待結果を定める。開発試験の限定迂回と、迂回なしの権利判定をそれぞれ確認する |
| 画面IFと両系統の画面 | ユーザー一覧・グループ一覧の変更が両系統で同じデータに反映されること、特定ユーザーとの通話が一般向けでは内部グループの操作なしで完了することを確認する。既存画面とDiagの情報・操作を維持し、両系統と外部入口で通話先・権利判定・実行結果が一致することも確認する |
| 操作と通知 | 通知拒否、遅延・重複、応答前の取消、通話中の着信、ロック状態、対象削除後のウィジェット、SiriとWatchの同時操作を確認する。呼出し通知の配送と、相手の応答・実音声到達を別の成功条件にする |
| 音声・節電・実機 | 低bitrateの圧縮劣化と配送・再生の不具合、設定統一の節電、Watchの継続時間を別に判定する。ソースと条件を残した自動検証に加え、iPhone・Watch・車載機器での実機確認を必要な項目へ割り当てる |
| 運用と削除 | 端末の購入状態・期限と最後の購入者ありの開始時刻の保存・共有、問い合わせに必要な最小記録、通知の失効・濫用抑止、無料配布の管理、アカウント削除、費用監視と障害時の対応を整理する。保守・運用・通信・処理の増分を確認し、独自の定期検証や個人情報不保持に反する記録を「運用のため」で自動追加しない |

実装着手の判断には、該当機能の未決事項への回答、データ保持表、権利・操作判定表、通話の状態遷移、OSごとの成立条件、受入条件が必要になる。全機能の価格・公開日が決まるまで独立した調査を止める必要はないが、未決の前提に依存する実装は進めない。packageの変更が必要な箇所は[開発方針](../policies/開発方針.md)に従いpackage単独で検証してからAppを追従させる工程に分ける。
