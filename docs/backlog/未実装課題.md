### 近距離制御のMultipeerからの移行

**区分:** 機能（基盤移行）。
**状態:** Network.framework＋peer-to-peer Wi-Fiを採用決定済み。RTC packageの実装・検証は未着手。以下のプロトコル選定理由、移行条件、保留候補を維持する。

2026-11-02の追加依頼。Xcode 27 SDKでMultipeerConnectivity全体が非推奨となった（[TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework)。各APIは「Deprecated in iOS 27.0」、移行先はNetwork.framework）。削除ではないため現行のbuild・動作は継続するが、今後の修正は期待できない。同日に代替手段を調査し、利用者の回答で方針を決めた。今回は記録だけを行い、実装・テストには着手していない。

現在MCSessionが担うのは、探索・招待、暗号化必須のsession、handshake・presence・操作のreliable配送だけである。Local音声は既にNetwork.frameworkのUDP（`includePeerToPeer = true`）で送っている（[RTC仕様](../spec/packages/RTC.md)）。TN3213は、Apple peer-to-peer Wi-FiがMultipeer専用ではなく、Network.frameworkからも使えることを明記している。移行後も、AP・セルラーがない屋外の近距離通話（[製品要求](../requirements/製品要求.md)）を同じ無線で成立させる。最低対応OSが27.0のため、iOS 26で追加された`NetworkListener`・`NetworkBrowser`・`NetworkConnection`をavailability分岐なしで使える。

| 代替手段 | 判断 |
|---|---|
| Network.framework＋peer-to-peer Wi-Fi | 採用。iOS/macOS両対応で、端末の組ごとのペアリングが不要。既存のUDP媒体と同じ基盤 |
| Wi-Fi Aware＋DeviceDiscoveryUI | 第1段階は不採用。対応機種と端末の組ごとのペアリングが制約になる。[改善候補](改善候補.md#近距離通信の追加経路と統合)へ置く |
| Core Bluetooth | 第1段階は不採用。音声主経路には帯域・距離・遅延が不足し得る。補助経路として後から検討する（[改善候補](改善候補.md#近距離通信の追加経路と統合)） |
| Nearby Interaction、GameKit、SharePlay、インターネット共有 | 対象外。音声・制御のデータ経路にならない、Multipeer系の旧方式である、またはAP・Internet不在の要求を満たさない |

| 論点 | 2026-11-02に決めた方針 |
|---|---|
| 制御protocol | QUICを使う。handshake・presence・操作をQUICのreliable streamへ移し、message境界はframingで保つ。64 KiBの受信上限など現行のLocal制約を引き継ぐ |
| 暗号化と認証 | TLS-PKIを基本路線とする。端末ごとに一時的な自己署名identityを生成してmutual TLSを張る。相手証明書はTLS層の信頼評価では受け入れ、既存のgroup共有鍵によるhandshake MACへ証明書fingerprint等を含めて通信路へ束縛し、そこで認証する。Apple OSにidentityの生成APIがないため、生成手段（swift-certificates等の外部依存か、最小の自前生成か）と束縛の具体方式は着手時に決める。TLS-PSKは旧APIだけの機能で、TLS 1.3とQUICに対応しないため使わない |
| 接続の形 | 届く相手とはすべて直接接続する部分メッシュとし、全員が直接届くことを前提にしない。隊列で先頭と最後尾が直接届かない場合も、既存の[重複破棄付き転送（最大8hop）](../spec/packages/RTC.md#混在通話と経路)で中間の端末が中継する。特定の端末をserverにするclient-server構成は、その端末の離脱や隊列内の位置で全体が切れるため採らない。同じ相手との重複接続はpeer IDの比較で片方を閉じ、既存の[招待競合の回避](../spec/packages/RTC.md#近距離接続試行の競合回避)の辞書順を引き継ぐ |
| 探索とプライバシー | 最低限とする。`NetworkListener`でBonjour serviceを広告し、TXTには現行と同じgroupHashを載せる。自動接続のため、service名には端末名を使わず通話世代ごとの識別子を使う。識別子のrotation等の追加対策は、利用規模・利用場所から現時点では行わない |
| 音声 | 第1段階は既存の`_ride-audio._udp`のUDP媒体を維持し、UDP媒体用のnonceを新しい制御経路のhandshakeから渡す。QUIC datagramへの統合は[改善候補](改善候補.md#近距離通信の追加経路と統合)とする |
| 旧版との互換 | 維持しない。Multipeer版と新版の混在通話は不可とし、同じ版同士で使う。利用者の操作・表示（Settingsの近距離ON/OFF、接続・切断、経路の表示）は変えない。保存済み設定の`RouteKind.multipeer`は名前を変えずに読むか、[移行の対象・条件・復旧](../policies/開発方針.md#技術選定方針)を定めてから変える |
| 電力 | 第1段階はTN3213の基本どおりとする。通話停止で探索・listener・connectionを破棄し、途中参加・再発見のために通話中は探索を維持する現行の扱いを引き継ぐ。Bluetooth併用等の省電力・補助経路は後から検討する |

**完了条件**:

- RTC packageの独立工程として実装・検証してからAppへ接続する。RTCから`MultipeerConnectivity`のimportをなくし、Multipeer専用の回避策（CFNetwork初期化、MCPeerIDの63 byte制約、MainActorでのnative資源の所有）を不要になった範囲で除く。
- 既存のLocal契約を新しい経路で維持する。対象は、handshake拒否と`connectionFailed`の区別、旧session通知の拒否、制御切断時の再handshakeとUDP媒体資格の保持、Local優先、経路変更・backoffである。既存のLocal関連テストを移植して全件成功させ、件数を減らして合格にしない。
- 隊列の形を自動試験する。直線に並んだ4端末（A–B–C–D。A–C、A–D、B–Dは直接届かない）の仮想経路で全方向の音声が中継で1回ずつ届くこと、中間端末の離脱で分断し、復帰後に自動合流することを確認する。

### アカウント削除のサービス範囲と別端末への反映

**区分:** 機能。

**状態:** 端末内の削除・再認証・server資格失効・稼働媒体回収は実装済み。削除対象の公開サービス範囲、同じ端末の別sessionと他の本人端末への反映は未完の判断・動作として残す。実Apple認証・実サービスの回収時間は[未確認事項](../validation/未確認事項.md)で受入確認する。

- 仮置き：この端末に公開Internet資格がなければ「この端末のデータ削除」とApple手動解除を提供する。任意URLで別端末が使った未知サービスのアカウントまで発見できない。公開版のサービス固定・サービス履歴／再認証からの削除先解決を確定し、どこまで削除するかUIと契約を揃える。現在のLocal通話・開発用手動資格を削除機能のためだけにInternet登録へ強制移行しない。
- 同じ端末の保存領域を使う別sessionのサインアウト／削除は、前面復帰・背景開始操作とApple確認復帰時の再読込で反映し、保持済みの旧ログインを失効させる。すでに継続中の別プロセスへの即時通知、別の本人端末と共有済みの相手端末への反映は引き続き未完了。端末内の旧repository書戻し拒否と、遠隔の媒体・通知・招待権限失効は同じ完了条件ではない。通知・利用権は共通処理へ接続済みであり、これらについても別端末への削除反映と実サービスの受入を確認する。

[Widget・Control・任意のLive Activity](../spec/App/システム表示と通話操作.md)は共通通話操作へ接続済み。上部表示のON/OFF・名前なし投影・古い終了拒否を実装した。OSによる手渡し・実表示は[未確認事項](../validation/未確認事項.md)へ移し、特定宛先Widgetも実装し、選択用App Group投影とAppでの再認可へ接続した。CarPlay Widgetの背景操作は現行仕様へ移し、車載の実受入を維持する。Watch音声はiPhone依存の媒体経路と押下／通常マイク操作を接続した段階であり、Watchからの開始→native入力→iPhoneでの処理・録音→Watchのnative再生のSimulator E2Eは未完。通常マイクONをinactiveだけで解除する実装は[回帰修正済み](../validation/history/Watch音声のApp接続とデバイス分離.md#通常マイクonをinactiveで維持する回帰修正)だが、実機の手首暗転と音声継続の対応は未確認。実機の遅延・電池消費等とは分けて、実行可能なコア経路を先に閉じる。[入力と再生の現在の検証範囲](../validation/history/Watch音声のApp接続とデバイス分離.md#iphone設定の5秒録音と有限配送)を参照する。

## インターネットとローカル接続での招待・削除同期

表示・操作・同期状態のデザイン判断は[招待・削除同期と呼出しのUI・UX課題](改善候補.md#招待削除の同期と個人登録相手への呼出しのuiux)で追跡する。

**主分類:** 機能。**関連分類:** 改善・デザイン。**状態:** 2026-11-04の利用者要望を記録。設計・実装・検証は未着手。個人招待の修復と通知・関係削除に関連する課題として追跡する。

招待だけでなく、個人の削除、グループ自体の削除、グループからのメンバー削除も同期する。インターネット・ローカルのいずれでも、相手との利用可能な接続経路があれば同期する。インターネットや通話の開始をローカル同期の前提にせず、両経路で同じ意味の変更を反映する。招待・削除のために無理にRTCを使う現行実装は見直し、通話やRTCの接続成立を同期の前提にしない。サーバーには一次情報だけを保存する方針を維持し、端末の一覧全体を永続的に複製する方式ではなく、同期に必要な招待・削除の情報を一時保持する。一次情報と配送用情報の具体的な範囲は、既存の[データ保持設計](利用権とデータ保持の設計.md#データ保持表)と照合して設計時に明確にする。

| 対象 | 求める動作・保持条件 | 受入条件・残る判断 |
|---|---|---|
| 招待の配送 | 相手がオフラインでも一時的に招待を預かり、インターネットまたはローカル接続時に受け取れる | 送信側・受信側の接続順、再接続、アプリ再起動、重複取得を含め、RTCの通話接続なしに反映できる。既存の[通知と招待配達](#通知とアプリ外からの通話操作)と責務・配送経路を揃える |
| 相手削除の双方反映 | 相手が自分を削除したら、自分側の相手一覧からも相手を削除する。削除時に相手がオフラインでも、後でインターネットまたはローカル接続した際に削除を受け取れる | 削除した側で即時に関係と不要な通知を止め、受取側も削除を適用する。削除済み関係を使う呼出し・招待等の不要な通知が飛ばないことを確認し、端末内の表示だけでなく通知の認可・配送待ちとの整合を取る |
| グループ削除・メンバー削除 | グループ自体の削除と、グループから特定メンバーを削除する操作も、権限に従って関係端末へ同期する。2026-11-06の利用者決定: 実行できるのは利用権を持つ人（課金者。グループ作成と同じ共通判定）。持たない人は自分が抜けるだけ（[削除できる人](../design/招待と登録の設計.md#削除できる人)） | 個人の削除と対象・影響範囲を区別し、対象グループの削除、または対象メンバーの除外が各端末へ反映される。削除済みグループ・除外済みメンバーへの不要な通知を止め、古い招待で復活させない。端末内だけの一覧整理との違い、実行できる権限と通話・参加資格への効果を設計時に明記する |
| インターネットとローカルの共通同期 | インターネットのみ、ローカルのみ、両方ある場合、経路の切替後でも同じ招待・削除を反映する | オフライン中の変更を保持し、再接続時に反映する。両経路からの重複・順序逆転でも一度適用した削除を戻さず、確認状態を整合させる。ローカルで確認済みの削除をサーバー経由で再取得しても復活させない |
| 一時保持と確認 | 削除を受取側が確認するまではサーバーへ残してよい。同期用データの保存期限は暫定28日とする | 受取側が削除を適用して確認を返す経路と、確認後の回収を設計する。未確認でも保存期限は28日とし、起算点・期限切れ時の扱い・複数端末での確認単位は設計時に明記する。28日を超えてオフラインの端末への確実な配送は未解決条件として扱う |
| 新しい人のグループ招待 | 2026-11-06の利用者指示（グループに誰かを招待したい意図は、相手が登録済みでも新規でも同じ）による設計（[グループへの招待](../design/招待と登録の設計.md#グループへの招待)）。登録済みの人へはグループを自動で届け、新しい人へは名前を付けた招待を送る。新しい人への招待は個人の登録とグループへの参加を兼ね、受け入れるとお互いのユーザーにも入る | 1つの招待で個人の関係とグループの鍵の両方を渡す形式、受け入れの順序、片方だけ成立した場合の扱い、宛先のないグループのリンクとの関係（Standardから外しAdvancedに残す）を設計する。登録済みの人への配達と新しい人の招待のどちらでも、送った側の表示が「招待中」から参加へ同じ語で進むことを確認する |
| 削除と古い招待の競合 | 削除後、遅れて届いた古い招待・返信・再送で削除済み関係や通知許可を復活させない | 順序逆転・重複・確認応答の喪失を再現して確認する。削除後の新しい明示的な再招待と古い配送待ちを区別する。本人と対象の認可、必要な暗号化・署名を保ち、第三者による削除を防ぐ |

2026-11-06の利用者決定: 1対1で接続中の相手を削除した場合は、その接続を切る。削除する側には、接続が切れることを確認のダイアログで示してから実行する（[接続中の相手・グループを削除するとき](../design/招待と登録の設計.md#接続中の相手グループを削除するとき)）。

今回の削除同期は、個人との招待・連絡先関係、グループ自体、グループからのメンバー削除を含む。アカウント全体の削除とは区別する。既存の「ユーザー一覧からの削除後も通常グループ・通話は維持する」という契約との関係、個人間専用グループ・実行中の個人通話・同一本人の複数端末への反映は、要求の差分として実装前に整理する。現行仕様を変更済みとは扱わない。同期待ち・削除反映・期限切れなどの表示が必要になれば、[デザイン引継ぎ規則](../policies/開発方針.md#機能実装とデザイン判断の引継ぎ)に従いデザイン残項目へ判断材料を残す。
