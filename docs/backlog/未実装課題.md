# 未実装課題

実装する必要がある残作業。現在の動作は[仕様](../spec/アーキテクチャ.md)、実装後の確認待ちは[未確認事項](../validation/未確認事項.md)を参照する。

| 課題 | 現状との差・対象 | 完了条件・制約 |
|---|---|---|
| 公開identity・端末資格管理 | Workerの個別端末registryは招待制試用向け（約4.5KiBまで）。公開登録・自動発行・失効を行うidentity backendがない | SFU transportとgroup招待形式を維持して入口認証を拡張する。本人確認・資格発行・失効を公開運用できること |
| 公開時のabuse・請求監視・停止運用 | SDP制限と参加者秒予約だけでは改変クライアントの過剰送信を金額で遮断できない | edge rate limit、実egress計測、請求通知、障害時停止運用を整備する。実運用の効果は検証側で確認する |

RTC診断とTURN資格lifecycleはこの一覧の実装作業ではない。現在の契約は[RTC](../spec/packages/RTC.md)・[Worker](../spec/server/Worker.md)、実サービス受け入れは検証側が所有する。

音声の連続性の実装修復と28測定の結果は[修復記録](../validation/history/音声の連続性修復.md)へ移した。物理iPhone同士の最終確認は検証側で管理する。

## 今後追加する機能と利用体験

2026-10-30の追加要望。今回はやることの記録だけを行い、実装には着手しない。以下は現行仕様や実装済み機能ではなく、着手時に設計・対応条件を確認する課題である。電池消費への効果を条件に採用する設定統一は[改善候補](改善候補.md#電池消費を条件に判断する案)へ分ける。

### 低ビットレートの許容

| 課題 | 目的・範囲 | 完了条件・確認点 |
|---|---|---|
| 低ビットレートでの通信を許容する | 通信量を抑えるため、低ビットレートによる音声波形の変化・劣化を許容できるようにする | 同じ入力・codec・周波数・音声処理条件でビットレートだけを変えて比較し、波形の崩れがビットレートの影響だけであることを確認する。通信なしのcodec往復と実通信の結果を照合し、音声処理や配送による欠落・不連続を低ビットレートの影響として扱わない。許容する範囲と確認方法は着手時に定める |

### ユーザー管理と一般ユーザー向け画面

| 課題 | 目的・範囲 | 完了条件・確認点 |
|---|---|---|
| ユーザーをグループと分けて保持・管理する | グループとは独立してユーザーを残し、既存ユーザーをそのまま使ってグループを追加・構成できるようにする | グループの削除でユーザー情報を失わず、同じユーザーを登録し直さずに別グループへ追加できる。ユーザーの保持、グループへの所属、通話の認証を区別して設計する |
| 一般ユーザー向け画面と個別発信を用意する | 現在の画面をアドバンスド・管理者向けとして位置づけ、一般ユーザー向けの画面を用意する。まずは英語でよい | 1対1のユーザーへの発信をグループ通話と分けて管理・操作できる。内部処理は同じグループ通話の仕組みを使ってよい。ユーザー管理と連携し、利用者が個人とグループを区別して通話先を選べる |
| 一般ユーザー向け画面を英語・日本語に対応させる | 英語で用意する一般ユーザー向け画面だけを日本語に翻訳できるようにする | 英語版の作成時から翻訳可能にし、その画面の日本語翻訳を揃えた時点で一般ユーザー向けの英語・日本語対応を完了とする。アドバンスド・管理者向け画面の日本語化は今回の対象に含めない |

### 通知とアプリ外からの通話操作

| 課題 | 目的・範囲 | 完了条件・確認点 |
|---|---|---|
| ユーザーへ通知し、通信起動までつなげる | Push to Talkでの通知が適さない可能性があるため、通常のメッセージ通知で相手を呼び出し、通信を起動する導線を用意する | 通知の送信・受信、応答、通信起動までの流れを確認する。通知到着だけで起動できる範囲と、タップ・応答など利用者操作が必要な範囲をOSの条件に照らして確認し、方式を決める |
| 会話の開始・終了をウィジェット化する | 特定ユーザー、特定グループ、最後に会話したユーザーまたはグループへの開始・終了を操作できるようにする | 指定先と直近の通話先をそれぞれ扱い、対象を確認して開始・終了できる。「最後の相手」の保持方法と通話先切替時の挙動を設計する |
| CarPlayでスマートモニターに対応する | 車載のスマートモニターから通話を操作できるようにする | ウィジェット等で用意する開始・終了操作を踏まえ、CarPlayで利用できる表示・操作・対応条件を実装前に確認する |
| iPhoneなどの上部表示で通話状態を可視化する | 画面上部で通話状態を確認できる表示機能を追加する | 対応する表示領域とOSの仕組みを確認し、可視化を設定でON/OFFできるようにする |
| ショートカット・Siri向けAPIに対応する | 通話操作をショートカットやSiriから呼び出せるようにする | 特定ユーザー・グループと直近の通話先に対する開始・終了を含め、公開する操作と対象指定方法を設計し、アプリ内操作と同じ意味で実行できることを確認する |
| iPhoneに依存するApple Watchでの操作・通話を用意する | 基本的にすべてiPhoneへの依存を前提とし、Apple Watchから呼び出し・応答・通話を行い、長時間利用できるようにする。Apple Watch単体で動く必要はない | トランシーバーの代わりに使える程度の体験を目指すが、トランシーバーそのものの再現を前提にしない。iPhone連携での操作・音声経路・継続動作と電池消費を確認する。タップでマイクをONにする操作も希望として検討する |

背景として挙がった「watchOS 27でトランシーバーがなくなった」という認識とPush to Talkの通知制約は、この記録では調査・確定していない。対応OSとAPIの可否は着手前に確認する。
