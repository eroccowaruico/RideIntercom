# 一般向け招待と利用制限・料金の見直し

## 指示と背景

2026-11-01の利用者報告と追加要望を記録する。一般向け画面の招待・共有と招待成立前の表示を修正し、一般利用でも復旧と通信経路の選択ができるようにする。利用制限は事故や復旧不能を避け、独自の台帳・監視・状態管理を増やさない。家族利用と少人数通話を含めて費用を見直し、利益を過度に求めず、赤字を避けられる料金を決める。

本書はバックログであり、報告の再現確認、機能修正、Apple機能の適合確認、価格決定は未実施。現在の動作は[Call画面](../spec/App/UI/Call.md)、[通話利用権](../spec/App/通話利用権仕様.md)、[StoreKit利用権](../spec/App/利用権仕様.md)を参照する。既存の[利用権とデータ保持の設計](利用権とデータ保持の設計.md)や[製品要求](../requirements/製品要求.md)との差は、実装着手時に整合させる。

## 一般向け画面の招待と復旧

| 課題 | 報告・求める動作 | 完了条件 |
|---|---|---|
| 一般向け画面から招待できない | 一般向け画面でも相手を招待できるようにする | 招待可能な権利・ログイン・対象の条件で入口から招待へ進める。権限等で実行できない場合は理由と次の操作を示す。Advancedへ切り替えることを通常の招待手順にしない |
| 一般向けの招待で共有ダイアログが出ない | 招待操作からOS標準の共有ダイアログを開く | 招待内容を渡して共有先を選べる。共有取消・共有失敗・再試行を確認する。共有完了だけでは相手を識別できず、相手の参加も分からないため、招待成功とは扱わない |
| 招待レコードを参加前に相手として見せてしまう | グループ招待も含め、招待成功は相手の参加成立とする。通常の相手・参加者レコードを出すのは参加成立後にする | 相手が招待を使って参加し、参加した相手を識別できた時点でユーザー／メンバーのレコードを確定する。URL発行・共有完了・受諾操作だけでは確定しない |
| 人数・招待枠の都合で事前表示が必要な場合 | 未成立のレコードを出す必要があるなら、その場に共有ボタンを出せるようにする | 未共有・招待待ち等の状態と操作を明示し、いかにも既に相手がいると思わせない。予約枠・招待中・参加済みの人数を混同しない。人数制御を口実に参加済みの見た目へ揃えない |
| 一般向け画面の設定リセット | 一般向けでも設定をリセットできるようにする | 標準の確認操作で実行でき、対象と影響が分かる。「設定のリセット」を理由に、ユーザー・グループ・資格など別の保存データまで無断で消さない。既存の保存データ復旧／リセットとの範囲を整理する |
| 一般向け画面の通信経路切替 | MultipeerとInternetの利用を一般向けでも切り替えられるようにする | 各経路の利用可否を設定でき、表示・保存・実処理が一致する。通話中の変更や、利用可能な経路がなくなる場合の案内・動作も確認する。詳細な診断画面の利用は前提にしない |

招待の表示は、直接の相手招待・グループ招待の双方を対象とする。2026-11-01の補足で、共有しただけでは相手が分からず、参加しなければ招待成功として意味を持たないことを確認した。参加成立に合わせて通常の相手・参加者表示と確定保存を行う。人数・招待枠の都合による参加前の表示は、上表の招待待ち表示と共有ボタンの例外として扱い、既に相手がいるようには見せない。[既存の直接招待関係](利用権とデータ保持の設計.md#グループ内の関係とグループ外操作の境界)の認可を、共有ダイアログの完了だけから広げない。

## 制限と無料利用を簡単にする

| 課題 | 利用者の意図・候補 | 検討・受入条件 |
|---|---|---|
| 同時通信の制限単位を見直す | 1ユーザー1通信が好ましいが、厳しくロックすると事故が起きそう。1端末1通信、同一ユーザーは2端末程度までを落とし所の候補にする | 「2端末程度」は今回の候補であり、確定済みの数値・実装済み上限にしない。同一端末の二重通信、端末切替、クラッシュ・通信断・古い予約残りを、少ない状態管理で扱える方式を比較する |
| 他で通信中の場合は後からの操作で復帰する | 「他で通信中」と拒否されるだけでは苦しいため、新しく開始した側を優先する | 後勝ちの切替先・終了対象を定義し、古い接続の自動再接続と奪い合わない。新しい側が開始できず解除操作にも進めない袋小路を避け、旧側には終了・切替理由が分かる。独自の厳密な端末間lockや大きな管理基盤を追加することを前提にしない |
| 24時間条件の管理を簡素に保つ | 24時間の制限も、あまり管理しない実装にしたい | 既存の起算点と再開判定・保存情報を確認し、独自の履歴台帳、常時監視、毎日の照会・手動確認を増やさない。起算・失敗・再開・通信断で期限を不必要に延長しない。今回の要望だけで24時間の意味や起算点自体を変更しない |
| 無料招待・無料配布にApple機能を使えるか確認する | 無料招待はAppleで実現できるなら、その方式でもよい | 既存の[無料配布方式](未実装課題.md#無料配布方式の確認待ち)へ関連づけ、Offer Codes等が必要な無料利用を満たすか確認する。Apple機能利用への条件付きの許容であり、特定機能の採用・対応済みを意味しない。相手／グループの招待共有と、無料利用権の配布を混同しない |

現行の[製品要求](../requirements/製品要求.md)は「同一ユーザーのWebRTC接続を原則1端末」とし、[既存課題](未実装課題.md#appleでのログインと通知先の識別)には旧通話を残して追加側を拒否する実装が記載されている。今回の2端末程度・後勝ち候補は、その制約を見直す課題として扱う。現行の仕様が既に後勝ちであるとは書き換えない。Multipeerを含む「1端末1通信」の対象と、serverのWebRTC予約制限との関係も整理する。

24時間は[通話利用権の再開猶予](../spec/App/通話利用権仕様.md)の簡素化課題として扱い、設定で選ぶ自動切断タイマーとは区別する。複雑さを減らすという[既存の設計方針](利用権とデータ保持の設計.md#後続へ渡す最小構成)と照合する。

## ファミリー共有と料金の再見積もり

| 課題 | 求める方針 | 完了条件 |
|---|---|---|
| 家族が使えるアプリ内課金にする | ファミリー共有を有効にし、家族で利用できることを前提にする | 商品別のApple対応・App Store Connect設定・StoreKit側の権利反映・復元を確認する。4人家族全員が利用するケースを受入と予算へ含める。4人全員が別々に購入する収入を前提にしない |
| MacとiOSの課金を共有する | Mac版もiOS版と同じアプリ内課金の共有でよい | OS別の二重購入を前提にせず、両OSで同じ購入・ファミリー利用権を認識・復元できる商品構成と運用を確認する。端末数・同時通信数の制限とは分ける |
| 少人数利用を含めて費用を見直す | 2人通話も相当数ある想定とし、グループ人数は平均4人を基準に見積もる | 2人通話、4人の平均ケース、4人家族全員の利用を比較する。平均4人という全体前提と2人通話を含めた分布・比率の置き方を明記し、従来の人数前提のまま金額だけ決めない |
| コストに見合う価格を決める | 利益重視にしすぎず、それでも絶対に赤字にならない程度のコスト見合いで課金額を決めたい | [既存の費用試算](../development/Cloudflare費用試算.md)を、家族共有・OS間共有・購入件数と実利用者数の差を含めて再計算する。利用時間、経路・通信量、基盤費用、販売手数料等の前提と上振れ時の余裕を明示し、原価・赤字を防ぐために必要な範囲・価格候補の根拠を示す。赤字回避に必要な利用量の想定範囲や費用上限も決め、価格だけで未定の利用量まで保証した扱いにしない |

既存設計には[週券は個人用・月額はファミリー共有](利用権とデータ保持の設計.md#購入の復元ユーザー切替とファミリー共有)という整理がある。今回の「家族で使える課金」の要望に対し、各商品の共有範囲・提供方式を照合して必要な見直しを行う。Appleで可能かを確認する前に、全商品が既に共有できるとも、週券は今後も必ず共有対象外とも決めない。購入の独自台帳を増やす解決を既定にしない。

価格・商品構成・平均人数の変更は本書への記録だけでは現行試算へ反映済みにならない。再見積もり時に前提・計算・価格候補を更新し、無料招待と24時間猶予による購入件数と利用量の差も含めて確認する。

## 一般向け画面のデザインは後続

一般向け画面は最終的にデザインが必要。iOS標準のコントロールを中心にしつつ、色・配置などを整える。今回は後回しとし、招待不能・共有ダイアログ・誤解を招く状態表示・必要な設定操作の修正をデザイン完成待ちにしない。診断情報を増やして一般向け画面の分かりやすさを損なわない。
