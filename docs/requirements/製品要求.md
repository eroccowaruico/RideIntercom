# 製品要求

## 目的と背景

RideComは、スキー、スノーボード、ツーリング、ドライブなどで、仲間と気軽に通話を楽しむためのiOS/macOSアプリである。音楽を聴きながらグループで同時通話を続ける。カメラを使う撮影やビデオ通話は提供しない。iOSを主対象とし、macOSにもデスクトップとして使える体験を求める。近距離とInternetが混在する移動中でも、接続経路がある限り手動の繋ぎ直しを減らす。少人数の試用から公開へ進められること、従量課金による費用増大を抑えることを重視する。

本書は統一して満たす目的・価値・品質を定める。達成状況や作業一覧は持たせない。製品の要求と、[開発方針](../policies/開発方針.md)・[文書作成規約](../policies/文書作成規約.md)の作り方の要求を区別する。

## 利用者に提供すること

| 要求 | 背景・期待する結果 |
|---|---|
| ログインして自分の通話情報を使う | すべての通話でAppleログインを必須とし、メール・本名を要求しない。ログイン済み端末は圏外でも近距離通話を使い、別アカウントのユーザー一覧・グループを混在させない |
| 同一ユーザーのWebRTC接続を1端末にする | 複数端末へ同じユーザーでログインしていても、WebRTC接続はユーザー単位で原則1端末に限る。端末やグループを変えて通常の同時接続を増やせないようにする。障害回避・復旧のための一時的な2端末接続には検討余地を残すが、常用の複数接続は提供しない |
| 本人の名前と自分の呼び名を分ける | 本人が好きな表示名を設定して相手へ伝えられる。サインイン後に名前を一度も設定していなければ、最初に名前の入力を求め、未設定の既定名のまま仲間へ伝えない。受け取り側は本人の名前を確認・保持したまま自分用の呼び名に変更でき、本人の名前へ戻せる。呼び名の編集は他端末へ配信せず、グループ内だけの関係をグループ外の操作権限へ変えない |
| グループで同時通話できる | 招待して同じグループへ参加し、認証済みの相手と会話できる |
| 閲覧と通話先変更を区別する | 別グループを見るだけで通話を切らず、接続先の変更は明示的に行える |
| 選んですぐ接続し、通知から応答できる | 接続していない間に相手・グループを選ぶとそのまま接続を始め、別の画面で改めて接続操作を求めない。接続中に別の接続先を選んだ場合は切替を確認する。グループ通話中はその画面から人を追加できる。呼び出しの通知から接続でき、接続を選んだ後に重ねて操作を求めない（拒否は置かない） |
| 呼び出しは親切な知らせとして1回送り、会話の始め方は利用者に任せる | 2026-11-10の利用者指示による（2026-11-02の「電話のように受ける」を改める）。RideComはインカムやWeb会議と同じ道具で、目の前でもインターネットでも「よーいドン」で同じ時間に入ったり、メッセージなど他の連絡手段も合わせて使ったりして会話を始める。電話のように相手を鳴らして呼び出すものではなく、通知は親切で添えるだけである（Zoomで最初の人が入ったと知らせるのに近い）。1対1は、相手を選んで接続を始めるたびに相手へ必ず1回だけ呼び出しの通知を送る。グループは通話の開始を誰にも通知せず、会話中に自分と直接つながっている（個人で登録している）人だけを選んで呼び出せる。どちらも呼びっぱなしとし、届かない・応答がない場合でも再送・応答待ちの表示・追いかけをしない。拒否は置かない。通知では誰からかが分かるようにする。グループへの招待の通知は、受け取る人が直接つながり呼び出しを許可した相手から、その人が選んだ相手にだけ届ける。グループの一部の人だけが会話しているときに、他のメンバーへ一斉に知らせたり自動で参加させたりしない。会話中に届いた呼び出し・招待で今の会話を鳴らして遮ったり、切り替えたりしない。CallKitは使わず標準の通知だけで実現する |
| 圏外でも近距離で会話できる | Wi-Fiアクセスポイント・ルーター・テザリングがなく、セルラーも圏外の場所で、近くの参加者同士はInternetやサーバーを必要とせず通話を開始・継続できる。Appleログインを完了し、同じグループの招待・鍵を共有済みで、端末の近距離無線機能と必要なOS権限が有効なことを前提とする。アクセスポイント不在と端末のWi-Fi機能OFFを混同しない |
| セルラーがあっても近距離を優先する | 相手へ届く近距離経路を音声配送の第一候補とし、全員へ近距離で送れるときは不要なInternet音声コピーを送らない。近距離経路の未準備・不達や遠隔参加者のために必要なInternet経路は使い、混在通話を切断しない。近距離接続をInternet資格取得やサーバー応答待ちに従属させない |
| 混在した経路でも通話を維持する | 一部離脱、近距離のみ・Internetのみの参加者が混在しても、届く経路がある参加者同士の会話を維持する |
| 経路によらず操作の意味を統一する | ミュート、個別音量、全体音量、音声効果を同じ意味で操作できる |
| 音声の鮮度を優先する | 遅れた音声をため込まず、会話に必要な低遅延を優先する。過負荷時の欠落は許容する |
| 音声機器の変化を理解できる | Bluetoothや有線機器が消失した際、停止理由と復帰方法が分かり、接続状態と音声の状態を区別できる |
| インカムを電話型の通話にしない | 仲間との連続会話を、CallKitによる電話と同じシステム通話へ変更しない。CarPlayではWidgetのボタンから既存のインカムを操作する体験を求め、専用の電話型通話アプリを目的にしない |
| WatchをiPhone通話の音声・操作端末にする | 通話処理はiPhoneが持ち、Watchはそのマイク・スピーカーと操作端末として接続する。複数人の音声合成、エフェクト、VADなどの音声処理もiPhoneへ集約し、Watchでミキサーを動かさない。Watchはマイク入力・iPhoneで処理済みの音声再生・操作を担い、通信に必要な最小限の入出力・符号化復号以外の処理を持たせない。この経路だけを提供し、Watch単体では動作させない。Watch独自の通話処理・グループ参加・直接のRTC接続は作らない。Watchから操作するときはWatchのマイクとスピーカーで会話し、Widgetに近い簡単な操作だけを提供する。ログイン、購入、ユーザーやグループの管理、詳細設定もiPhone側に置く |
| Widget・Watchから指定相手への通話を開始する | Widgetは画面へ配置・設定する際に登録済みユーザーまたはグループを指定し、その通話先専用のリモコンとして開始・終了・ミュートを操作する。WatchはiPhoneに保存済みのユーザー・グループから通話先を選んで開始できる。いずれも毎回iPhoneで先に通話を開始する条件を設けない。ユーザー追加・グループ作成・メンバー追加などの管理は行わない。Watch音声もWatch自身の操作から開始できることを採用条件とし、満たせなければ音声機能は提供せずiPhone通話のリモコンに限定する。その場合も通話先の選択と開始操作は必須とする |
| Watchで押している間だけ話せる | Watchのマイクは操作部を押している間だけミュートを解除し、それ以外は常にミュートする。2026-11-01の利用者指示により、通常のマイク切替とモード選択はWatchに置かない。指を離す・押下を取り消す・操作が中断する・接続が切れる場合はミュートへ戻し、復帰だけで送話を再開しない。通話と相手の音声の受信は押下ごとに開始・終了せず維持する。AppleのPush to Talk機能への統合を求めるものではない |
| 音楽と会話を両立する | 音楽との共存、発話に応じた送信抑制、自己録音による入力・出力確認を提供する |
| 自分が送信する音を確認できる | 録音チェックでは、通話と同じ設定・エフェクトを適用した送信音声を5秒分録音し、選択した出力先で先頭から末尾まで再生して本人が確認できるようにする。Watch使用時も音声処理と録音はiPhoneが担う |
| 不要な再接続を求めない | Wi-Fiの不安定化、別ネットワークへの移動、セルラーの不安定化が複数端末で重なっても、到達可能な経路で通話を維持し、経路回復後は自動復旧する。利用者が終了した通話や自動切断タイマーで終了した通話は再開せず、介入が必要な場合は理由を示す |
| 接続の放置を自動切断する | 電池消費、長時間接続による不具合、通信運営費用を抑えるため、通常利用とWatch利用で個別に自動切断時間を選べる。選択肢は1・3・5・10・15・30分、1・2・3・6・8・12・24時間とし、無制限は設けない。初期値は通常3時間、Watch5分。通信断と自動復旧で期限を延長せず、期限到達時は終了して自動再接続しない。利用権の24時間の再開猶予とは独立して扱う |

Watchの音声操作はWatch内でマイクのON/OFFを完結させ、押下ごとのiPhoneミュート連動を要求しない。iPhoneの既存VAD・通話処理を継続し、少量の通信削減より操作応答と処理の軽さを優先する。iPhone側のWatch向け媒体接続・必要な音声回路は交換可能な音声デバイスのプラグインとして責務を分離し、AppにWatch固有の符号化・媒体処理を残し続けない。Watch専用ミキサーや別VADを設ける要求ではない。

Watchから開始した通話は、明示終了または設定した自動切断期限まで入出力ともWatchに固定する。Watch Appを開いたまま手首を下げ画面が暗くなっても音声と受話を維持し、送話は暗転で閉じる。押下解除で閉じるのはWatchローカルの送話gateだけとし、相手の受話経路を止めない。省電力で音声通信を休止する場合も、Watchのnative再生経路は無音を出せる状態で維持し、次の受話に再初期化を要求しない。

入力バーで分かるのはマイク入力の有無や大きさであり、エフェクトを適用して相手へ送る音の内容・聞こえ方までは判断できない。送信者自身が何を送っているか確認して設定を調整できるように、録音チェックでは実際の送信処理を通した音を聞けることを必須とする。

## 共通の品質方針

| 要求 | 判断の基準 |
|---|---|
| アプリケーション名 | 正式名称をRideComに統一する。アプリ・Widget・Watchの表示、通知、権限説明、招待・共有文、翻訳、製品を説明する現行文書に同じ名称を使う |
| 対応端末 | iPhoneとiPadを同じiOS版で支援し、macOSも支援する。macOSをiOSの単純移植で済ませない。WidgetはiPhone・iPad・Mac、WatchはiPhoneとの連携を対象とし、通話状態を各OSで利用可能なシステム表示へつなぐ |
| 対応OSバージョン | 初回リリースはiOS/iPadOS/macOS/watchOS 27.0以降を支援する。以降は可能な限り最新メジャーと直前メジャーの最大2世代を支援し、下位OSだけの互換経路を長期維持しない |
| 安全なグループ通話 | 認証済みの同一グループだけで通話し、全経路の音声を保護する。秘密・音声内容をログへ出さない |
| 簡単な仕様と復旧 | 利用条件や上限の目的は費用の膨張と明らかな悪用を防ぐこととし、必要最低限にする。制限には余裕を持たせ、厳密な強制より実装・保守・運用・処理の総コストを優先し、複雑な管理を増やさない。切替や既存通話の終了を含む選択肢から、理解しやすく復旧しやすい方法を選ぶ。デッドロックや復旧操作へ進めない袋小路を避ける |
| 分かりやすい状態 | 接続、音声停止、失敗、未取得の計測値を区別し、成功していない状態を正常に見せない |
| アクセシビリティ | 色だけに依存せず、VoiceOver、文字サイズ、各端末の入力方法・画面サイズで利用できる |
| 走行中の操作 | バイクの運転中やスキー・スノーボードの滑走中は手で端末を操作できない前提とする。接続は出発前に済ませ、走行中は操作なしで会話が続くことを主な体験にする。操作は止まっている間に、携帯を取り出さずに（Apple Watch・ウィジェット・Siri等）、グローブをしたまま行える。端末を解除せずに触れられる表示から、取り消せない操作で接続を失わない |
| 音声品質 | 低遅延と会話の安定性を重視し、音響品質は実機で評価する |
| リアルタイム会話 | Watch音声経路を除く通常端末は、良好な通信条件では約125msを快適性の限界として、入力から出力までのアプリ内遅延を最小化する。標準は送信側の音声分離を有効、受信側を任意のオプションとし、この標準で125msを満たす。受信側を重ねた際の追加遅延は区別して示す。微小な欠落・重なり・ポップノイズも抑え、1〜3秒の間と短い相槌を保つ。ネットワークの遅延を、アプリが古い音声を貯める理由にしない |
| 費用と公開への移行 | 容量・時間・制御処理を含む費用で判断する。少人数試用の費用を抑え、公開へ拡張しても経路を作り直さず運用できる構成を求める |
| 有料提供の利用条件 | 購入者を中心にグループを作成・開始しつつ、仲間と気軽に再開できる猶予を設ける。グループ内の購入者の人数・割合は強制せず、利用条件の厳密な強制のために複雑な仕組みを増やさない。既存の認証・通信保護・費用制限は維持する |
| Watch音声の遅延と操作 | iPhone経由の処理と複数段の通信により、通常端末に対して少なくとも約100msの追加遅延を見込む。これは利用者の設計上の想定であり、実測値や固定の保証値ではない。通常端末と同じ約125msの総遅延基準をWatchへ適用しない。押して話すUIに近い体験としてこの差を許容し、押下・送話許可・ミュートの状態とタイミングが分かることを優先する。無制限の遅延・古い音声の滞留・解除後の録音継続を許す意味ではない |
| Watchのcodec選定 | Apple標準のAACを優先候補として成立性を確認する。現在の実装が使う形式解析APIの不在だけでAAC自体を非対応と判断しない。Opusへの変更は、実際の対応・品質・遅延に加え、電池消費の明確な利点を比較して判断する。Apple標準であることだけでハードウェア処理や省電力を保証せず、未測定のOpus省電力優位も前提にしない |
| 通信コストとバッテリー消費の徹底削減 | 処理・通信・保守・運用・仕様管理のコストと、利用者の直感に反する条件を減らし、軽量で簡単な構成を維持する。不要な処理と複雑さを排除し、バッテリー消費量・通信量を増やす案を採用しない。未測定の効果を省電力・低通信量の実績として扱わない。提供機能・会話の同一性・接続継続・低遅延を維持したまま、通信コスト、サーバー運用コスト、バッテリー消費を徹底的かつ継続的に削減する。無音時の送信量、不要な演算・周期起床・サーバー処理を削減対象とし、無効にした機能は実処理も休止する。共通化はpackage境界で行い、通信方式・codec固有の最適化をその内部に閉じる。節電のために音声を蓄積・再送して遅らせない。機能の削減や品質基準の緩和を、最適化の達成として扱わない |
| 利用枠と継続 | 通常は通話を自動継続し、利用枠を使い切った場合は理由を示して停止する。無制限継続と厳密な費用上限を同時に保証しない |
| 検証費用の抑制 | 開発・検証の大量実行によって実Cloudflare等の従量費用を増大させない。実サービスが必要な確認は、単体・結合を含むローカル検証をすべて成功させた後、必要最小限の人数・時間・回数に限定する。ローカルの代替環境による確認と、実サービスでしか確認できない項目を分ける |

## 付録：省電力機構の考え方

2026-11-02に利用者から提示された、省電力を再検討するための参考の考え方を整理する。本付録は各技術の導入を定める要求ではなく、既存の「通信コストとバッテリー消費の徹底削減」の背景資料とする。現行のバースト送信を前提とし、CNGなどの導入予定は設けない。再検討の作業と適用可否は[バックログ](../backlog/改善候補.md#バースト通信の省電力再検討)へ分ける。

### 音声レイヤー

無言の区間に不要な符号化・音声packet送信・復号を減らし、発話に必要な処理へ集中するという考え方である。

| 技術 | 仕組みの考え方 | 期待する省電力と適用条件 |
|---|---|---|
| VAD（Voice Activity Detection／音声活動検出） | 入力から人が話す区間と、無音・背景ノイズ等の非発話区間を判別する | 判定を符号化・packet送信の抑制へつなげられれば、CPU処理と通信を減らす余地がある。検出そのものの処理や、次の発話を検出する入力は必要となる。小声・発話の立上がり・短い相槌を保つことが前提 |
| CNG（Comfort Noise Generation／快適ノイズ生成） | 音声の送信を休止する方式で、完全な静寂による切断感を和らげるため、受信側で背景雑音を合成する。ホワイトノイズ等は例であり、方式によって背景音の特徴も使う | 送信音声と音声復号の仕事を減らせる可能性がある一方、雑音生成や再生の処理は残る。背景音情報を送る方式もある。現行のバースト送信へ追加する計画ではなく、考え方の参考として保持する |
| DTX（Discontinuous Transmission／不連続送信） | 非発話区間の音声送信を休止する、または背景音情報等の少量の更新へ減らす。VAD・CNGと組み合わせる方式がある | codec・packet化・送信制御が協調する仕組みで、ネットワーク側だけの機能には限定されない。符号化・送信・受信処理の削減余地を考える参考とする。完全停止の可否と更新間隔は方式依存 |

送信頻度を「数秒に1回」程度まで下げるという提示例は、削減の方向性として残す。具体的な共通値にはしない。例えば[OpusのDTX](https://www.rfc-editor.org/rfc/rfc6716.html#section-2.1.9)には400msごとのframeという説明があり、方式ごとの条件がある。[CNGのRTP表現](https://www.rfc-editor.org/rfc/rfc3389.html)も、すべてのcodec・媒体経路に同じまま適用されるものではない。

### 通信・アーキテクチャレイヤー

不要な送受信や周期的な起床を減らし、通信処理と無線が休止できる時間を増やすという考え方である。実際の省電力効果は、通信量だけでなくOS・無線・媒体経路と処理の動きに依存する。

| 技術 | 仕組みの考え方 | 期待する省電力と適用条件 |
|---|---|---|
| 接続状態に応じたビットレート制限・輻輳制御 | 帯域の詰まり、遅延、損失等に応じて送出量を調整する。GCCやBBRは、この方向性を考えるために挙げられた例 | 過剰な送出、送信待ち、損失に伴う再送等を抑えられれば、通信負荷・無線の高負荷時間を減らす余地がある。再送の有無は媒体の信頼性設定にも依存し、bitrateを下げれば必ず再送や消費電力が減るという関係ではない |
| ICE／TURNのキープアライブ最適化 | 接続維持のための確認packetと周期処理の送信頻度を、必要な接続性を保てる範囲で整理する。STUN Binding等はその例 | 不要な起床を減らし、無線が休止できる時間を増やす余地がある。NAT保持、送信同意の再確認、TURNの割当・permission・channelの更新は役割と期限が異なる。接続維持と期限を満たす条件を先に区別する |

[GCCの設計資料](https://datatracker.ietf.org/doc/html/draft-ietf-rmcat-gcc-02)はRTP媒体向けの参考となるInternet-Draftであり、[BBR](https://github.com/google/bbr)とは適用するトランスポートや制御点が異なる。アルゴリズム名の例示と、音声codecのbitrateを実際に変える処理は分けて考える。[WebRTC Data Channel](https://www.rfc-editor.org/rfc/rfc8831.html#section-6.1)にはSCTP側の輻輳制御があり、WebRTCを使うだけで独自音声payloadのbitrateが自動調整されるとは限らない。

接続維持の参考は[ICE keepalive](https://www.rfc-editor.org/rfc/rfc8445.html#section-11)、[Consent Freshness](https://www.rfc-editor.org/rfc/rfc7675.html#section-5)、[TURN](https://www.rfc-editor.org/rfc/rfc8656.html)。送信間隔を広げる考え方は、これらの必要な期限・確認と、通信断からの復旧を満たす範囲で扱う。「切断されなかった最大の間隔」を、異なるNAT・ネットワークや背景動作でも安全な値と一般化しない。

### この考え方を読む基準

本付録の省電力効果は期待する方向であり、RideComで測定済みの効果ではない。現行のバースト送信・codec・配送経路で、既に減らせている仕事と残る仕事を区別する。参考技術を一式で追加する前提を置かず、採否が必要になった項目だけを、会話の品質・低遅延・接続維持と処理・通信・電池消費の観測から判断する。
