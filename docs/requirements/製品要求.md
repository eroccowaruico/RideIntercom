# 製品要求

## 目的と背景

RideIntercomは、スキー、スノーボード、ツーリング、ドライブなどで、仲間と気軽に通話を楽しむためのiOS/macOSアプリである。音楽を聴きながらグループで同時通話を続ける。カメラを使う撮影やビデオ通話は提供しない。iOSを主対象とし、macOSにもデスクトップとして使える体験を求める。近距離とInternetが混在する移動中でも、接続経路がある限り手動の繋ぎ直しを減らす。少人数の試用から公開へ進められること、従量課金による費用増大を抑えることを重視する。

本書は統一して満たす目的・価値・品質を定める。達成状況や作業一覧は持たせない。製品の要求と、[開発方針](../policies/開発方針.md)・[文書作成規約](../policies/文書作成規約.md)の作り方の要求を区別する。

## 利用者に提供すること

| 要求 | 背景・期待する結果 |
|---|---|
| グループで同時通話できる | 招待して同じグループへ参加し、認証済みの相手と会話できる |
| 閲覧と通話先変更を区別する | 別グループを見るだけで通話を切らず、接続先の変更は明示的に行える |
| 混在した経路でも通話を維持する | 一部離脱、近距離のみ・Internetのみの参加者が混在しても、届く経路がある参加者同士の会話を維持する |
| 経路によらず操作の意味を統一する | ミュート、個別音量、全体音量、音声効果を同じ意味で操作できる |
| 音声の鮮度を優先する | 遅れた音声をため込まず、会話に必要な低遅延を優先する。過負荷時の欠落は許容する |
| 音声機器の変化を理解できる | Bluetoothや有線機器が消失した際、停止理由と復帰方法が分かり、接続状態と音声の状態を区別できる |
| 音楽と会話を両立する | 音楽との共存、発話に応じた送信抑制、自己録音による入力・出力確認を提供する |
| 不要な再接続を求めない | 継続通話や一時的な通信障害からの復帰は自動で進め、利用者の介入が必要な場合は理由を示す |

## 共通の品質方針

| 要求 | 判断の基準 |
|---|---|
| 対応端末 | iOSとmacOSを支援し、macOSをiOSの単純移植で済ませない |
| 安全なグループ通話 | 認証済みの同一グループだけで通話し、全経路の音声を保護する。秘密・音声内容をログへ出さない |
| 分かりやすい状態 | 接続、音声停止、失敗、未取得の計測値を区別し、成功していない状態を正常に見せない |
| アクセシビリティ | 色だけに依存せず、VoiceOver、文字サイズ、各端末の入力方法・画面サイズで利用できる |
| 音声品質 | 低遅延と会話の安定性を重視し、音響品質は実機で評価する |
| リアルタイム会話 | 良好な通信条件では約125msを快適性の限界として、入力から出力までのアプリ内遅延を最小化する。標準は送信側の音声分離を有効、受信側を任意のオプションとし、この標準で125msを満たす。受信側を重ねた際の追加遅延は区別して示す。微小な欠落・重なり・ポップノイズも抑え、1〜3秒の間と短い相槌を保つ。ネットワークの遅延を、アプリが古い音声を貯める理由にしない |
| 費用と公開への移行 | 容量・時間・制御処理を含む費用で判断する。少人数試用の費用を抑え、公開へ拡張しても経路を作り直さず運用できる構成を求める |
| 通信量と電池消費 | 会話の同一性・接続継続・低遅延を維持し、無音の送信量、不要な周期処理、サーバー処理を減らす。無効にした機能は実処理も休止する。共通化はpackage境界で行い、通信方式・codec固有の最適化をその内部に閉じる。節電のために音声を蓄積・再送して遅らせない |
| 利用枠と継続 | 通常は通話を自動継続し、利用枠を使い切った場合は理由を示して停止する。無制限継続と厳密な費用上限を同時に保証しない |
