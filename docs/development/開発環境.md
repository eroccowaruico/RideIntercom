# Xcode / VS Codeの開発環境

## 目的

両エディタで同じcheckout・実ファイルを編集する。Xcodeの手動ファイル一覧が古くなる問題を避け、ファイル追加・削除を継続的に反映する。表示・Git追跡・ビルド対象は別の設定として扱う。

## 開く入口

| 環境 | 入口 | 操作 |
|---|---|---|
| Xcode | rootの`RideIntercom.xcodeproj` | 共有scheme `RideIntercom`。My Mac / iOS Simulatorを選んでRun / Test |
| VS Code | rootの`RideIntercom.code-workspace` | root全体と9 local packageを開く。Swift拡張の推奨を表示 |
| terminal | rootで`scripts/build_and_run.sh` / `scripts/validate.sh` | エディタによらない同一のビルド・検証 |

開発の基準は`main`とする。`dev`への先行反映を挟まず、通常のcheckoutでmainを編集する。別worktreeを使用する場合も、両エディタで同じworktreeの入口を開く。別checkoutの同名projectを編集しても、このcheckoutには反映されない。ブランチの運用は[開発方針](../policies/開発方針.md)に従う。

## ファイル表示とビルド対象

| 対象 | 表示・更新 | ビルド所属 |
|---|---|---|
| Xcode `Repository` | root `.` を指す`PBXFileSystemSynchronizedRootGroup`。新しいrootファイル・サブフォルダも同じ参照下に入る。Gitへの追加は条件にしない | どのtargetにも所属させない |
| App / AppTests / UITests | 既存の同期フォルダを維持。新しいSwiftファイルは対応する実フォルダへ作る | 対応targetへ自動所属 |
| `RideIntercom/packages` | Repositoryまたはlocal Swift Packageから編集。ソース・テスト・manifestを保持 | SwiftPMでcompile。Appの自動所属から`packages`を除外 |
| docs / scripts / server | 実フォルダを参照。Repositoryから新規階層にも到達 | Appへcompile/copyしない |
| `.vscode` / `.codex` / `.github` / `.gitignore` | Xcodeのrootにも明示参照を置き、隠し設定への入口を確保 | Appへcopyしない |
| VS Code Explorer | root全体を開く。`explorer.excludeGitIgnore=false`、file nestingなし、既定の隠しファイル除外を解除 | 表示だけでGit追跡やビルド対象は変わらない |
| 生成物・秘密設定 | `.gitignore`は維持。VS Codeではignoredファイルも閲覧可能 | ステージ・配布対象へ追加しない |

Xcodeの「Repository」は元フォルダそのものを参照する。ここでMove to Trashや移動をすると実ファイルにも反映される。フォルダを古い`PBXGroup`へ変換したり、RepositoryにTarget Membershipを付けたりしない。

Repository内の`RideIntercom.xcodeproj`は`explicitFileTypes`で`folder`、`RideIntercom/packages`は`explicitFolders`でフォルダ参照として扱う。閲覧用の同期から自身のprojectやpackage内部の`.swiftpm/xcode`を子projectとして取り込むことを防ぐ。`.xcodeproj`は`explicitFolders`だけではXcodeがprojectとして再認識するため、ファイル種別を明示する。App側の`packages`フォルダ参照・target所属除外と、9個の`XCLocalSwiftPackageReference`は維持する。packageのソース・テスト・manifestはlocal Swift Packageから編集できる。Xcodeは保存時に`explicitFileType = folder`の参照を`projectReferences`へ記録することがある。このフォルダ参照は許容し、projectとして解釈される自己参照だけを検査エラーとする。

表示を確認するときはXcode navigatorの文字列・Recent Files・source controlのfilterを解除する。VS Codeで独自のユーザー設定に`files.exclude`を追加している場合、その除外も確認する。OSの隠しファイル・bundleの内部表示はエディタ側の表示規則も関わるため、後述の画面確認を別途行う。

## Xcode推奨設定

projectとApp / AppTests / UITestsのDebug・Releaseで`DEAD_CODE_STRIPPING = YES`を設定する。projectの`STRING_CATALOG_GENERATE_SYMBOLS = YES`も有効にする。Appでの既存の有効化と、テストtargetでの`NO`指定は維持する。

## 共通ビルド番号とArchive

公開バージョンは`MARKETING_VERSION`、ビルド番号はXcode project内の`CURRENT_PROJECT_VERSION`として別管理する。[開発方針](../policies/開発方針.md#公開バージョンとビルド番号)を要求の正本とし、公開バージョンは自動変更しない。

XcodeでRideIntercom schemeと配布先を選び、通常どおりRun・Build、または **Product → Archive** を実行する。専用コマンドやXcodeの終了は不要。projectのDebug・Releaseに同じ`CURRENT_PROJECT_VERSION`を設定し、AppのBuild欄はその値を継承する。番号の正本は`project.pbxproj`だけとし、採番専用のxcconfigや常設lockファイルは置かない。日付を付けず、ゼロ埋めもしない。8桁へ桁上がりしても切り詰めない。基準を手動で変える場合は、ProjectのBuild SettingsでDebug・Releaseを同じ値に揃える。

| 動作 | 採番・注意点 |
|---|---|
| Run・Build・Test・Archive | AppのRun Script phaseが、Xcode内部の`ACTION=build`または`install`で共通の10進番号を1増やす。Debug・Releaseでカウンタを分けず、連続回数によらず同じ規則を適用する。標準の`xcodebuild`も同じ処理を使う |
| ビルドを伴わない操作 | インデックス専用など`build`／`install`以外のactionは採番しない。テストの実行だけでAppをビルドしない場合も増えない |
| project設定との一致 | project.pbxproj内のビルド番号だけを更新し、公開バージョンや他の設定は保持する。採番差分は配布記録としてコミットする |
| Archive本体への反映 | `prepare_archive_info.py`が各ビルド専用のDerivedSourcesへ入力Info.plistを生成する。既存のソースInfo.plistと使用中の`INFOPLIST_KEY_*`を保持し、採番直後の値を渡す。XcodeのProcessInfoPlistFileと署名はその後に実行される |
| Info.plist設定 | Appのみ`GENERATE_INFOPLIST_FILE=NO`とし、読み込み済みの旧番号での上書きを防ぐ。アイコン、SDK、対応OSなどは引き続きXcodeがマージする。新しい`INFOPLIST_KEY_*`を追加するときは生成処理・メタデータ保持検証も更新する |
| 同時実行・失敗 | 同じcheckoutではfile lockとatomic replaceで採番を直列化し、各ビルドの入力plistへ予約番号を固定する。異常終了でlockファイルが残ってもOSがロックを解放する。採番後に失敗した番号は戻さない |
| 設定の欠落・破損 | 低い番号へ自動初期化せずBuildを失敗させる。配布済みの最大番号と履歴を確認して共通xcconfigを復旧する |
| 別Mac・別checkout | 配布担当を一本化し、採番差分を共有してから次のArchiveを作る。ローカルlockは別checkoutや別Macの重複を防がない |

移行時には既存の採番値を引き継ぎ、低い番号へ戻さない。採番結果はProjectのBuild Settingsで`CURRENT_PROJECT_VERSION`のResolved値、またはAppのGeneral → Buildで確認する。Archiveを再配布する際は作り直さず、同じArchiveを選択する。

Organizerで配布する場合は **Manage version and build number** をOFFにする。これをONにするとXcode自身の配布処理で再採番されるため、Archive本体との一致を維持できない。このGUIの選択はproject設定から強制できない。CLIでIPAを書き出す場合は、`manageAppVersionAndBuildNumber = false`を保存した`scripts/ExportOptions.plist`を使う。保存済み設定は`destination=export`のためアップロードしない。

根拠: Appleの[Run Script build phase](https://developer.apple.com/documentation/xcode/running-custom-scripts-during-a-build)、[ビルド設定](https://developer.apple.com/documentation/xcode/build-settings-reference)、[CFBundleVersion](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion)。以前の専用コマンド方式の検証は[当時の記録](../validation/history/配布ビルド採番とOrganizer認証調査.md)へ残す。

## 配布時の署名設定

現在のAppはCloudKitを使用しないため、`RideIntercom.entitlements`にはiCloudサービス・コンテナの権限を含めない。空のコンテナ一覧とCloudKitだけを有効にすると、App Store Connectの配布検証でiCloud環境の不備として拒否される。署名設定を変更した場合は新しいArchiveを作成し、OrganizerでそのArchiveを選んで配布する。既存Archive内の署名設定はソースの変更だけでは更新されない。

## 配布時の暗号化申告

App Store Connectでアップロードごとに暗号化の質問へ回答する手間を省くため、AppターゲットのDebug・Releaseビルド設定に`INFOPLIST_KEY_ITSAppUsesNonExemptEncryption = NO`を設定する。Appのmetadata生成phaseがこの設定を読み、iOS/macOSのビルド時に生成されるInfo.plistへ`ITSAppUsesNonExemptEncryption = false`（Boolean）が反映される。この値は、暗号化の使用についてAppleへの書類提出が免除されるという申告であり、通信の暗号化を無効にはしない。

| 項目 | 現在の設定・判断根拠 |
|---|---|
| Apple OSの暗号化 | CryptoKitのAES-GCM、HMAC-SHA256、SHA256と、暗号化必須のMultipeerConnectivityを使用する |
| 同梱ライブラリの暗号化 | WebRTCのDTLSを使用するため、Apple OS内の暗号化だけを使用するアプリには分類しない。使用経路は[RTC仕様](../spec/packages/RTC.md)を参照 |
| 配信地域の前提 | 利用者の配信方針によりフランスを対象外とする。Appleの書類要件表では、OS外の標準暗号化に対するフランス向け申告書はフランスで配信する場合に必要 |
| 再判定する条件 | フランスへの配信開始、独自・非標準の暗号化の導入、依存ライブラリや暗号化方式の変更時には申告を見直す |
| 配布への反映 | 変更後に新しいArchiveを作成してアップロードする。既存Archiveやアップロード済みビルドの申告は更新されない |

配信地域はApp Store Connect側で管理し、このInfo.plistの値では制限されない。現在の配信地域やApple側の処理結果を、この設定の追加だけで確認済みとは扱わない。

根拠（2026-10-23確認）: Appleの[申告キーの定義](https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption)、[暗号化に関する書類要件](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption)、[書類提出が不要な場合のInfo.plist設定](https://developer.apple.com/help/app-store-connect/manage-app-information/determine-and-upload-app-encryption-documentation/)。

## 申請情報を事前設定できる範囲

| 項目 | 保存場所・反映方法 | Web入力との関係 |
|---|---|---|
| 暗号化申告 | 上記のAppビルド設定 | 新しいビルドに申告を含め、繰り返しの質問を省く |
| Bundle ID・バージョン・ビルド番号・アイコン | Xcode projectとasset catalog。設定済み | ビルドから読み取られる。ストア掲載用のバージョン情報は別途管理 |
| 端末上の表示名・マイクとローカルネットワークの使用説明 | Appの`INFOPLIST_KEY_*`。設定済み | 権限ダイアログなどに使用。ストア掲載名・説明文の代わりにはならない |
| macOSカテゴリ | `LSApplicationCategoryType`。Lifestyle設定済み | App Store Connect側のカテゴリと一致させる必要があり、Web側の指定を省くキーではない |
| Required Reason APIの使用理由 | `RideIntercom/PrivacyInfo.xcprivacy` | Appへ同梱する。App Privacyの回答やプライバシーポリシーURLの代わりにはならない |
| ストア説明・キーワード・サポートURL・更新内容 | App Store Connectのバージョン別メタデータ | Info.plistから自動入力されない。確定した内容は公式APIで登録できる |
| 年齢制限・コンテンツ権利・App Privacy・配信地域・価格・審査連絡先 | App Store Connect側の申請情報 | 実際の機能、運用、権利者、公開先に基づき登録する。ビルド設定だけでは代替できない |

プライバシーマニフェストのAPI理由は[通信仕様](../spec/App/通信仕様.md#申請用のapi利用理由)を参照する。Appの同期フォルダ内に配置し、既存のtarget所属によってリソースとして扱う。新しいArchiveのApp bundle（macOSは`Contents/Resources`）に含まれることと、Organizerの`Generate Privacy Report`でSDK分を含む申告を確認する。

マニフェストは確認済みのAPI利用理由を記載し、収集データ・追跡について未確認の「なし」を埋めない。通話音声、参加者ID、診断情報、Cloudflare側の保存・処理を確認してApp Privacyへ回答する。WebRTC同梱zipにもマニフェストは存在するが、App側の申告でSDK自身の申告を代替しない。

根拠（2026-10-29確認）: Appleの[Required Reason API](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype)、[App Privacy](https://developer.apple.com/app-store/app-privacy-details/)、[申請情報一覧](https://developer.apple.com/help/app-store-connect/reference/app-information/required-localizable-and-editable-properties)、[バージョン情報のAPI](https://developer.apple.com/documentation/appstoreconnectapi/app-store-version-localizations)。

## VS Codeの開発操作

`Tasks: Run Task`から次を使う。タスクはshell文字列を再解釈せずprocessとして実行し、working directoryはrootに固定する。rootを単独でOpen Folderした場合にも同じタスクを利用できる。package単体を独立workspaceにする場合はそのpackageのSwiftPM操作を使う。

| タスク | 内容 |
|---|---|
| `Check development setup` | フォルダ同期・target分離・editor設定・package参照の検査 |
| `Check documentation` | 相対リンク・開発ツール入口・READMEからの到達性・空文書ディレクトリ・Settings仕様の記載を検査 |
| `Build and run macOS` | 既定build task。App bundleを通常起動しプロセス存在を検証 |
| `Debug macOS (LLDB)` | 既存script経由でbuildし、統合terminalのLLDBでdebug。`run` / `breakpoint set` / `bt`等を使用 |
| `macOS logs` | 通常起動後に統合logを表示 |
| `Test headless / packages / macos / ios / ios-ui / pair / worker / scripts` | 既存validate入口を呼ぶ。iOSは音声E2Eと共通の専用Simulatorを再利用し、作成前に過去の不要端末を整理 |
| `Open Xcode` | 同じcheckoutのprojectをXcodeで開く |

`DEVELOPER_DIR`とSwift toolchainは`/Applications/Xcode.app`を既定とする。別名のXcodeを使う場合はworkspaceと`.vscode/settings.json`の両方を一致させる。system全体のxcode-selectは変更しない。

Swift拡張のSourceKit-LSPは各Swift Packageで利用する。Appの`.xcodeproj`に対する補完・indexはSwift拡張だけでは限定的であり、Xcode同等のApp index対応済みとは扱わない。Appの正確なcompile診断・実行・テストは共有xcodebuild入口を使い、SwiftUI Canvas・署名・Appの完全なindex/debug UIはXcodeを利用する。外部build serverは今回追加していない。

## 配布用アプリアイコン

`RideIntercom/Assets.xcassets/AppIcon.appiconset` に、道路と音声波形を組み合わせた紺・白・ターコイズの仮アイコンを登録している。利用者の指示で新規生成した暫定素材であり、正式デザイン承認済みとは扱わない。iOSは不透明な1024px画像からXcodeが必要サイズを生成し、macOSには16〜1024pxを登録する。Archiveで120px・152pxのPNGと `CFBundleIcons` 内の `CFBundleIconName=AppIcon` を確認する。

生成には内蔵image generationを使用した。生成指示は次のとおり。

> Create a temporary production-quality app icon for RideIntercom, a group voice intercom app used by riders while moving. Square 1024x1024 full bleed opaque image, no transparency, no rounded outside corners, no mockup or surrounding margin. Deep navy background with a simple bold original turquoise and white emblem combining two flowing road lanes and a compact sound wave / conversation motif. Clean geometric vector-like rendering, highly legible at 60 pixels, minimal shapes, balanced centered composition, premium restrained style. No text, no letters, no logos, no Apple SF Symbols, no gradients that reduce contrast. This is the actual icon artwork filling the entire canvas.

生成画像を `sips` で各pixel寸法へ変換してasset catalogへ保存した。生成指示に指定した解像度だけで判断せず、保存したPNGとコンパイル後のApp bundleを検査する。

## 継続検証

| 実行地点 | 検査と失敗時の扱い |
|---|---|
| Xcode buildの`Check Development Setup` phase | 毎回read-only検査。壊れた参照を検出したらbuild失敗。build中にprojectを書き換えない |
| `scripts/validate.sh`全mode | 最初に同じ検査。失敗をresults.tsv / results.jsonへ記録し、独立段階は継続 |
| `scripts/validate.sh scripts` | 文書検査7件、設定検査の回帰7件、WebRTC scripts2件、Cloudflare scripts4件 |
| `.github/workflows/development-setup.yml` | push / PRで同じ設定検査・文書検査・回帰。リモートへ送った後に動く定義であり、今回GitHub実行済みではない |

`python3 scripts/check_development_setup.py`単独でも実行できる。全体同期の削除・静的groupへの変換・navigatorからの切り離し・targetへの誤所属を検出する。packageを追加するときはXcodeのlocal package参照とVS Codeのworkspace rootsを合わせる。ソースファイルごとの一覧更新・generator・常駐watcherは不要。

確認待ちと結果は[検証](../validation/README.md)で管理する。
