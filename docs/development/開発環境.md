# Xcode / VS Codeの開発環境

## 目的

両エディタで同じcheckout・実ファイルを編集する。Xcodeの手動ファイル一覧が古くなる問題を避け、ファイル追加・削除を継続的に反映する。表示・Git追跡・ビルド対象は別の設定として扱う。

## 開く入口

製品名は[製品要求](../requirements/製品要求.md)に従いRideComとする。表示名と、既存の署名・保存・通信・開発環境に使う技術識別子は次のように扱う。

| 対象 | 名称・扱い |
|---|---|
| App・Widget・Watchの表示名 | `CFBundleDisplayName`と`CFBundleName`は`RideCom`。画面、権限説明、招待、通知、翻訳、現行文書もRideComとする |
| Xcode・ソースの識別子 | `RideIntercom.xcodeproj`、scheme・target・module・実行ファイル名、ソースの型名・配置は既存値を使用する。コマンド・パス・コードを記載するときは実在する名前を使う |
| 署名・保存・通信の識別子 | Bundle ID、App Group、Keychain・UserDefaults・保存namespace、ログのラベル、`rideintercom://`、Bonjour名、サーバーのresource名は既存値を使用する。製品名の変更で別アプリ・別データ・別接続として扱わない |
| 過去の記録 | 過去計画・検証証跡・当時のコマンドにある旧名は原文を保持する |

| 環境 | 入口 | 操作 |
|---|---|---|
| Xcode | rootの`RideIntercom.xcodeproj` | 共有scheme `RideIntercom`。My Mac / iOS Simulatorを選んでRun / Test |
| VS Code | rootの`RideIntercom.code-workspace` | root全体と9 local packageを開く。Swift拡張の推奨を表示 |
| terminal | rootで`scripts/build_and_run.sh` / `scripts/validate.sh` | エディタによらない同一のビルド・検証 |

開発の基準は`main`の通常作業フォルダとする。`dev`への先行反映を挟まず、両エディタから同じ実ファイルとprojectを開く。通常のBuild・Run・Test・Archiveもこのprojectから実行し、Xcode既定の`~/Library/Developer/Xcode/DerivedData`を使用する。`/tmp`等へのprojectコピーや別worktreeでのbuild、専用のDerivedDataへの切替は行わない。テスト用の保存namespace、fixture、ログ出力の隔離は維持する。保全用の別checkoutを編集しても通常作業フォルダには反映されない。ブランチの運用は[開発方針](../policies/開発方針.md)に従う。

## Xcodeだけで実行・テスト・配布する

| 操作 | Xcodeでの選択と動作 |
|---|---|
| 編集・通常起動 | `RideIntercom.xcodeproj`を開き、`RideIntercom` schemeとMy Mac／iPhone／iPadを選ぶ。Build／Runは従来のDebug構成、通常の保存先を使う |
| Watch実機 | ペアのiPhoneを接続・ロック解除し、まず`RideIntercom` schemeとiPhoneでRunする。その後、共有`RideIntercomWatch` schemeと実機Apple Watchを選んでRun（⌘R）。Watch側も開発者モードを有効にする。WatchのRunは通常Debug・自動署名を使い、検証用構成や専用CLIは不要。通話先・ログインはiPhoneの既存データを使う |
| App単体・UI | Test navigatorで対象を選ぶかProduct → Test（⌘U）。TestActionは`Debug-Validation`へ自動的に切り替わる。UIは専用iPhone／iPad Simulatorを使う。破損復旧fixtureの準備と確認もUI test自身が行うため、外部CLIの事前操作は不要 |
| ローカルStoreKit | `RideIntercom-StoreKitTests` schemeとMy Macを選んでTest。通常のテストと共通の`Debug-Validation`を使い、専用Test PlanがStoreKitTestと付属の商品fixtureを選ぶ。購入・復元の検証に実App Storeの商品や実購入は使わない。iOS購入UIは別schemeと[既知の受入境界](../validation/未確認事項.md)を参照 |
| package単体 | navigatorの各local Swift PackageからTestを実行する。Appの検証用認証fixtureとは独立 |
| Archive・提出 | `RideIntercom` schemeと配布対象を選びProduct → Archive。Release構成を使い、OrganizerでValidate／Distribute AppからApp Store Connectへ提出する。後述の署名・バージョン・配布設定と、OrganizerのManage version and build numberの選択を確認する |

通常Runの環境変数をTestActionへ引き継がず、検証用の名前空間と明示的な未ログインfixtureから開始する。UIはケースごとに検証用ログインを指定する。検証のnamespace・環境指定が欠けた場合は起動を失敗させ、通常のKeychainへfallbackしない。検証構成はDebug.localの開発接続資格を読み込まない。App／Widget／Watchの各生成Infoに保存先を渡し、検証中は本番App Group・Live Activity・Watch Connectivity・OS通知へアクセスしない。

Watch実機の初回Runで「Copying OS library symbols」「Waiting for device unavailability condition to be resolved」と表示される場合は、アプリ起動前のXcode端末準備である。WatchとMacの接続を維持して準備完了を確認する。ビルド成功だけで導入・起動成功とは判断せず、Runの実行記録と実機画面を照合する。iPhoneの`Locked`による起動拒否はロック解除後に再実行する。署名・接続の[実機導入記録](../validation/history/AppleWatch実機への導入とXcode起動.md)と、音声・背景継続の[未確認事項](../validation/未確認事項.md#iphone依存watchの実機操作と音声)は区別する。標準の選択方法は[Appleの実機実行手順](https://help.apple.com/xcode/mac/current/en.lproj/dev5a825a1ca.html)を参照する。

local Swift PackageはAppの同期フォルダからresourceとしてコピーしない。各packageのrootを所属例外へ明示し、ビルド済みtest bundleやcacheがArchiveへ入ることを防ぐ。検査も各rootの実所属を確認するため、Xcode保存時に親packagesの記述だけが省かれても停止しない。package参照とnavigatorでの編集は維持する。

構成名にDebugを含めることで、local Swift Packageもtestabilityを備えるDebugビルドを使用する。検証専用のxcconfigは認証・保存の隔離を共通化し、通常Debug／Releaseと公開バージョンを変更しない。全構成のビルド番号はprojectの共通設定へ揃える。GUIによる実際の操作・署名付き提出・Apple側の処理完了はローカルbuild／testとは別に受け入れる。

StoreKit専用のbuild構成は設けない。通常の`RideIntercom` schemeは`LocalStoreKitTests`と`StorePurchaseUITests`を実行対象から静的に外し、実StoreKit fixtureが必要な試験を通常unit/UIへ混ぜない。専用`RideIntercom-StoreKitTests` schemeのTest Planは4つのStoreKit suite、`RideIntercom-StoreKitUITests` schemeは購入UI suiteだけを選択する。これは実行時のskipではない。通常のRunはDebug、ArchiveはReleaseのままで、環境変数だけではfixture catalogを有効にできない。

維持する構成はDebug／Release／Debug-Validation／Release-Validation。Debug-Validationは共通の隔離検証、Release-Validationは製品と同じ最適化を使う音声測定に使う。OS別のProductsはXcode標準の生成先であり、全組合せを常時保持する運用にはしない。iOS AppがWatchを埋め込むbuildでは、同じ構成のWatch生成物も依存として必要になる。用途を終えた構成・診断生成物は[開発方針](../policies/開発方針.md#一時物を残さない開発)に従って回収する。

## ファイル表示とビルド対象

| 対象 | 表示・更新 | ビルド所属 |
|---|---|---|
| App / AppTests / UITests / 音声E2E / Widget / Watch | 各実フォルダの同期参照を維持。新しいSwiftファイルは対応する実フォルダへ作る | 対応targetへ自動所属。既存の所属例外は保持 |
| `RideIntercom/packages` | App配下のフォルダまたはlocal Swift Packageから編集。ソース・テスト・manifestを保持 | SwiftPMでcompile。Appの自動所属から各package rootを除外 |
| docs / scripts / server / Configuration | 各実フォルダを個別の同期参照として表示。内部の新規ファイル・階層にも追随 | 閲覧・編集用であり、Appへcompile/copyしない |
| `.vscode` / `.codex` / `.github` / `.claude` / `.agents` / `.gitignore` | Xcodeのrootにも明示参照を置き、隠し設定への入口を確保 | Appへcopyしない |
| README / workspace / AGENTS / CLAUDE | rootの既存ファイルを通常のfile参照で開く | 閲覧・編集用であり、Appへcopyしない |
| 新しいroot直下の項目 | Xcode標準の **Add Files to “RideCom”…** で参照を追加する。既存の同期フォルダ内に作る場合は追加操作不要 | docs・設定などの閲覧用参照にはTarget Membershipを付けない |
| VS Code Explorer | root全体を開く。`explorer.excludeGitIgnore=false`、file nestingなし、既定の隠しファイル除外を解除 | 表示だけでGit追跡やビルド対象は変わらない |
| 生成物・秘密設定 | `.gitignore`は維持。VS Codeではignoredファイルも閲覧可能 | ステージ・配布対象へ追加しない |

同期参照は元フォルダそのものを参照する。Move to Trashや移動は実ファイルにも反映される。表示だけを整理するときはRemove Referenceを使い、実ファイルの削除と区別する。

project自身を含むroot `.` の再帰同期参照は置かない。自己`RideIntercom.xcodeproj`が子projectとして再検出され、保存のたびに参照が増える構成を避ける。`.xcodeproj`のファイル種別を`folder`へ上書きして許容する回避策も使わない。各編集フォルダの同期と、rootファイルの標準参照を使う。

local Swift Packageとその親は`explicitFolders`でfolderへ強制せず、Xcodeのpackage検出へ委ねる。親のfolder強制によるpackageの二重解釈と`Missing package product`を避け、App側の各package rootのtarget所属除外と9個の`XCLocalSwiftPackageReference`を維持する。packageのソース・テスト・manifestはlocal Swift Packageからも編集できる。

表示を確認するときはXcode navigatorの文字列・Recent Files・source controlのfilterを解除する。VS Codeで独自のユーザー設定に`files.exclude`を追加している場合、その除外も確認する。OSの隠しファイル・bundleの内部表示はエディタ側の表示規則も関わるため、後述の画面確認を別途行う。

## Xcode推奨設定

projectとApp / AppTests / UITestsのDebug・Releaseで`DEAD_CODE_STRIPPING = YES`を設定する。projectの`STRING_CATALOG_GENERATE_SYMBOLS = YES`と`CLANG_ANALYZER_LOCALIZABILITY_NONLOCALIZED = YES`も有効にする。Appでの既存の有効化と、テストtargetでの`NO`指定は維持する。AppとWidgetの全構成で`REGISTER_APP_GROUPS = YES`を設定し、macOSのApp Groupを署名profileへ反映するXcode標準設定を使う。project設定の有効化と、実際のprofile登録・署名検証は別に確認する。

## Xcode標準のバージョン管理とArchive

公開バージョンは`MARKETING_VERSION`、ビルド番号は`CURRENT_PROJECT_VERSION`で別管理する。[開発方針](../policies/開発方針.md#公開バージョンとビルド番号)を正本とし、全shared schemeのBuild後処理からApple標準の`agvtool next-version`を実行して次回用のビルド番号を進める。公開バージョンは自動変更せず、`1.0`を`1.0.0`へ補正しない。採番用の設定ファイル・target・別カウンタは追加しない。

Xcodeのproject navigatorで`RideIntercom` projectを選び、App targetの **General → Identity → Version / Build** で表示を確認する。projectの`Versioning System`は`Apple Generic`を使う。共通値を確認するときは、PROJECTの **Build Settings → Versioning → Marketing Version / Current Project Version** を編集し、Debug・Release・検証構成を揃える。App・Widget・Watchにtarget固有の上書きを置かず、projectの共通値を継承する。

| 操作・設定 | 動作・確認事項 |
|---|---|
| Run・Build・Test・Archive | Xcode標準の操作を使う。CLIも同じshared schemeを指定した標準の`xcodebuild`を使う。Build後処理が次回用の`CURRENT_PROJECT_VERSION`を自動更新する。専用の事前コマンドやXcodeの終了は不要 |
| 新しい配布ビルド | Archiveでも通常Buildと同じ後処理を行う。今回のArchiveの番号は成果物で確認し、次回用設定はその後に進む。開始時点への即時反映や厳密な連番は要求しないが、前回と同じ番号を使い続ける状態は許容しない |
| App・Widget・Watch | 同じprojectのBuild設定をApp・Widget・Watch・テスト対象が継承する。同一成果物内の番号を揃え、Watch単独schemeを含む全scheme・Debug/Release/検証構成で次回番号を進める |
| AppのInfo.plist | `prepare_archive_info.py`は原本のcustom keyをコピーし、Debug通常利用時だけ試用接続情報を注入する。番号・公開バージョン・実行形式・platform情報は生成せず、projectにもアクセスしない。`GENERATE_INFOPLIST_FILE=YES`とXcodeのProcessInfoPlistFileが標準項目と`INFOPLIST_KEY_*`を反映し、その後に署名する |
| Widget・WatchのInfo.plist | 原本のInfo.plistと`GENERATE_INFOPLIST_FILE=YES`によるXcode標準の生成を使う。独自生成scriptは使わず、原本のextension・Watch設定と保存namespaceを維持する |
| スクリプトsandbox | AppのInfo準備は宣言済みのsource Info.plistとscriptだけを読み、sandboxを有効のまま使う。採番はBuild後処理へ置き、Info生成や署名後のbundle書換へ混ぜない。開発設定・VS Code設定の検査は独立したCLI検証で行い、Xcodeの通常buildの前提にしない |
| 設定の欠落・破損 | 低い番号へ自動初期化しない。配布済みの番号と履歴を確認してXcodeの設定を復旧する |
| 別Mac・別checkout | 新しい配布ビルドの番号を担当者間で共有し、同じ番号の別配布物を作らない。独自の採番lockや別カウンタは置かない |

Archiveは`RideIntercom` schemeと配布先を選び、**Product → Archive** で作成する。Organizerで対象ArchiveのVersion / Buildを確認し、**Validate App / Distribute App** の標準手順で配布する。同じArchiveを再配布する場合は、作り直さず保存済みのArchiveを選ぶ。

Organizerの **Manage version and build number** はXcode標準の配布時番号管理として選択できる。有効にする場合は配布時にXcodeが設定する番号を確認する。無効にする場合はArchiveの番号を使うため、配布先と重複しない番号を事前に設定する。CLIでIPAを書き出す既存の`scripts/ExportOptions.plist`は`manageAppVersionAndBuildNumber = false`、`destination = export`を維持し、保存済みArchiveの番号で書き出す。書き出しだけでアップロードはしない。

根拠: Appleの[標準採番ツール](https://developer.apple.com/library/archive/qa/qa1827/_index.html)、[Version / Buildの設定](https://help.apple.com/xcode/mac/current/en.lproj/devba7f53ad4.html)、[配布の準備](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution)、[ビルド設定](https://developer.apple.com/documentation/xcode/build-settings-reference)、[CFBundleVersion](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion)。独自採番を使っていた時点の検証は[当時の記録](../validation/history/配布ビルド採番とOrganizer認証調査.md)と[Widget・共通採番の記録](../validation/history/Widget表示と共通採番のローカル検証.md)に残し、現行の番号管理とは区別する。

## 配布時の署名設定

現在のAppはCloudKitを使用しないため、`RideIntercom.entitlements`にはiCloudサービス・コンテナの権限を含めない。空のコンテナ一覧とCloudKitだけを有効にすると、App Store Connectの配布検証でiCloud環境の不備として拒否される。署名設定を変更した場合は新しいArchiveを作成し、OrganizerでそのArchiveを選んで配布する。既存Archive内の署名設定はソースの変更だけでは更新されない。

## 配布時の暗号化申告

App Store Connectでアップロードごとに暗号化の質問へ回答する手間を省くため、AppターゲットのDebug・Releaseビルド設定に`INFOPLIST_KEY_ITSAppUsesNonExemptEncryption = NO`を設定する。Appのmetadata生成phaseがこの設定を読み、iOS/macOSのビルド時に生成されるInfo.plistへ`ITSAppUsesNonExemptEncryption = false`（Boolean）が反映される。この値は、暗号化の使用についてAppleへの書類提出が免除されるという申告であり、通信の暗号化を無効にはしない。

| 項目 | 現在の設定・判断根拠 |
|---|---|
| Apple OSの暗号化 | CryptoKitのAES-GCM、HMAC-SHA256、SHA256と、暗号化必須のMultipeerConnectivityを使用する |
| 同梱ライブラリの暗号化 | WebRTCのDTLSを使用するため、Apple OS内の暗号化だけを使用するアプリには分類しない。使用経路は[RTC仕様](../spec/packages/RTC.md)を参照 |
| 配信地域の前提 | 利用者の配信方針によりフランスを対象外とする。Appleの書類要件表では、OS外の標準暗号化に対するフランス向け申告書はフランスで配信する場合に必要 |
| 再判定する条件 | フランスへの配信開始、独自・非標準の暗号化の導入、依存ライブラリや暗号化方式の変更時には申告を見直す |
| 配布への反映 | 変更後に新しいArchiveを作成してアップロードする。既存Archiveやアップロード済みビルドの申告は更新されない |

配信地域はApp Store Connect側で管理し、このInfo.plistの値では制限されない。現在の配信地域やApple側の処理結果を、この設定の追加だけで確認済みとは扱わない。

根拠（2026-10-23確認）: Appleの[申告キーの定義](https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption)、[暗号化に関する書類要件](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption)、[書類提出が不要な場合のInfo.plist設定](https://developer.apple.com/help/app-store-connect/manage-app-information/determine-and-upload-app-encryption-documentation/)。

## 申請情報を事前設定できる範囲

| 項目 | 保存場所・反映方法 | Web入力との関係 |
|---|---|---|
| 暗号化申告 | 上記のAppビルド設定 | 新しいビルドに申告を含め、繰り返しの質問を省く |
| Bundle ID・バージョン・ビルド番号・アイコン | Xcode projectとasset catalog。設定済み | ビルドから読み取られる。ストア掲載用のバージョン情報は別途管理 |
| 端末上の表示名・マイクとローカルネットワークの使用説明 | Appの`INFOPLIST_KEY_*`。設定済み | 権限ダイアログなどに使用。ストア掲載名・説明文の代わりにはならない |
| macOSカテゴリ | `LSApplicationCategoryType`。Lifestyle設定済み | App Store Connect側のカテゴリと一致させる必要があり、Web側の指定を省くキーではない |
| Required Reason APIの使用理由 | `RideIntercom/PrivacyInfo.xcprivacy` | Appへ同梱する。App Privacyの回答やプライバシーポリシーURLの代わりにはならない |
| ストア説明・キーワード・サポートURL・更新内容 | App Store Connectのバージョン別メタデータ | Info.plistから自動入力されない。確定した内容は公式APIで登録できる |
| 年齢制限・コンテンツ権利・App Privacy・配信地域・価格・審査連絡先 | App Store Connect側の申請情報 | 実際の機能、運用、権利者、公開先に基づき登録する。ビルド設定だけでは代替できない |

プライバシーマニフェストのAPI理由は[通信仕様](../spec/App/通信仕様.md#申請用のapi利用理由)を参照する。Appの同期フォルダ内に配置し、既存のtarget所属によってリソースとして扱う。新しいArchiveのApp bundle（macOSは`Contents/Resources`）に含まれることと、Organizerの`Generate Privacy Report`でSDK分を含む申告を確認する。

マニフェストは確認済みのAPI利用理由を記載し、収集データ・追跡について未確認の「なし」を埋めない。通話音声、参加者ID、診断情報、Cloudflare側の保存・処理を確認してApp Privacyへ回答する。WebRTC同梱zipにもマニフェストは存在するが、App側の申告でSDK自身の申告を代替しない。

根拠（2026-10-29確認）: Appleの[Required Reason API](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype)、[App Privacy](https://developer.apple.com/app-store/app-privacy-details/)、[申請情報一覧](https://developer.apple.com/help/app-store-connect/reference/app-information/required-localizable-and-editable-properties)、[バージョン情報のAPI](https://developer.apple.com/documentation/appstoreconnectapi/app-store-version-localizations)。

## VS Codeの開発操作

`Tasks: Run Task`から次を使う。タスクはshell文字列を再解釈せずprocessとして実行し、working directoryはrootに固定する。rootを単独でOpen Folderした場合にも同じタスクを利用できる。package単体を独立workspaceにする場合はそのpackageのSwiftPM操作を使う。

| タスク | 内容 |
|---|---|
| `Check development setup` | フォルダ同期・target分離・editor設定・package参照の検査 |
| `Check documentation` | 相対リンク・開発ツール入口・READMEからの到達性・空文書ディレクトリ・Settings仕様の記載を検査 |
| `Build and run macOS` | 既定build task。App bundleを通常起動しプロセス存在を検証 |
| `Debug macOS (LLDB)` | 既存script経由でbuildし、統合terminalのLLDBでdebug。`run` / `breakpoint set` / `bt`等を使用 |
| `macOS logs` | 通常起動後に統合logを表示 |
| `Test headless / packages / macos / ios / ios-ui / pair / worker / scripts` | 既存validate入口を呼ぶ。iOSは音声E2Eと共通の専用Simulatorを再利用し、作成前に過去の不要端末を整理 |
| `Open Xcode` | 同じcheckoutのprojectをXcodeで開く |

`DEVELOPER_DIR`とSwift toolchainは`/Applications/Xcode.app`を既定とする。別名のXcodeを使う場合はworkspaceと`.vscode/settings.json`の両方を一致させる。system全体のxcode-selectは変更しない。

Swift拡張のSourceKit-LSPは各Swift Packageで利用する。Appの`.xcodeproj`に対する補完・indexはSwift拡張だけでは限定的であり、Xcode同等のApp index対応済みとは扱わない。Appの正確なcompile診断・実行・テストは共有xcodebuild入口を使い、SwiftUI Canvas・署名・Appの完全なindex/debug UIはXcodeを利用する。外部build serverは今回追加していない。

## 配布用アプリアイコン

正式図案は利用者指定の`RideIntercom/Assets.xcassets/AppIcon.appiconset/AppIcon-4,096.svg`。前景を抽出した`RideIntercom/AppIcon.icon`をiPhone・iPad・Mac・Watchで共有し、Liquid Glassの光沢・影・外観切替はOSに任せる。レイヤーとWatchの円形配置は[アイコン適用](../spec/App/UI/アイコン適用.md#正式アプリアイコン)を正本とする。

| 操作 | 手順 |
|---|---|
| 図案の編集 | 正本SVGを編集する。制作時の非表示の参照画像はそのまま保持し、配布レイヤーには含めない |
| 全画像と前景の再生成 | `python3 scripts/generate_app_icons.py`。`rsvg-convert`（Homebrewの`librsvg`）を使用し、道とシュプール・波形のSVGとApp/Watchの全PNGを更新する |
| 更新漏れの確認 | `python3 scripts/generate_app_icons.py --check`。正本から再生成した10アセットとのbyte一致を確認し、不一致なら失敗する |
| ガラス効果の調整 | Xcode付属のIcon Composerで`RideIntercom/AppIcon.icon`を開く。`icon.json`は効果・対応platform・Watch配置の設定であり、図案再生成では上書きしない |
| ビルド設定 | AppとWatchの全configurationでApp Iconを`AppIcon`にする。WatchはAppと同じ`.icon`をresourceとして明示参照する。各asset catalogの同名PNGは平面の配布素材として保持する |
| 配布物の確認 | App bundleの`Assets.car`に`AppIcon`の`IconImageStack`と道・波形のvectorがあり、iOSでは120px・152pxのPNG、Macでは`AppIcon.icns`、Watchでは`CFBundleIcons`が出力されることを確認する |

Appleの[Icon Composer手順](https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer)と[アプリアイコンHIG](https://developer.apple.com/design/human-interface-guidelines/app-icons)を参照する。旧暫定素材の生成指示と今回の検証は[正式アイコンの検証履歴](../validation/history/正式アイコンとLiquid Glassの検証.md)に保存する。

## 継続検証

| 実行地点 | 検査と失敗時の扱い |
|---|---|
| 開発設定のCLI検査 | `python3 scripts/check_development_setup.py`でread-only検査する。通常のXcode build phaseから分離し、VS Codeや任意検証の設定を標準buildの前提にしない |
| `scripts/validate.sh`全mode | 最初に同じ検査。失敗をresults.tsv / results.jsonへ記録し、独立段階は継続 |
| `scripts/validate.sh scripts` | 文書検査7件、設定検査の回帰7件、WebRTC scripts2件、Cloudflare scripts4件 |
| `.github/workflows/development-setup.yml` | push / PRで同じ設定検査・文書検査・回帰。リモートへ送った後に動く定義であり、今回GitHub実行済みではない |

`python3 scripts/check_development_setup.py`単独でも実行できる。必要な同期フォルダの削除・navigatorからの切り離し・閲覧用参照のtargetへの誤所属と、project自身を含む再帰同期・自己project参照を検出する。packageを追加するときはXcodeのlocal package参照とVS Codeのworkspace rootsを合わせる。既存の同期フォルダ内ではソースファイルごとの一覧更新・generator・常駐watcherは不要。新しいroot項目にはXcode標準のAdd Filesを使う。

通常検証と独立音声E2Eは、ファイルのSHA-256を共通処理で記録し、Xcode projectを含む入力の一致を確認する。ビルド番号・公開バージョン・署名設定も除外せず、検証中の設定／ソース変更や対象ファイルの増減は失敗にする。通常のビルドは番号を変更しない。

確認待ちと結果は[検証](../validation/README.md)で管理する。
