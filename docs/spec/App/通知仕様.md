# 通話の通知仕様

通常のAPNsアラートから、利用者のタップを既存の通話開始処理へ接続するAppの契約である。通知の受信・送信許可と、通話の所属・本人確認・利用権・24時間条件を分ける。認証資格と公開IDは[Worker契約](../server/Worker.md)、通話の実行は[共通操作](通信仕様.md#通話先と操作対象の共通境界)を使う。通知APIの詳細はserver側の通知仕様が正本であり、Appはその固定DTOを使用する。

## 責務と入口

| 対象 | 契約 |
|---|---|
| HTTP | `InternetAccountClient`の通知extensionでdevice・grant・call requestを扱う。既存のHTTPS origin検証・redirect拒否・10秒request timeout・32KiB応答上限を共用し、native `ri1`資格だけを送る |
| 状態 | `CallNotifications`はログインモデルに属し、Nativeログイン世代、現在の確認済み公開principal、サービスと資格の一致を各await後に確認する。旧結果で新モデルの状態を変えない |
| OS | `NotificationSystem`が許可とAPNs登録を扱い、`AppNotificationBridge`がnative delegateを現在のAppCallOwnerへ渡す。単体・ローカル自動検証では実OS許可・APNs登録を要求しない |
| 許可 | SettingsのEnable Notificationsでalert/soundのOS許可を求める。起動・前面復帰の再確認は許可シートを自動で出さず、既に有効化した端末の登録だけを再要求する |
| 受取後の表示 | 前面ではpayloadの版・requestID・recipientIDに加え、現在ログインのrecipient一致と端末受信ONを端末内で確認する。OFF・ログアウト・別recipient宛を表示しない。この表示判定だけのためのネット照会はしない |
| 通話開始 | 到着だけでは開始しない。利用者の通知タップ後にserverのGETで再確認し、現在のSavedUserへ解決して`startCall(to: .user, accountAccessID:, allowSwitchingCall: false)`へ渡す。別の通話を通知だけで切り替えない |
| iPhoneで応答 | iOSは固定category`RIDEINTERCOM_CALL_REQUEST`へ背景action`RIDEINTERCOM_RESPOND_ON_IPHONE`（表示「iPhoneで応答」）を登録する。optionsは空。default tapまたは一致するcategoryの当該actionだけを同じ応答処理へ通し、未知action・dismissを拒否する。Watchに転送された通知のこの背景actionはiPhoneで処理し、Watch上の通常tapはWatch Appを開くだけと区別する |

## 端末の登録・取消

| 状態・操作 | 契約 |
|---|---|
| 登録 | OSが返す可変長device tokenをその処理中だけ保持し、hex・environment・bundle topicをPUTする。tokenをUserDefaults・Keychain・ログへキャッシュしない |
| environment | Infoの`RideIntercomAPNsEnvironment`を優先し、developmentをsandbox、productionをproductionへ変換。キーがない検証buildではDebug/sandbox・Release/productionへfallbackする。Info・OS別entitlement・単一build設定を揃える設定本体はOS設定工程の責務 |
| ON/OFFの保存 | アカウント別の既存Defaultsに有効化の希望を保存する。通知の許可とは別の購入済みフラグ・server購入台帳は作らない |
| OFF | 希望を即時OFFにし、tapと前面表示を直ちに拒否する。登録資格が読めない場合もDisable操作を使える。server取消が失敗した場合はremovalPendingの1bitを保持し、Check Notificationsと前面復帰でDELETEを再試行する |
| 遅延処理 | 同じモデルのdevice PUT/DELETEだけをin-flight Taskで直列化し、実行直前に最新の希望を確認する。古いPUTの後にOFFのDELETEが続き、再ONした端末の新登録を遅いcleanupで消さない。新しい長期queue・台帳は作らない |
| ログアウト・削除 | 待機・旧表示を退役させ、進行中の登録の後に旧資格の宛先取消を試みる。既存のserver資格失効・アカウント削除も配送対象を無効にする。取消の応答待ちで端末内のログアウトを止めない |

## 相手ごとの用途別許可

| 対象 | 契約 |
|---|---|
| 対象 | 直接招待でSavedUserになり、同じサービスの確認済みprincipalと保存端末鍵がある相手だけ。group内だけの相手、名前の一致、相手IDの知識だけでは発行・送信しない |
| 明示同意 | 相手編集のAllow Call Requestsで受信者がserver grantを発行する。直接招待やOSの通知許可を、その相手への通知同意へ自動変換しない |
| 交換する接続 | 相手との内部1対1groupで、対象principalが一致し、接続・認証中のpeerがその相手1人だけの場合に限定する。自分の別端末を相手扱いせず、通常groupでは送信も受理もしない。既存broadcastへ個人用capabilityをそのまま流さない |
| 署名 | 既存の端末署名鍵を用途`callNotificationPermission`へ区切って使う。owner・allowedSender・revision・grantを署名し、受信は保存済みの直接相手の鍵と照合する。group共通秘密を通知許可の発行権限へ変換しない |
| capabilityの照合 | 受領時と送信前にJWT内のissuer・audience・recipient・sender・grantIDが選んだ相手と本人に一致することを拒否条件として確認する。decodeだけでserver署名や有効性を信頼せず、実送信の署名・active grant・本人資格の検証はserverに任せる |
| 保存 | 発行したgrant、相手から受け取ったcapability、取消と再送のrevisionを既存のアカウント別`.InternetConnection` Keychainの`notification-permissions`へ保存する。GroupSnapshotや通常設定へcapabilityを混ぜない |
| 発行revisionと回収 | アカウント別の既存Defaultsへ単一の発行counterを保存し、新しいrevisionはcounterと現在行のrevisionの大きい方に1を加える。取消済みでreceivingがなく受信OFF、同principalのSavedUserもない現在ownerの行だけを回収する。回収前に旧行の最大revisionをcounterへ引き継ぎ、Keychain保存成功後だけメモリから外す。再追加でrevisionを戻さず、符号・破損・上限は既存の失敗経路へ戻す |
| 既知の別端末 | 最後に受領した相手端末鍵とrevisionだけを保持し、同じ鍵の古い更新を拒否する。別の既知端末の独立counterで新grantを受け取れ、その端末の取消だけが現在選択中のgrantを外す。他端末の取消で現在の別grantを消さず、端末別の履歴台帳は作らない |
| 連絡先統合 | 既に確認済みの同じprincipalへ端末を統合しSavedUserのUUIDが変わっても、既知の許可と元のgrantIDを維持する。別principal・別サービスへ持ち越さない |
| 相手削除・許可OFF | ローカルの受信許可を先に無効化し、本人が発行したgrantをDELETEする。送信権限とtapも現在のSavedUserから再解決し、削除済み相手を復活させない。失敗した既知の取消はオンライン復帰時に再試行する |
| 保存失敗 | 新grantを発行した後にKeychain保存が失敗した場合は、そのgrantをbest-effortで1回取消す。保存を成功扱いにしたり、独自の永続orphan台帳を増やしたりしない |
| 読取不能 | 読み取れない許可を空データで上書きしない。Check Notificationsで再読取でき、端末の宛先取消は相手の許可データが読めなくても実行できる |

許可の保存・交換は現状端末別である。他の本人端末が別に発行したgrantの一括取消や、端末間の即時同期は提供しない。端末通知OFFは当該端末の宛先を外す。アカウント削除はserver側の当該公開IDの許可を取消し、再登録で旧許可を復活させない。新しい端末間同期の仕組みをこの工程へ追加しない。

## 送信結果・tap・保持する情報

| 対象 | 契約 |
|---|---|
| 送信 | 直接相手から受け取ったcapabilityとUUID requestIDだけをPOSTする。名前・自由text・group情報をserverへ送らない |
| 結果 | acceptedは通知サービスの受付であり、配送・閲覧・応答・通話成立を意味しない。processing・宛先なし・再試行待ち・拒否・取消を分ける。自動再送や状態の定期pollingはしない |
| 通知本文 | serverの固定`CALL_REQUEST_TITLE`/`CALL_REQUEST_BODY`を英日でlocalizeする。payloadは版・requestID・recipientIDだけで、表示名・自由文・group秘密・capabilityを含めない |
| tapの再確認 | recipient一致・端末ONを端末内で確認後、GETでserverの120秒期限、取消、grant、元sender資格を再検証する。戻ったsenderを現在の直接相手へ照合し、await後も世代・資格・期限・ローカル許可を再確認する |
| 取消 | 送信者は元requestIDをDELETEできる。取消・期限切れの通知は既存の通話を終了させず、新しい開始だけを拒否する |
| データ消去 | Keychainは既存のアカウント別`.InternetConnection`全消去、希望と取消pendingは同じDefaultsの全消去へ含まれる。serverへ相手一覧・表示名を保存する機能を加えない |

OSが背景で既に表示・配送した通知は、Appの前面判定だけで取り消せない。普通のAPNsアラートであり、VoIP Push・CallKit・通知到着だけの音声開始は提供しない。実OS、鍵設定、外部配送と署名の受入は[未確認事項](../../validation/未確認事項.md#通常通知の受入)、ローカル証跡は[通知Appの接続と認可の検証](../../validation/history/通知Appの接続と認可の検証.md)で区別する。
