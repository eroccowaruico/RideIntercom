# 通知宛先と呼出し API

## 範囲と認可

通常のAPNs表示通知から、利用者のタップをAppの共通通話操作へ渡すためのserver基盤。[WorkerのApple認証](Worker.md#apple認証と端末資格)で発行した有効な`ri1`端末Bearerだけを受け付ける。試用の静的資格、公開IDの知識、groupの共有鍵、招待receiptは送信許可にならない。通知許可の拒否・通知設定不足・配送失敗を、既存の認証・Local通話・購入・復元の失敗へ変換しない。

受信者は送信者の公開`userID`を指定して、**呼出し通知専用**のcapabilityを発行する。署名には既存の`DEVICE_IDENTITY_SIGNING_KEY`を使うが、`typ=rideintercom-notification+jwt`、`aud=rideintercom-call-notification`、HTTPS originのissuer、送信者のsub、受信者のrecipient、ランダムUUIDのjtiを照合する。端末証明としてもgroup参加権としても使用できない。Appはcapabilityを不透明な文字列として保持し、serverから確認した本人IDと対応させる。

serverには受信者ごとの**有効なgrantIDのSHA-256集合**だけを保存する。取消済みtombstoneを積み上げず、取消時に集合から削除する。月ごとの再発行を要求する期限は設けない。再発行は新しいgrantIDなので取消済みcapabilityは復活しない。アカウント削除、公開IDの変更、署名鍵の変更でも旧capabilityは使えなくなる。宛先の登録資格は期限を持ち、再ログイン時に宛先を再登録する。通常のサインアウトはその端末の宛先と資格を失効させ、他端末と未取消のアカウント単位の通知同意は維持する。

**直接招待関係の成立・相手とのcapability交換・ユーザー削除時の取消はApp側の接続点**。serverは連絡先一覧を持たず、直接関係を推測しない。Appは直接招待した相手にだけ発行・交換し、groupで会っただけの相手には発行せず、送信・タップ時も保存ユーザーとの対応を確認する。このserver工程だけで、group外の通知を利用可能としていない。

## HTTP 契約

全APIは`Authorization: Bearer <ri1>`を必要とし、JSON応答に`Cache-Control: no-store`を付ける。以下のpathは`/api/notifications`からの相対表記。余分なJSON fieldを拒否し、共通bodyサイズ・読取時間制限も適用する。公開IDは64桁小文字hex。UUIDは大文字・小文字を受け付け、同じIDとして小文字へ正規化する。時刻はUnix epochの**ミリ秒**。

| 操作 | 要求 | 成功応答・認可 |
|---|---|---|
| PUT `/device` | `{token, environment, topic}` | `200 {registered:true}`。現在の資格のdeviceIDに1件。tokenはAPNsのバイト列をhexへ変換した2〜4096文字の偶数長。32byte固定にしない。environmentは`sandbox`または`production`でserver設定に一致、topicも設定に完全一致 |
| DELETE `/device` | bodyなし | `200 {}`。現在の資格に対応する宛先のみ解除。通知停止・設定不足でも可能 |
| POST `/grants` | `{senderUserID}` | `200 {grantID, capability}`。受信者本人だけ発行、本人宛てのgrantは拒否。senderUserIDへ送信者を固定。capabilityの最大受入長4096文字 |
| DELETE `/grants/{grantID}` | bodyなし | `200 {}`。自分の有効集合からのみ削除。存在しないIDも同じ応答。他人の許可を変更しない |
| DELETE `/grants` | bodyなし | `200 {}`。自分が発行した全許可を取消。端末消去・発行応答紛失時の回復手段。相手一覧やcapability一覧は返さない |
| POST `/calls` | `{capability, requestID}` | `200 {requestID, expiresAt, status}`。capabilityのsenderと現在の本人公開IDが一致し、受信者の有効集合にgrantがある場合のみ受付。固定通知のみ。本文・名前・group・任意URLの指定は不可 |
| GET `/calls/{recipientUserID}/{requestID}` | bodyなし | `200 {requestID, expiresAt, status, senderUserID}`。受信者本人だけ取得。タップ時に期限・取消・有効grant・元送信者の資格世代を再確認する |
| DELETE `/calls/{recipientUserID}/{requestID}` | bodyなし | `200 {}`。元送信者の公開IDだけ取消。同じIDの取消再送も可。受信者や第三者には許可しない |

GETとすべてのDELETEは通知機能停止中でも可能。認証不正は401、入力不正400、送信許可不正403、他人の取得・取消や未知の呼出し404、取得時の期限切れ・取消・grant失効・送信者資格失効410。発行の有効集合上限または処理中の本人失効は409 / `grant_limit_or_inactive`、頻度・保持上限は429。通知作成・登録に必要な設定不足または内部通知処理失敗は503 / `notifications_unavailable`。外部providerの本文や秘密を返さない。

`status`は`processing`、`accepted`、`no_destinations`、`retry_later`、`rejected`、`cancelled`のいずれか。`accepted`は少なくとも1端末について**APNsが200を返した**という意味で、端末表示・利用者の応答・通話接続成功ではない。`processing`は同時再送または処理中断後にも残り得る。同じrequestIDの再送は記録済み結果を返し、配送を追加しない。再試行は利用者による別requestIDの新規呼出しとし、自動再送queueは設けない。

## 費用・悪用を抑える境界

| 対象 | 上限・期限 | 回収・失敗時 |
|---|---|---|
| APNs宛先 | 有効なnative登録最大8端末、各deviceIDに1件 | credentialの30日期限内。再認証・sign-outで旧世代を外し、account削除で全件削除 |
| 宛先登録とgrant発行 | 合算60回/UTC分/account | 429。取消操作にはこの制限を適用しない |
| 有効grant | 最大256/account | 409。個別取消または全取消で枠を回復。取消済みhashを保持しない |
| 送信要求 | 60回/UTC分/sender account | 重複要求もこの入口の枠を消費、429 |
| 新規呼出し | 20回/UTC分/recipient account | 重複は新規枠を消費しない。複数送信者による集中も同じ枠で制限 |
| 呼出し記録 | 最大512/recipient account、作成から24時間保持 | 重複抑止用。期限・取消後も保持期限まで再配送しない。alarm・次回開始で削除 |
| 呼出しの応答期限 | 作成から120秒 | APNs expirationとGET検証へ同じ期限。24時間の通話利用権とは無関係 |
| 配送 | 1要求につき最大8宛先、各fetch timeout 8秒 | 固定Apple hostへ逐次送信。外部からURLを指定しない |
| 公開ID索引・token所有索引 | 登録資格の期限まで、最大30日 | 通常は置換・sign-out・account削除で該当索引を除去。障害や並行処理の残りはalarmで回収 |

同一account・公開IDのrouting索引は既存と新登録の長い方の資格期限を保持し、古い端末の再登録で他の有効端末の経路を短縮しない。token所有索引にはこの延長規則を適用せず、最後の登録世代を優先する。

索引は公開IDまたは`environment|topic|token`のSHA-256ごとに別のSQLite DOを使う。token索引は現在の所有account・device・ランダムregistrationIDを保持し、同じtokenが別アカウントへ登録された後に旧アカウント向け配送を続けない。grant集合、宛先数、短期呼出し記録は上限を持ち、索引は期限を持つ。これらの制限は通知の費用・濫用を抑えるもので、購入や通話権を表す台帳ではない。

配送直前にsender資格、recipientの公開ID・grant・呼出し・宛先世代、token索引の所有を再確認する。遅れて返った410は配送時のregistrationIDと一致する宛先だけ削除し、新登録を消さない。取消・削除・sign-out中の残り端末への送信は止める。すでにAPNsへ渡った1要求は取り消せないため、payloadに個人名を載せず、タップ時GETで再検証する。索引掃除の失敗を既存認証や削除の停止条件にしない。残った索引だけでは旧UserAccountの資格・grantを通過できないが、物理的な索引消去完了と即時失効は区別する。

## 保存する情報と配送

UserAccountにはAPNs token・environment・topic・端末資格hash・registrationID・期限、有効grantID hash、短期呼出しのID・sender公開IDと内部資格世代・期限・結果、固定少数のレートカウンタだけ追加する。索引には内部locatorと公開ID・端末/登録世代・期限を保持する。表示名、メール、連絡先一覧、group情報、購入状態、capability JWT、端末Bearerの秘密は保存・ログ出力しない。APNs tokenもログへ出さない。短期呼出しの送信者は取得時の本人照合に必要な情報であり、恒久的な友達一覧へ昇格させない。

APNsの固定payloadは次の形。Appは`CALL_REQUEST_TITLE`と`CALL_REQUEST_BODY`の英日表示文字列を用意する。自由文や深いlinkは受け取らない。

```json
{"aps":{"alert":{"title-loc-key":"CALL_REQUEST_TITLE","loc-key":"CALL_REQUEST_BODY"},"sound":"default","category":"RIDEINTERCOM_CALL_REQUEST"},"version":1,"requestID":"<UUID>","recipientID":"<public userID>"}
```

`aps.category`は固定の`RIDEINTERCOM_CALL_REQUEST`だけを付ける。Appが同じcategoryへ応答actionを登録するための識別子であり、要求からcategory・action・通知本文を指定できない。category自体は送信許可や通話開始を意味しない。iPhone宛て通知のWatch転送と背景actionの応答先は[Appleのaction規則](https://developer.apple.com/documentation/watchos-apps/adding-actions-to-notifications-on-watchos)に従う。Appでの「iPhoneで応答」の登録と共通判定への接続は後続App工程で行い、このserver変更だけで応答機能を完成扱いにしない。

`apns-push-type=alert`、priority 10、requestIDを`apns-id`と`apns-collapse-id`へ、120秒期限を秒に変換して`apns-expiration`へ設定する。HTTP 200はaccepted、410は該当宛先失効、429・5xx・通信失敗はretry_later、それ以外はrejected。APNs応答本文をAppへ転送しない。ES256 provider JWTは同じWorker isolateで50分再利用し、毎回生成しない。isolate再作成・複数isolate間の接続共有条件は実配送受入で確認する。

## 設定と未受入の範囲

`NOTIFICATIONS_ENABLED=false`がmain / previewの既定。公開設定は`APNS_TOPIC`と`APNS_ENVIRONMENT`、secretは`APNS_PRIVATE_KEY`（PKCS8 P-256）、`APNS_KEY_ID`、`APNS_TEAM_ID`。既存`DEVICE_IDENTITY_SIGNING_KEY`も必要。`NOTIFICATION_INDEX` bindingとSQLite migration v3を追加する。実値の配布、鍵作成・登録、デプロイはこの実装に含まない。通知設定を揃えても、既存SFUのSERVICE_ENABLEDやApple認証の設定を変更しない。

Workerのnative fetchを実配送候補とする。Cloudflareの[workerd側の一次報告](https://github.com/cloudflare/workerd/issues/4841)では本番proxyがHTTP/2へ接続する一方、ローカルworkerdの直接接続とは挙動が異なる。`node:http2`のstubだけを理由にnative fetchが不能とは判断しない。本工程の試験はMiniflareのoutbound adapterが外部接続前に応答を代替し、実APNsへ送っていない。**配置したWorkerからのHTTP/2・provider JWT/接続再利用・APNs受入、署名entitlement/provisioning、実端末のtoken登録・通知許可・表示・応答は未確認**。iOSとmacOSのApp lifecycleへの接続、背景/終了/ロック状態、拒否・遅延・重複・取消後タップも別に受け入れる。PushKit、PTT、silent push、自動通話開始の実装ではない。
