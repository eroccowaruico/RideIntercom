## 録音再生の末尾を排出してから停止

録音開始修正は`4048fc3c`として先にコミットした。続く既存の有音E2Eで、5秒の壁時計だけで再生を停止すると初回の末尾48 samplesが欠けることを再現した（`.validation/recording-button-speech-green-20261102/`）。録音・送信処理済みの入力は240,000 framesで、出力の開始遅れは41ms、観測出力は5.04秒だった。2回目は完全一致し、録音全体が無音になる問題ではなかった。

端末本体だけ、既存sourceの残りbuffer・native出力遅延・20msの出力観測2packet分の排出を待ってから停止する。追加待機は既存の有限再生予算内の最大1秒とし、超過は失敗にする。Watchの終了時間は維持する。

|---|---|

## 1人で待つ通話を再接続中と出さない

2026-11-09の利用者指示（コールの開始）により、[画面実装とデザイン見本の差分](../../backlog/画面実装とデザイン見本の差分.md#call)の「実装の状態が実際の状況と違う」（優先度 高）を対応し、バックログから外した。Advancedの通話で1人で待つと、状態が「Local Connecting」から赤い「Reconnecting / Offline」に変わっていた。

原因はRTCの`RouteManager.updateState`だった。どのrouteもつながっていず、再試行を待つrouteが1つでもあると`reconnecting`にしていた。試験環境ではInternetのrouteが接続に失敗して再試行を待つため、Localが探索を続けていても通話全体が再接続中になっていた。画面ではなく状態の導出を直し、初回の試行中のrouteがある間は`connecting`のままにした（[RTC仕様](../../spec/packages/RTC.md)）。再試行中のroute自身は数えないため、Internetだけの通話で切れたときは従来どおり`reconnecting`になる。

| 確認 | 結果・証跡（`.validation/`配下、ローカルのみ） |
|---|---|
| 失敗の再現（変更前） | UI試験`testAdvancedCallAloneReportsWaitingNotReconnecting`が、12秒間の状態`["Local Connecting", "Reconnecting / Offline"]`で失敗（`design-alone-20261109-red`）。RTCの単体試験`aRouteStillSearchingKeepsTheCallConnectingWhileAnotherRetries`も最初の期待で失敗 |
| RTC package | `swift test`の全119件が成功。1回目は既存の`eightLocalPeersTalkWhileInternetIsUnavailable`が1件失敗したが、単独では変更前・変更後とも2回ずつ成功し、全体の再実行も成功した（負荷による時間依存とみられる） |
| App UI | 同じUI試験が成功（`design-alone-20261109`）。画像で、1人で待つ間は「Local Connecting」（橙）のままであることを確認 |
| 未確認 | 実機でInternetがつながる環境では、もともとInternetのrouteが接続済みになるため、この経路は通らない。初回の試行中のrouteがなくなれば`reconnecting`になることは、単体試験の2つめの期待（Localも失敗した後）で確認した。Internetだけの設定で切れて戻る場合は、再試行中のroute自身を数えない導出から変更前と同じになるが、その場合を直接確かめる試験は追加していない |
