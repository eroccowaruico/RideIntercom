## 録音再生の末尾を排出してから停止

録音開始修正は`4048fc3c`として先にコミットした。続く既存の有音E2Eで、5秒の壁時計だけで再生を停止すると初回の末尾48 samplesが欠けることを再現した（`.validation/recording-button-speech-green-20261102/`）。録音・送信処理済みの入力は240,000 framesで、出力の開始遅れは41ms、観測出力は5.04秒だった。2回目は完全一致し、録音全体が無音になる問題ではなかった。

端末本体だけ、既存sourceの残りbuffer・native出力遅延・20msの出力観測2packet分の排出を待ってから停止する。追加待機は既存の有限再生予算内の最大1秒とし、超過は失敗にする。Watchの終了時間は維持する。

| 検証 | 条件と結果 |
|---|---|
| iPhoneの回帰とUI | `.validation/recording-button-final-20261102/`、App 32件とSettings UI 1件が成功。native入出力、録音・再生、途中停止・再実行、入力期限・取消・失敗・通常通話の設定復帰を確認 |
| 送信処理後の有音波形 | `.validation/recording-button-speech-final-20261102/`、既存E2E 1件が成功。実入力clockのマイクPCMだけを既知発話fixtureに置換し、送信エフェクト・VAD・codecとnative出力を実行。2回とも入力240,000／出力243,840 frames、全量coverage成立、全信号相関1、正規化RMS誤差0、無音残差0、入力・renderのdrop 0。相手への通信や実マイクの音響品質の検証ではない |
| Macの実録音 | `.validation/recording-button-mac-acceptance-20261102/`、App 20件が成功。実マイク→送信処理→5秒録音→native出力を2回実行。初期のテストは入力準備を5秒録音と同じ期限で判定していたため失敗し、最初の有効入力待ちと録音待ちを分離した。完了・録音240,000 frames・実formatで5秒以上の出力という条件は維持。標準scheme／Debug-Validationと一時的なローカルad-hoc署名を使用し、配布署名の検証とは分ける |

Mac初回のnative準備に残る遅さは[改善候補](../../backlog/改善候補.md#voiceprocessingioと既定デバイスの開始安定性)へ保持する。録音開始・全量再生・再実行の成功と、初回準備時間の改善完了を区別する。

再生末尾修正は`81690a4a`として分けてコミットした。別作業のSettings統合後、`.validation/recording-button-acceptance-20261102/`ではnative録音2回は成功したが、UIテストが固定2回のスクロールではボタンへ届かず失敗した。既存の`revealSettingsControl`へテストだけを追従し、`.validation/recording-button-ui-acceptance-20261102/`でUI 1件が成功した。最終画面の同一ボタンから、録音・再生完了・途中停止・再録音を確認した。

最終の有音E2E・Mac実録音・iPhone UI各runの`final-source-correspondence.json`で、録音実装、実行したテスト、該当SettingsのSHA-256と最終ソースの一致を確認した。各成功runは失敗・skip・runtime warning 0。専用Simulatorの入力・出力・音量復元とshutdownも完了し、Mac全体の既定入出力は保持した。
