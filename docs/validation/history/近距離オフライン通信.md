# 近距離オフライン通信の調査と検証

## 背景と成立条件

2026-10-30、Local音声をMCSessionから認証済みUDPへ分離したことで、アクセスポイントもセルラー電波もない屋外の通話を失っていないか調査した。出発点は`44518d19`。Wi-Fiなしはアクセスポイント未接続を指し、Wi-Fi無線機能OFFと区別する。

| 調査対象 | 確認した内容と判断 |
|---|---|
| Network.frameworkの近距離通信 | Appleの[TN3151](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api)は、peer-to-peer Wi-FiをWi-Fiネットワーク設定なしに使えると説明し、Network.frameworkの`includePeerToPeer`を案内している。現行UDPは探索・待受・送信すべてで有効であり、APやセルラーを必須とする構造ではなかった |
| Multipeerだけでなければ不可能か | [TN3213](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework)は、MultipeerだけがApple peer-to-peer Wi-Fiを使えるという理解を明確に否定している。制御はMCSession、音声はNetwork.frameworkでも近距離無線を使える |
| Multipeerの信頼なし | [`MCSessionSendDataMode.unreliable`](https://developer.apple.com/documentation/multipeerconnectivity/mcsessionsenddatamode/unreliable)は即時に送れなければ破棄し、順序保証を行わない。音声向けbest-effortの選択肢である。ここから下位transportが常にUDPであるとは断定しない。再送なしUDPを明示できる現在の媒体分離を維持した |
| 端末の無線機能 | Bluetoothで制御peerを見つける可能性と、UDP音声が到達することを同一視しない。現在のLocal音声はpeer-to-peer Wi-Fiまたは利用可能なLANを必要とし、Wi-Fi機能OFFでBluetoothのみの通話は提供しない |
| 消費電力 | [peerToPeerIncluded](https://developer.apple.com/documentation/network/nwparametersprovider/peertopeerincluded(_:))はpeer-to-peer資源の電力負荷と不要時の停止を指摘する。通話停止でbrowser・listener・送受信flowを破棄する現行lifecycleを維持。通話中は途中参加・再発見のため探索を維持する。実消費電力は実機確認が必要 |

## 移動による経路変更の追加調査

Apple DTSの[peer-to-peer解説](https://developer.apple.com/forums/thread/751839)では、UDP/TCPの確立済み接続は別の経路へ自動移行せず、`betterPathUpdateHandler`を使う必要があると説明している。現行実装にはこのhandlerがなかった。AP接続から屋外のpeer-to-peerへ移る条件を想定し、利用可能な旧flowは保持しながら新flowを作り、ready後に切り替える処理を追加した。到達性喪失の通知も扱い、失敗中の音声packetごとの接続連打は2〜30秒のbackoffで防ぐ。再接続のために音声をためたり再送したりしない。

同資料はpeer-to-peer Wi-Fi自体が条件によって数百msの遅延を生じ得るとも説明している。無線区間の125ms達成はAPI選択だけで保証できない。アプリ内の待ちを減らす要求と125msの判定基準は維持し、実機で無線区間も含めて測る。

## 修正した差分

Localのpeer-to-peer設定自体にAP依存は見つからなかった。一方、全員が近くてもLocal / Internetへ常に同じ音声を送る経路方針は、近距離優先・通信費削減の要求と不一致だった。

| 変更 | 振る舞いと限界 |
|---|---|
| Local優先 | 即時UDP送信を受け付けた認証済みpeer集合をRTC route契約で返す。Internetの全既知参加者をLocalがカバーしたpacketはInternetコピーを省く。接続状態だけでは判断しない |
| 代替経路と混在 | Local未準備・送信上限・遠隔参加者があればInternet音声も即時送信。到着ACKや再送、追加の待機はない。SFU fan-out時の近隣重複は先着だけ再生 |
| 近距離parameters | UDP parametersの重複を共通化し、peer-to-peer有効、特定interface固定なし、セルラー禁止を全経路へ適用 |
| 要求と操作案内 | AP・セルラーなしの開始/継続、セルラー利用可能時のLocal優先、必要な端末無線機能を要求とマニュアルに明記 |

UDPの送信受付は受信確認ではない。無線損失のゼロ保証や、悪いLocalリンクでもInternetより必ず速いことは意味しない。音声を再送せず、受信側の既存の期限・連続性制御を維持する。Internetの制御接続・遠隔参加者探索は残るため、音声コピー削減を全サーバー費用ゼロとは扱わない。

## 検証記録

- 修正前の再現: `/tmp/ride-offline-red.log`。全員近距離でもInternet音声を送る期待違反を4件確認した。
- RTC package: `/tmp/ride-offline-rtc-final.log`。`swift test --package-path RideIntercom/packages/RTC --skip WorkerPairTests`でRTC 77件とnative WebRTC 4件が成功し、対象内skip・warningなし。Worker実サーバー付きpairは別工程のため対象外。8名がInternet接続失敗中も56方向で一度ずつ話せる結合、UDP実通信、再起動後の非再生、認証、制御待ち分離、Local未準備・復旧・遠隔参加者、peer-to-peer/セルラー禁止の条件を含む。
- 初回App音声E2E: `/tmp/RideIntercomAudioE2E/offline-local-priority-20261030/network`。両OS buildとAAC/Opus/PCMの6測定の音声同一性は成功・欠落0。ただし標準AACのMac受信118.664msに整列誤差枠10msを足すと125msを超えるため、総合は不合格。基準は維持する。source-stabilityと所有資源cleanupは成功。経路変更対応後にも再検証する。

同一MacのBonjour/UDPとMac–iPhone SimulatorはAPなしの独立した無線端末間試験ではない。屋外iPhone間の無線・Bluetooth・画面ロック・移動時125ms・消費電力は[未確認事項](../未確認事項.md)へ残す。実機合格として扱わない。

経路変更追加後のpackage検証: `/tmp/ride-path-red.log`で経路通知handler不在を再現し、`/tmp/ride-path-rtc-final.log`でRTC 78件・native WebRTC 4件が成功。実UDP flowにOS通知と同じcallbackを入力し、旧flow維持、新flow切替、到達性喪失、旧callback拒否、backoff中の送信抑制、破棄音声が再送されないことを確認した。これは実無線のAP離脱を再現した試験ではない。
