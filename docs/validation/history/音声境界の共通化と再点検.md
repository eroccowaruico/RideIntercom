# 音声境界の共通化と再点検

## 背景と判定条件

2026-10-30。通信方式・codec・effectの差し替え境界を維持し、共通処理と固有条件を整理する作業を二巡行った。機能、音声同一性、低遅延、接続継続を維持したまま通信コストと電力負荷を削減する[製品要求](../../requirements/製品要求.md)を適用する。125ms、欠落・重複・click・短い相槌・無音後の復帰の既存判定は緩めない。

## 点検と修正

| 工程 | 確認した問題・共通化 | 固有のまま維持する条件 |
|---|---|---|
| 最初のRTC点検 | MultipeerとUDPが別々に全件Bonjour探索していた。探索・認証をMultipeerへ集約し、認証済みpeerのUDP serviceを個別解決。媒体枠を置換するときは古いendpoint・flow・retry状態も破棄 | UDP parameters、native path migration、listenerはLocal所有。WebRTCはunordered / maxRetransmits=0 / UDP ICEを維持。GroupRelay・Local優先・先着採用は共通RTC層 |
| 最初のApp点検 | codecとsample rateを別々に適用していた。完全なencoding設定を一回で送信ownerへ渡し、同じ適用・保存・RTC通知経路を使用。正規化後の同値入力は無処理 | AAC/Opusの対応bitrateとfallbackはCodecの情報に従う。共通化のために最低bitrateや波形判定を変更しない |
| 再点検のRTC | route全体とUDPのbackoff計算を`ConnectionRetry`へ集約。policyに初期2秒・上限30秒を明示。認証messageのsenderと直接peerの一致を必須化 | 接続開始・timeoutはroute所有。UDPは新しい送信・認証・path変更で回復を試み、音声再送や周期pollingは追加しない。HTTP再試行はサーバー応答依存の別契約 |
| 再点検のApp | stop/rebuildのlock待ち中の旧音声が新graphへ入る問題を再現・修復。stopで世代を更新し、再構築中は受信拒否。Isolationの設定・bypass・診断snapshot反映をTX/peer/masterで共通化 | TXの同期DSP、RXのnative render・playout予約でsettling時間は異なる。実nodeの遅延を使い、固定値へ統一しない。準備・graph lockは各所有者 |
| 追加の再参加点検 | 同一Bonjour名の古いport cacheで再起動後の音声が不達になることをnative通信で再現。署名済みhandshake nonceでlistener世代を識別し、世代ごとに新service名を直接解決 | 同一制御sessionの重複handshakeは無処理。再認証は旧backoffを解除するが通常音声は解除しない。認証済みの既存UDPを制御切断だけで破棄しない |
| 初回制御接続の点検 | 厳格化したE2EがMultipeer内部のCFNetwork初期化によるpriority inversionを検出。stackをsymbolicateし、初回resource-loader生成の同期待ちと特定。端末内socket pairで一度だけ非同期準備 | native制御stream固有。UI・音声threadを待たせず、外部通信・周期処理・常駐socketを増やさない |
| 自動検証の共通化 | Appと独立音声E2Eの共通合格関数でruntimeWarnings / testFailuresも拒否。成功件数だけでnative実行時問題を見逃さない | Xcode build警告と実行時警告は区別する。所有processの試験後cleanupは障害による終了と区別する |

Codecのstream履歴・時刻・silence抑制・復帰・fadeは既存のStreamingCodecとPCMStreamTransitionを共通経路として維持した。Opusの3 packet残留とAACの1 packet残留、native priming、magic cookie、bitrate正規化はcodec特性であり、既存インラインコメントの根拠を残した。effect OFF時はMixer接続から外す既存処理を維持し、設定共通化でDSPを常時実行させない。

## peer-to-peer Wi-Fiと電力の確認

| 確認 | 根拠と扱い |
|---|---|
| Bluetooth単独へ自動移行するか | [Apple DTSの回答](https://developer.apple.com/forums/thread/749346)は現在のMultipeerによるBluetooth単独通信を否定している。[Bonjourの説明](https://developer.apple.com/forums/thread/747860)ではBluetoothの探索補助とWi-Fiのデータ通信を区別している。Bluetoothだけの音声へ移って節電する前提は置かない |
| Wi-Fiを使うことの電力負荷 | [Networkのpeer-to-peer設定](https://developer.apple.com/documentation/network/nwparametersprovider/peertopeerincluded(_:)-60331)は、探索・待受・接続の電力増大と不要時の停止を明記している。UDPという形式だけから消費電力の増減を決めない |
| 減らした処理 | UDPの継続全件browserを削除。認証済みの最大7相手だけ解決。接続失敗時のbackoff、同値設定の無処理、通話停止時のlistener・flow・探索の解放を維持。無音時の通信量とDSP休止は独立音声E2Eで回帰確認する |
| 残す資源 | APもセルラーもない近距離通話にはpeer-to-peer Wi-Fiを許可する必要がある。途中参加を受け付けるMultipeer探索と通話中のUDP listenerは残す。Wi-Fi機能OFFのBluetooth単独通話は提供しない |
| 証明範囲 | API資源の削減と自動試験による通信量・処理挙動の確認であり、実機のmAh・発熱・バッテリー持続時間を測定した結果ではない。屋外のAWDL遅延、距離、移動、ロック中の品質も実機確認が必要 |

## 最終検証

初期の音声E2Eは`ea57fba6`、codec周期差の修正後は`5efed70`と同じソース内容の隔離worktreeで実行する。後者のmanifestはpackage commit `69fe9870`とApp差分を記録し、全対象ファイルのhashをcommit内容と照合する。途中で別作業のArchive設定変更がmainへ入ったため、そのcommitも含む同一HEADをビルドし、検証中のソース変更は許容しない。主作業directoryに残る利用者のproject設定差分は変更・commitしない。

RTC packageは`--no-parallel --skip WorkerPairTests`で80件、native WebRTCは4件合格。WorkerPairはこの作業の対象外であり、全repository検証の完了とは表現しない。scriptsは59件合格。

追加点検では、最初の並列RTC再実行で8名試験が一度欠落した。期限切れ・overflow診断を追加した後の同条件3回は成功し、この一度の欠落を特定のdrop counterへ帰属する証拠はない。圧縮した耐久負荷と実時間ゲートの競合を避けるため、自動入口ではSwift Testingへ明示的に直列実行を指定する。試験内の8名同時配送と100ms鮮度期限、50ms native配送の基準は維持する。実時間8名音声E2Eも別processで検証する。

codec周期差の追加修正前の比較証跡rootは`/tmp/RideIntercomAudioE2E/commonization-20261030/final`。下表はその時点の値である。実通信の`network`はMacと再利用iPhone Simulatorの双方向音声であり、iPhone二台の屋外無線やBluetooth機器の測定ではない。遅延はcapture時刻からnative render出力までを測り、波形位置合わせの10ms分解能を加えて125ms以内を要求する。

| 実通信設定 | Mac側出力 | iOS Simulator側出力 | 判定 |
|---|---|---|---|
| Local、標準AAC・送信分離ON | 113.0ms | 100.0ms | 分解能10ms込み125ms以内 |
| Local、Opus・分離OFF | 56.9ms | 44.1ms | 同上 |
| Local、PCM・分離OFF | 51.3ms | 37.3ms | 同上 |
| WebRTC、標準AAC・送信分離ON | 107.7ms | 101.5ms | 同上 |
| WebRTC、Opus・分離OFF | 51.6ms | 45.6ms | 同上 |
| WebRTC、PCM・分離OFF | 46.0ms | 38.9ms | 同上 |

12測定すべてでcontinuityPassed=true、missingActiveRatio=0、matchedWindowRatio=1、longestMissingSeconds=0。capture・delivery・render・senderのdropは0。Mac/iOS双方、Local/WebRTCすべてのxcresultでruntimeWarnings・testFailures・skipは0。初回CFNetwork警告も解消した。これは検査窓内の欠落0という結果であり、任意の実機・無線条件での無欠落保証ではない。

設定切替の`switches`も2試験に合格した。codec・sample rate・bitrate・TX/peer/master分離を含む12段階と、native input processingの4回切替を測定。steady tone判定はすべて成功し、drop・output resetは0。codec設定切替で最大31ms、TX分離ONで60ms、受信graph切替で最大84msの無音があり、既存の120ms上限を満たした。切替全体の最大sample stepは0.0145（基準0.04未満）。入力処理再起動は26.3〜47.7ms。これらはnative node・converter再構成に伴う境界であり、通話音声の滞留時間へ加算しない。

8名の最終波形試験で見つけた周期差は、Codecが入力quantumとnative frameの最大公約数から必要量を計算し、任意metadataとして渡す修正を追加した。AudioMixerはcodec名に依存しない秒数を使い、Appはその接続だけを所有する。通常の整合した周期ではmetadataを送らず、余裕も0。非整合のAAC16kHz/20ms入力では10msだけを追加する。Codec35件、AudioMixer59件が合格。

追加修正後の`app-cadence-final`はMac/iOS各145件、失敗・skip・runtime warningは0。追加したApp結合テストでcodecの必要余裕が10msだけ受信sourceへ反映されることを確認した。App試験時の全source hashはcommit後も同一である。

追加修正後の最終音声証跡は`acceptance`。8名混在は、失敗時に止まる事前設定の3回連続実行（`eight-1`〜`eight-3`）をすべて合格。途中のplayout補正・reset、packet欠落・重複は3回とも0。各参加者540入力frameのうち送信は158〜235 packetで、無音区間による半分以上の削減を維持した。ネットワーク全体のbyte数や電流の測定値へ置き換えない。

追加修正後の全試験も合格した。`acceptance/acceptance-summary.json`に集計を保存し、全modeのsource-manifestとApp試験の全対象ファイルhashが一致することを確認した。検証用App差分をcommit `5efed70d`へ揃えた後も全hashは一致し、worktreeはclean。検証中に入った別作業の文書commitは音声ソースを変更していない。
