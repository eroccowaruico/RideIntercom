# 音声の連続性修復

## 依頼と対象

2026-10-29、iPhone同士の発話が途切れるとの報告に対し、追加済みの結合テストと音声E2Eを先にcommitし、判定基準を緩めず原因を修復して再検証するよう依頼された。再現試験は`404f9bc`にcommitした。[修復前の測定](音声同一性と途切れの再現.md)は削除せず保持する。

## 原因と変更

| 原因 | 確認した証拠 | 修復 |
|---|---|---|
| 新frame自身の長さまで加えて過負荷判定していた | 通信なしでも100 ms入力＋未再生tail数msで旧予約を破棄。破棄を外した比較では全文の一致窓100%、低出力率0%。5 msのtailを持つpackage回帰試験は修正前に失敗 | AudioMixerとSessionManagerは新frameの再生開始までの待ち時間で判定。単一frame長の上限と停滞時の最新音声への置換は維持 |
| 通話sourceの100 ms設定が正常なbatch配送にも不足 | 通常のtap・通信配送で受信予約約100〜200 msを観測。時刻補正だけ、VAD無効化だけでは直らない | TX sourceの待ち上限を200 msに変更。RXは以下の時刻再生設定を使用。通話hardware出力は200 ms、通信なし結合試験は100 msのまま |
| 送信側の到着順即時再生が100 ms入力の配送揺れを吸収しない | 受信・出力の修復後も、録音冒頭に70 msの欠落が残った。ウォームアップを含む診断でiOSの音声分離前プレイヤーにも80 ms欠落・一致窓92.9%を確認。送信packetと受信packetは同じ波形 | TXにも収録時刻再生を適用し、開始待機100 ms・最大待ち200 msを指定。50 ms遅れた100 ms入力を元の再生時刻へ予約するApp回帰試験は修正前に失敗 |
| 発話直前音声の保存がframe数だけに依存 | 日本語のiOS→Macでは受信予約破棄がなくてもLocal / WebRTCとも時間整合が崩れた。100 ms入力で最大2秒を送信sourceへ一括投入。20 ms / 100 msのApp回帰試験で必要な5 / 2frameに対し21frameを出す失敗を再現 | attack時間を覆う最小の全frame列だけを保持する。語頭の全frameと順序を維持し、古い無音の大量再投入をなくす |
| 受信packetの収録時刻を再生時刻へ反映していなかった | 同一runの受信packetを時刻通りに復元すると一致窓100%・低出力率0.16%で合格する一方、最終出力は一致窓95.3%・低出力率5.1%。到着の揺れの幅は約172 ms | AudioMixerへ相対収録時刻による予約を追加。RXに開始待機200 ms・最大待ち400 msを設定。無音render frameもhardware出力へ渡し、発話間の時間を詰めない |
| 単発の遅着で受信時計全体を再同期する候補が過敏だった | 200 ms / 400 ms設定前の候補は、Local・Opusの小さな遅れに再同期を重ねて欠落を拡大した。10 ms遅れの回帰試験で後続音声までずれる失敗を確認 | 上限内の遅着はplayerの時刻予約で経過部分だけを省略し、後続の時刻は維持。完全に期限を過ぎたpacketも再生しない。開始待機200 msで実測約172 msの揺れを覆う |
| Mixer sourceと最終出力の予約量に過去のrender境界を使っていた | 日本語12条件中11条件が通った候補でも、Local→iOSの最終出力だけ予約リセット1回・最長70 msが残った | SessionManagerとAudioMixer sourceは実時間modeでhost時刻までplayer位置を補正。補正だけでは通話の2batch配送に100 ms上限が不足したため、通話時は200 ms上限を開始時に指定する。固定待機は追加しない。直接結合の100 ms構成は維持し、offlineは明示的なrenderだけで時計を進める |
| 収録時刻の基準より先に空のplayerを開始 | `diagnostic-empty-start-20261029`で最初の予約時のplayer位置が-512 / -256sampleとなる例を確認。既定設定の片方向に70 msの欠落と受信時計再同期が残った | 時刻再生sourceは最初のbuffer予約と同時にplayerを開始し、sample 0と収録時刻の基準を揃える。二重startは時計を再起動せず、stop後は再び最初の音声を待つ |
| Codec・bit rate変更だけでも送受信Mixer全体を破棄 | 既定→PCM16→Opusの測定で、切り替え後に200〜460 msの欠落。App回帰試験ではCodec変更だけでengineが増え、受信sourceの予約履歴が0へ戻る6件の失敗を再現 | packetの符号化設定とRTC policyだけを更新し、engine・effect・収録時刻と受信予約を維持。PCM formatなどgraphに必要な変更だけは再構築する |
| OpusのpacketごとにOS変換器を生成・破棄 | 上記候補の英語12条件中11条件は合格したがLocal→MacのOpusで再び予約破棄12回・最長320 msの欠落。該当区間にOSのconverter reporter制限ログが集中 | Codecに排他的な変換器再利用を追加。待機16個まで、方向・format・bit rate・cookieを照合し、返却時にstreamをreset。後続E2Eで効果を検証 |

無制限予約、VAD無効化、診断用の毎frameログは比較試験だけで使い、製品変更には残さない。最終出力の時計補正は、旧合計予算の判定と組み合わせただけでは直らなかったが、予約・時刻再生を修正した後の残る出力段の誤検出に適用した。時刻再生の修復後、音声分離を元の100%へ戻した英語12測定では、PCM16・Opusの10測定は合格した一方、既定設定のiOS→MacだけLocal / WebRTCで低出力率2.67% / 2.63%となった。一致窓はいずれも100%、受信source破棄は0回だった。通話presetは処理音80%・原音20%とし、弱い音節を保持する。背景音抑制とのtradeoffは実機確認へ残す。packageの変更とその単体検証を終えてからAppの設定変更を適用した。Appに独自DSPは追加していない。送信には100 ms、受信には200 msの初期待機を設けるため、合計300 msの遅延が増える。これは配送揺れを覆う有限の設定で、端末間の総遅延保証ではない。設定値と実適用値の診断報告は同じpresetを参照し、有効・無効の両方で一致を試験する。

予約量の契約は[AudioMixer](../../spec/packages/Audio/AudioMixer.md)・[SessionManager](../../spec/packages/Audio/SessionManager.md)、通話設定は[AudioMixer設定](../../spec/App/Configuration/Bindings/Audio/AudioMixer.md)・[音声分離設定](../../spec/App/Configuration/Bindings/Audio/Effectors/SoundIsolation.md)を正本とする。

## 最終回帰中に見つかった切断クラッシュ

音声28測定の合格後、`.validation/audio-repair-final-regression-20261029`と`audio-repair-final-regression-retry-20261029`のUI試験で、Disconnect直後／グループ削除後にCFNetwork `_netServiceMonitorCallBack` → `_MonitorCancel`のEXC_BAD_ACCESSを2回確認した。browserの操作をmainへ寄せるだけでは、actor上で生成・解放されるMCSessionを含むnative資源の寿命が揃っていなかった。MainActorの所有者へnative資源をまとめ、生成・操作・isolated deinitによる最終解放を同じactorに統一した。delegateの世代照合と停止後callback拒否は維持する。

MainActor所有修正後のRTCは57件成功。`.validation/audio-repair-native-lifetime-ui-20261029`ではUI4件＋破損復旧1件がすべて成功し、3回の切断・再接続とグループ削除でクラッシュしなかった。不要なtryと、デフォルト引数でmain actor上の設定を参照するコンパイラ警告も除去した。設定値・試験のassertionは変更していない。これらを含めた最終ソースで全体回帰と音声28測定を再検証し、すべて成功した。

再実行中のWorker pairは断続的に失敗した。エラーの型とコードだけの一時診断により、peer購読更新のHTTP要求が`NSURLErrorDomain -1005`（networkConnectionLost）となり、通話全体を切断していたと特定した。冪等な`pull`だけに、初回を含め3回・総期限25秒以内の再試行を追加した。接続断2回後の成功、持続障害の3回打ち切り、新規session・認証失敗・cancelを再試行しない4件の回帰試験を追加し、修正前2件の失敗から成功を確認した。RTCは59件＋native WebRTC 2件成功。一時診断出力は除去し、Worker pairの判定・5秒の条件待ち・4秒のleaseは変更していない。

全体回帰の`audio-repair-accepted-regression-20261029`は、上記Worker失敗と、MainActor化したdelegate試験が接続callbackを待たず認証を実行する順序依存を検出したため中断した。delegate試験はcallback配送完了を明示的に待つよう修正し、assertionは維持した。失敗・中断runは合格へ読み替えない。
