# リアルタイム音声の遅延と連続性

## 対象と判定

2026-10-29〜30、`b5591e43540e5c6449f5da7cdd159305daf8df09`からの作業ツリーを検証。各実行の`source-manifest.json`を対象sourceの正本とし、buildから受入までの変更を拒否する。全体回帰と独立した音声E2Eを区別する。

| 条件 | 基準 |
|---|---|
| 実発話 | 既存の全文照合・200ms区間照合に加え、実通信の有声欠落率を0とする |
| 遅延 | 相手のcaptureと実renderを共通host clockで比較。単一の音声offsetを使い、計測余裕10msを含め125ms以下 |
| 微小な欠落・重複・クリック | 2ms区間のtone残差と隣接sample差を検査。1ms欠落・重複・クリックを注入した負例が失敗すること |
| 会話 | 1〜3秒の無音と短い「うん」「ふん」を含む2声を使用。相槌を削除した負例も拒否 |
| 処理待ち | capture、Appへの配送、render、送信待ちの内部破棄0。遅延音声の再送で成功にしない |
| 結果の区別 | Debug / Release、ローカル自動検証 / 物理端末 / 実サービスを区別。失敗を条件緩和や再試行だけで成功へ書き換えない |

## 確認した原因と変更

| 区間 | 原因と対応 |
|---|---|
| 入力・Mixerの出力 | 通常のtapが約100msをまとめる。native render quantumごとの有界handoffへ変更 |
| 送信DSP | hardware出力と別のplayer予約を経由していた。同期offline Audio Unit処理と10ms packet化へ変更 |
| 受信から機器出力 | Mixerで再生後、App actorを経て別engineへ再予約していた。入力・受信Mixer・機器出力を同じengine clockへ接続し、通知は観測だけにする |
| VAD | 無音中だけ先頭を保持して発話開始時に一括送信し、packet間隔が揺れた。発話中も同じ短いlookaheadを維持して各区間を1回だけ送る |
| 静音中の遅延回復 | 通常の20ms captureに含まれる2個の10ms packetを、遅延したburstと誤認。通常batchの余裕と実際の静音burstを区別 |
| AAC | monoのELD v2はconverter作成後に変換失敗し、従来試験ではPCM代替が紛れた。実際に変換できるAAC-ELDを選び、streamのencoder/decoder履歴を保持する |
| OS設定 | 変化していないvoice processing設定まで再適用していた。成功した前回値との差だけを適用し、部分失敗時は全設定を再適用 |
| 受信effectの切替 | 実行中の接続変更で、playerが再生中を返したまま無音になる。変更経路に流入するsourceの予約と時計だけ初期化し、次のPCMから再開。別経路と停止中sourceは初期化・開始しない |
| 再生予約の境界 | `lastRenderTime`の開始だけを参照すると、すでに描画済みのブロックへpacketを予約して先頭が欠ける。render captureの実ブロック長で終端を求め、明示時刻の下限へ反映 |
| 設定後の音声復帰 | 宣言されたnative遅延を超えて無音が続くと、音声が戻る前にfade-inが完了していた。実際の音声復帰からfade-inし、Appはnative接続変更前に出力保護を要求 |
| ネイティブclock | host時刻の観測揺れと実PCM欠落を混同しないようsample clockで連続時刻を導出。実sampleの飛びは保持 |
| 実行負荷 | monoのsampleごとの配列コピーとkey path検査、packetごとのUDP宛先名再生成を削減。値と拒否条件は保持 |
| RTC | 制御は信頼あり、音声はUDP / unordered・maxRetransmits 0。TCP ICE・TCP TURN・信頼あり音声fallbackを拒否 |
| 受信開始時の並べ替え | 相手の先頭packet番号が0以外だと、実際の欠番がないのに15msの猶予を待っていた。任意の番号から即時開始し、観測した欠番だけを待つ |
| UDPと制御の実行境界 | UDPもBonjour・制御のMainActorを同期経由していた。媒体peerのsnapshotを使って直接datagram queue / event sourceへ渡す。制御actorを占有する負例で送受信締切を検査 |
| Appの送信待ち | 符号化後の送信workerもMainActorに戻っており、UI・制御の処理が終わるまでpacketが止まることを再現。workerを独立させ、既存の100ms・64件上限、期限破棄、停止・ミュート時の取消と単一送信を保持 |
| Appの入力・受信 | 入力のVAD・DSP・符号化と受信decode・再生予約にもMainActor待ちが残っていた。graphの直列所有を送受信で分離し、収録workerとRTCの独立購読から直接呼ぶ。UIへは有界の観測通知を渡す |

## テストの修正

Macのfixtureは未来のPCM時刻を通知せず、完了した10ms区間を配送する。iOS fixtureもcapture clockに従い、実際に失われたcapture区間の音声を後へずらさない。録音probeは領域を事前確保し、render callbackで動的配列を拡張しない。これらは不具合を隠す補正ではなく、時刻と実出力を正しく記録するための修正であり、それぞれ回帰テストを設けた。
